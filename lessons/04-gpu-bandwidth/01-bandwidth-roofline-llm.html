GPU Bandwidth & Roofline · Lesson 04 · L0 + optional L2

为什么 TFLOPS 很高，LLM 还是可能跑不快？

买二手卡时最常见的对比是：显存多少、带宽多少、TFLOPS 多少。问题是这三个数字回答的是三件完全不同的事。今天把它们压成一个能实际做判断的模型。

真实问题

两张卡：A 的算力高很多，B 的显存带宽高很多。跑本地 LLM 到底谁更快？

答案不能只看卡，要先问 workload 每搬一份数据会做多少计算。

先把三个指标拆开

指标它回答什么
VRAM/HBM capacity模型、KV cache、context、buffers 能不能放下
Memory bandwidth每秒能把多少 bytes 喂给 GPU
Compute throughput每秒能做多少目标 datatype 的运算

16 GB 显存说的是容量，不自动告诉你带宽；1 TB/s说的是搬运速度，也不自动告诉你 FP16/INT8/FP4 算力。

1. Theoretical bandwidth 和真实 bandwidth 不是一回事

厂商规格给的是 theoretical bandwidth。真实 kernel 只能拿到 achieved/effective bandwidth。

最简单的 copy：

read N bytes+ write N bytes= 2N useful bytes

如果耗时 t：

effective bandwidth = 2N / t

但 profiler 看到的 DRAM bytes 可能不同，因为 cache、coalescing、transaction granularity 都会改变真正下到显存的流量。

2. Arithmetic Intensity：每搬 1 byte，你做多少计算？

Arithmetic Intensity = FLOPs / bytes transferred

比如：

  • AI = 1 FLOP/B：搬 1 byte，只做 1 次浮点工作；
  • AI = 100 FLOP/B：同样 1 byte，能支持大量重复计算。

上一节的 tiling 为什么重要？因为它不改变 GEMM 的数学结果，却减少 global bytes：

reuse ↑→ global bytes ↓→ AI ↑

3. 最小 Roofline：性能有两块天花板

第一块是 memory roof：

memory-limited performance = memory bandwidth × AI

第二块是 compute roof：

compute-limited performance = compute throughput

所以真正的上限是：

Performance ≤ min(compute roof, bandwidth × AI)

4. Ridge point：到底从什么时候开始“不缺带宽了”？

两条 roof 相交的位置：

AIridge = compute throughput / memory bandwidth

假设一张抽象 GPU：

  • 20 TFLOP/s
  • 500 GB/s

它的 ridge：

20 × 1000 / 500 = 40 FLOP/B

所以：

  • AI < 40：memory roof 更低；
  • AI > 40：compute roof 更低。

5. 为什么只加 TFLOPS 对低-AI workload 可能完全没用？

GPU AGPU B：算力×2GPU C：带宽×2
Compute20 TFLOP/s4020
Bandwidth500 GB/s5001000
Ridge40 FLOP/B8020

看一个 AI=4 的 workload：

  • GPU A：500 × 4 = 2 TFLOP/s
  • GPU B：还是 500 × 4 = 2 TFLOP/s
  • GPU C：1000 × 4 = 4 TFLOP/s

算力翻倍，性能上限没动；带宽翻倍，性能上限翻倍。

这就是“不能拿 TFLOPS 直接排所有 GPU workload”的数学原因。

6. 反过来：高 AI workload 更吃 compute

如果 AI=80：

  • GPU A：被 20 TFLOP/s compute roof 卡住；
  • GPU B：可以到 40 TFLOP/s；
  • GPU C：带宽更高，但仍只有 20 TFLOP/s compute roof。

所以不存在“带宽最重要”或“算力最重要”的万能结论。

7. Cache 怎么放进 Roofline？

真实 GPU 不只有 HBM/VRAM 一层。

如果某个数据被 L2 命中：

L2 hit→ HBM traffic ↓→ HBM-level AI ↑

但 L2 本身仍要提供带宽。

所以高级 profiler 会画 hierarchical roofline：HBM、L2、L1、LDS 都可以有自己的 traffic 和 roof。AMD ROCm Compute Profiler 就明确支持这种分层分析。

8. Roofline 不是万能解释器

Roofline 只告诉你 throughput ceiling。

如果 kernel 离两条 roof 都很远，原因可能是：

  • resident warps 太少；
  • dependency latency；
  • divergence；
  • bad coalescing；
  • bank conflicts；
  • launch overhead；
  • 软件/编译器根本没走目标硬件路径。

所以前面的执行模型没有白学：

scheduler / latency+ reuse / tiling+ Roofline

9. 现在把它接回本地 LLM：Prefill vs Decode

Prefill

一次处理一批 input tokens，大 GEMM 更容易形成并行与 data reuse。

通常更偏 compute-bound。

Decode

token-by-token 生成，每一步都需要新的模型计算，并伴随 weights 与 KV state traffic。

通常更偏 memory-bandwidth-bound。

NVIDIA Dynamo 和 AMD Infera 都使用这个阶段划分。但它不是绝对规则：batch、concurrency、context、模型结构和 backend 会改变实际 bottleneck。

10. 为什么量化常常特别影响 decode？

假设 memory-bound 阶段主要在扫 weights。

把每个 weight 的 bytes 降低：

weight bytes ↓→ bytes/token ↓→ AI ↑→ same GB/s does more useful work

这不等于“4-bit 必然 4× 快”。还要付：

  • dequantization；
  • scale / metadata traffic；
  • packing；
  • kernel/backend 支持；
  • quality。

11. KV cache：decode 的 bytes 不只来自 weights

随着 context 与 concurrency 增大，KV cache 的 capacity 和 traffic 也会进入瓶颈。

这意味着两张同带宽 GPU，如果一个能把更多 active KV 留在高速本地 memory、另一个需要 offload，真实结果可能完全不同。

KV 的精确 size 公式和 layout 后面单独讲。

垃圾佬现在应该怎么比较卡？

  1. 先问 model + KV 是否 fit。
  2. 再判断你的使用是 decode-heavy 还是 prefill-heavy。
  3. 查目标 precision 的真实 compute path，不只看一个通用 TFLOPS。
  4. 查 raw memory bandwidth。
  5. 看实际 backend/benchmark 的 achieved bandwidth 与 tokens/s。
  6. 估算或 profile arithmetic intensity。
  7. 找 ridge point。
  8. 如果 kernel 离 roof 很远，再回头查 occupancy、scheduler、cache、coalescing、软件支持。

教材补全：Roofline 是上限模型，不是性能预测器

Worked Example：decode 为什么常被带宽卡住

极简化地看，一次 decode step 需要把大量权重读入参与计算。如果一个模型每生成 token 需要有效读取约 20 GB 权重，而可持续有效带宽约 600 GB/s：

idealized upper bound
≈ 600 / 20
≈ 30 token/s

这只是非常粗的带宽上限：真实实现还包含 cache、kernel efficiency、KV、量化解码、同步与其他流量。

Arithmetic Intensity

AI = operations / bytes moved

低 AI 更容易撞 memory roof；高 AI 更可能撞 compute roof。Prefill 与大 batch 往往比单 token decode 有更高的计算复用，因此瓶颈可能不同。

实验预期

  • 单用户 decode 常更接近 memory-bound。
  • 扩大 batch / prompt matrix 后，计算单元利用率可能提高。
  • 理论显存带宽高，不代表 backend 能达到同样有效带宽。

排错

  1. 先确认模型/量化实际每 token 需要搬多少数据。
  2. 不要用厂商峰值带宽冒充持续有效带宽。
  3. 检查是否被 CPU offload / PCIe / kernel implementation 限制。
  4. 区分 PP 与 TG；它们可能撞不同 roof。

无 GPU 怎么办？

可用厂商公开规格 + 模型文件大小做上限估算练习，但必须标注为 theoretical bound，不能写成实测 TG。

Decision Rule

Roofline 用来排除不可能、定位瓶颈方向，不用来替代 benchmark。理论上限与真实性能之间永远需要实现效率证据。
