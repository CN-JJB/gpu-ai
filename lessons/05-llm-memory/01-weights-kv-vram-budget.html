Local LLM Memory · Lesson 05 · L0

模型到底能不能塞进这张显卡？

垃圾佬买卡最危险的问题不是“这卡多少 TFLOPS”，而是模型下载完才发现：权重能塞，KV 塞不下；单用户能跑，一开长上下文或并发就 OOM。今天先学会在买卡之前粗算。

真实问题

我有一张 8 GiB 显卡。一个“7B 4-bit”模型文件看起来只有几 GB，是不是就稳稳能跑 32K context？

不能这么判断。

第一条公式：显存不只有 weights

weights+ KV cache+ runtime/workspace≤ VRAM

这是 baseline，不是 runtime 保证。

1. 权重：参数量 × 每参数有效 bit 数

weight bytes ≈ parameter count × effective bits per weight / 8

7B 参数如果真的每个参数只占：

bpw纯 weight payload
16约 13.04 GiB
8约 6.52 GiB
4约 3.26 GiB

但真实的“4-bit”格式往往还有 scale、metadata、某些未量化 tensor、alignment，所以课程更愿意让你输入 effective bpw。

2. 三个数字千万别混

Checkpoint file

磁盘上的文件。受 serialization、shards、metadata、dtype mix 影响。

Weight payload

参数真正的数据体积 baseline。

Runtime VRAM

还要加 KV、activation/workspace、allocator、backend converted layout 等。

文件 5 GB ≠ 运行只需要 5 GB 显存。

3. KV cache：为什么聊天越长，显存越吃越多？

autoregressive decode 每次只生成一个新 token。如果每一步都重新计算之前所有 token 的 K/V，会浪费大量计算。

所以 inference 会缓存之前 token 的 key/value。

Hugging Face 的基本 cache tensor 可以写成：

K: [batch, kv_heads, seq_len, head_dim]
V: [batch, kv_heads, seq_len, head_dim]

有 K 和 V 两份，所以一个标准 attention layer：

KV bytes = 2 × batch × seq × kv_heads × head_dim × bytes/element

再乘所有需要 cache 的 layers。

4. 每增加一个 token，要付多少 KV？

把 batch=1、seq=1 留下来：

KV bytes/token/sequence = 2 × layers × kv_heads × head_dim × bytes/element

这条式子非常适合垃圾佬。

因为你只要读一份 config.json，就能先估一大半。

5. MHA / GQA / MQA 为什么会影响显存？

假设：

  • 32 layers
  • 32 query heads
  • head_dim = 128
  • FP16 KV = 2 bytes
模式KV headsKV / token4096 tokens
MHA32512 KiB2 GiB
GQA8128 KiB512 MiB
MQA116 KiB64 MiB

Hugging Face LlamaConfig 就用 num_key_value_heads 区分这三类。

所以看到“32 attention heads”还不够。一定还要查 KV heads。

6. Context 与 concurrency 是乘法，不是加法

普通 full-attention DynamicCache 下：

KV/token× context× active sequences

context 从 4K 到 32K，是 8×。

同时 concurrency 从 1 到 4，又是 4×。

KV baseline 合起来就是 32×。

7. 做一个 7B-like 抽象预算

这不是某个真实模型，只用一组便于练习的参数：

  • 7B params
  • effective 4.5 bpw
  • 32 layers
  • 8 KV heads
  • head_dim 128
  • FP16 KV
  • 4096-token context

权重：

约 3.667 GiB

KV：

128 KiB/token/sequence → 512 MiB / 4K sequence

如果 4 个 active sequences：

2 GiB KV

再人为留 1.5 GiB runtime reserve：

3.667 GiB weights
+ 2.000 GiB KV
+ 1.500 GiB reserve
= 7.167 GiB

对 8 GiB 卡而言，只剩约 0.833 GiB。

这不应该被写成“稳了”。

8. 为什么公式算得对，运行还可能不一样？

因为现实 backend 还会改变 memory policy。

  • Static cache：可能按 max length 预分配，当前 token 少也占大空间。
  • Paged KV：runtime 管 block pool，reserved bytes 不等于当前 used bytes。
  • Sliding-window：某些层到窗口上限后不再继续线性增长。
  • Quantized KV：降低 cache bytes，但有计算/精度/支持代价。
  • Prefix reuse：多个请求可能共享已缓存的 prefix block。
  • Offload：把 KV/weights 放 RAM/NVMe/别的 GPU，但产生传输成本。

TensorRT-LLM 就是很好的现实提醒：它的 runtime 可以主动把大量剩余 VRAM 管理成 paged KV pool。

9. 为什么必须留 Headroom？

你还没有数：

  • runtime buffers
  • temporary activations
  • allocator fragmentation
  • CUDA/ROCm context
  • graph capture
  • desktop/display
  • 其他进程

“estimated = 7.9 GiB，VRAM = 8 GiB”不是 fit 结论，而是危险信号。

10. 真模型怎么调查？

  1. 先读 model card。
  2. 打开 config.json。
  3. 找 layers / attention heads / KV heads / head_dim。
  4. 看有没有 sliding window、特殊 layer type、per-layer config。
  5. 从 safetensors metadata 或仓库 metadata 查参数量与 dtype mix。
  6. 确认你下载的究竟是哪种 quant format。
  7. 查目标 backend 的 KV dtype、paged/static policy、offload、workspace。
  8. 用 baseline calculator 做 preflight。
  9. 最后才在真实 runtime 测 peak/steady VRAM。

11. 这和上一节 bandwidth 有什么关系？

容量问题解决“能不能放”。

放下之后，decode 还要不断读取：

weights+ KV state→ memory traffic/token

所以：

量化不仅减少容量，也可能减少 memory-bound decode 的 bytes/token。

而 offload 虽然扩容量，却可能把 PCIe/RAM/SSD 变成新的 bandwidth roof。

教材补全：显存预算要分“静态占用”和“随请求增长的占用”

Worked Example：24 GiB 为什么不等于能塞 24 GiB 权重

GPU capacity: 24 GiB
weights:      19 GiB
runtime/workspace: 1.5 GiB
KV target:     2.5 GiB
headroom:      1 GiB

total: 24 GiB

这已经几乎没有 allocator fragmentation、额外 buffer、并发增长空间。工程上通常不能把“刚好等号”当作稳定 fit。

预算公式

required VRAM
≈ weights
+ KV cache
+ temporary/workspace
+ runtime/backend overhead
+ safety headroom

其中 KV 还会随 context、batch/concurrency、KV heads、dtype/cache policy 改变。

实验预期

  • context 增长时，KV 占用应呈可解释增长。
  • 并发增加时，KV/slot 需求通常上升。
  • 更小 quant 先降低 weights，占用变化不必等比例映射到速度或质量。

排错

  1. 先确认模型文件大小不是实际 VRAM 占用的唯一来源。
  2. 确认是否有 CPU offload；“没 OOM”不等于全在 GPU。
  3. 区分 reserved/allocated/free 等不同 telemetry 语义。
  4. OOM 时逐项缩减 context、concurrency、offload/weights，而不是一次全改。

无目标 GPU 怎么办？

可以先做纸面 budget，把所有未知数明确写成 UNKNOWN 或范围。只有真实 runtime telemetry 才能把估算升级成实测。

Decision Rule

买卡前先做 VRAM budget；如果只有“模型文件 < 显存”这一条依据，视为证据不足。必须给 KV、runtime/workspace 和 headroom 留位置。
