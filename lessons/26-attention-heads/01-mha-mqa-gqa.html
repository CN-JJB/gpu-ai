LLM 架构 3 — MHA / MQA / GQA：为什么 KV Heads 比你想象中重要

1. Query heads 和 KV heads 是两个数字

很多人看到：

32 attention heads

就默认 KV 也有 32 heads。

现代模型未必。

Hq = query heads
Hkv = key/value heads

2. MHA

Hq = 32
Hkv = 32

每个 query head 有自己的 K/V head。

3. MQA

Hq = 32
Hkv = 1

不是“只有一个 attention head”。

是：

32 Q heads
share
1 K head + 1 V head
MQA 仍然可以有很多 Query heads。

4. GQA

取中间：

Hq = 32
Hkv = 8

每 4 个 query heads 共用一组 K/V。

Q0 Q1 Q2 Q3 → KV0
Q4 Q5 Q6 Q7 → KV1
...

5. 为什么这首先改变 KV Cache？

缓存 shape 是：

K [B,Hkv,S,Dh]
V [B,Hkv,S,Dh]

所以每 token：

2 × layers × Hkv × Dh × bytes

公式里没有 Hq。

6. 用真实量级算

假设：

32 layers
32 query heads
head_dim 128
FP16 KV
类型KV headsKV/token32k context
MHA32512 KiB16 GiB
GQA8128 KiB4 GiB
MQA116 KiB0.5 GiB

同样 32 层、同样 query heads、同样 head_dim，只改 KV heads。

7. 这对垃圾佬为什么比“8B”更有用？

两个都写 8B 的模型：

Model A: Hkv=32
Model B: Hkv=8

权重文件可能差不太多，但 32k context 的 KV 可以差 4 倍。

所以：

same parameter count
!=
same context VRAM

8. GQA 也改 attention projection weights

Q projection：

d → Hq×Dh

K/V：

d → Hkv×Dh

Hkv 变小，Wk/Wv 也变窄。

但 Wq/Wo 仍然大，所以整个模型参数不会按 KV 缩减倍数一起缩。

9. Decode 为什么更吃这个红利？

每生成一个 token，都要 attention 到历史 K/V。

current Q
→ read historical K/V length S

K/V 更少：

  • cache 更小；
  • memory traffic 更少；
  • concurrency 更容易；
  • 长 context 更容易 fit。

10. 为什么不所有模型都用 MQA？

因为独立 K/V 表达能力和模型质量也是设计目标。

可以理解为：

MHA
more KV capacity

MQA
maximum sharing

GQA
middle ground

GQA 论文就是在做这个质量/效率折中。

11. 不是 runtime 开关

不能拿一个训练好的 MHA 模型，在 llama.cpp 里写：

--gqa 8

就自动变成正确 GQA。

这些 K/V projection weights 是模型训练出来的结构。

12. GQA 和 KV 量化可以叠加

architecture:
Hkv 32 → 8

runtime:
KV FP16 → Q8

两个维度都会减少 KV bytes。

但是：

GQA = architecture
KV quant = representation

不要混。

13. 以后选模型先查这几个字段

num_hidden_layers
num_attention_heads
num_key_value_heads
head_dim
KV dtype
context
concurrency

然后你自己就能算，不需要等别人说“这个模型吃显存”。
