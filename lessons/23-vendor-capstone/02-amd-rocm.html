Vendor Capstone · AMD · L0→L2

AMD / ROCm 实战闭环：从设备支持到 HIP LLM 真实 offload

AMD 的 capstone 核心不是“把 ROCm 装上”。你要学会把 exact GPU、OS/kernel driver、ROCm runtime、HIP libraries、应用 backend、model kernel 与 benchmark 绑定成一条可复现证据链。这样即使未来 ROCm 支持矩阵变化，你仍知道怎样重新验证。

Prerequisite Check

完成 GCN/RDNA/CDNA 课程，知道 CU/wave/LDS 是硬件层概念，也知道“AMD GPU 有计算能力”不等于“当前 ROCm 支持 exact device”。

真实问题：为什么 AMD 本地 LLM 最怕一句“理论上支持”？

因为“理论上”常混合了不同命题：ISA 能执行、Linux driver 能枚举、ROCm 官方支持、HIP runtime 能打开、llama.cpp build 含 HIP、目标 quant 有 GPU kernel。真正可用必须逐层通过。

1. ROCm evidence chain

exact PCI device / ASIC
→ kernel GPU driver
→ ROCm userspace runtime
→ HIP compiler/runtime + libraries
→ application HIP backend
→ target model/quant kernels
→ offload observed
→ fixed PP/TG + quality

稳定教材永远保留这条链；具体版本号则在你学习时查询官方 support matrix。

2. “ROCm supported”到底要记录什么？

不要只写 yes/no。至少记录：

  • exact GPU/device family；
  • OS/distribution；
  • kernel/driver path；
  • ROCm version；
  • 官方支持、community/unsupported workaround 还是其他 backend；
  • 目标 application build/runtime；
  • 测试日期。

这让未来升级后可以判断是硬件问题还是支持生命周期变化。

3. HIP：源码可移植不等于 kernel 自动最优

HIP 允许很多 CUDA 风格代码迁移到 AMD，但 warp/wave、memory hierarchy、matrix instruction、library 和 compiler behavior 都可能不同。一个“能编译”的 kernel 不代表充分利用 AMD。

性能问题应检查：

  • wave utilization / divergence；
  • VGPR/LDS resource pressure；
  • memory coalescing/cache；
  • matrix/low-precision kernel coverage；
  • launch/host overhead。

4. 应用是否真的用 HIP backend？

从应用日志或 build info 找证据：检测到哪个 AMD device、分配了多少 VRAM/HBM、offload 多少 layer/tensor、使用哪种 kernel path、是否出现 CPU fallback。

如果只有“程序成功生成文本”，你尚未证明 GPU inference。

5. Radeon 与 Instinct：同一 ROCm 生态，不同部署风险

消费 Radeon 更容易放进普通台式机，但 exact ROCm support 与 kernel maturity 需查；Instinct 可能有 HBM/计算优势，却可能要求服务器散热、特殊形态、更多功耗与平台条件。

因此不要写“AMD = Radeon”或“MI = 便宜大显存神卡”。

Worked Example：ROCm 应用能启动，但速度和 CPU 差不多

Step 1: verify device chosen by app
Step 2: verify GPU layers / tensors offloaded
Step 3: inspect VRAM/HBM allocation
Step 4: look for unsupported quant / CPU fallback
Step 5: separate PP and TG
Step 6: monitor clocks, power, temperature
Step 7: keep same model/build/protocol and change one variable

如果 offload 很少，先修 fit/config/kernel；如果全部 offload 但 TG 低，检查 memory/quant kernel；如果 PP/TG 都低，检查 build、device clocks、driver/runtime。

6. Vulkan 等 alternative backend 怎么定位？

一个 Radeon 可能通过 Vulkan backend 工作，即使当前 ROCm path 不合适。这并不矛盾。你应把结论精确写成：

exact device + Vulkan backend = measured usable
exact device + ROCm/HIP backend = blocked / unverified

而不是泛化成“这卡支持/不支持 LLM”。

7. Benchmark 与质量

固定 model artifact、quant、prompt/token identity、context、GPU offload、KV type、flash-attention setting、runtime build、warmup/repetition。性能至少分 PP/TG，改变 quant/backend 时配套固定质量 corpus 或任务。

Why it matters

  • ROCm 支持矩阵会变化，方法必须比版本表寿命更长。
  • AMD 潜在价格/显存优势只有通过应用 backend 后才真实存在。
  • 精确的 blocked conclusion 比“AMD 不行”更可迁移。
  • Radeon/Instinct 的物理部署差异可直接改变垃圾佬性价比。

常见误区

  • “ROCm 安装成功 = 应用 HIP 加速成功”——缺 application/kernel/offload。
  • “HIP 是 CUDA 翻译器，所以性能一样”——硬件与优化不同。
  • “官方不支持 = GPU 完全不能算”——其他 backend 可能工作，但证据等级不同。
  • “Vulkan 能跑 = ROCm 也能跑”——两条独立 software path。
  • “MI 卡 HBM 大就适合桌面”——服务器物理/散热/供电可能拦截。

实践路径

作者阶段完成 support worksheet、实验说明和 evidence schema；你以后上课时根据当时 ROCm 官方文档选择 exact supported path，再运行受控 benchmark。若无 AMD 卡，使用文档/fixtures 完成 L0。

Retrieval Practice

  1. 为什么“ROCm 支持”必须记录 device+OS+version+date？
  2. HIP code 能编译为什么不保证 AMD 上高效？
  3. 怎样证明 LLM 应用真的通过 HIP offload？
  4. Vulkan 可用、ROCm 不可用时应如何写精确结论？
  5. Radeon 与 Instinct 的硬件优势为什么需要不同系统 gate？
  6. 改变 quant/backend 时为什么必须配质量检查？

Decision Rule

AMD 路径只有 exact device × current runtime × application backend × model kernel × measured workload 全链通过后，才进入购买/性能比较。Unsupported workaround 可以学习，但不能冒充官方支持或生产级稳定性。

Transfer

这套“多个 backend 可独立成立”的思维尤其适用于 Intel/AMD。换 NVIDIA/Apple 时同样记录 exact backend，而不是只写厂商品牌。
