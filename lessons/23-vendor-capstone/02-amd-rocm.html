Vendor Capstone 2 — AMD ROCm/HIP

1. AMD 第一身份不是“RX 7000”，是 exact gfx target

amd-smi list
rocminfo
hipconfig --full

记录 exact GPU + gfx* + ROCm/HIP version。

2. 当前 llama.cpp HIP 构建

HIPCXX="$(hipconfig -l)/clang" HIP_PATH="$(hipconfig -R)" \
cmake -S . -B build \
  -DGGML_HIP=ON \
  -DGPU_TARGETS=<exact-gfx-target> \
  -DCMAKE_BUILD_TYPE=Release

cmake --build build --config Release -j

upstream 当前说明 GPU_TARGETS 可省略；课程显式写它是为了让 Evidence 更清楚。

3. 不要把 workaround 悄悄当官方支持

如果必须使用 gfx override、社区 patch、特殊 build：

support_state = community-enabled

这会进入 TCO/维护成本。

4. 第一轮优化仍由证据选

  • PP 弱 → FA/backend；
  • TG 接近 bandwidth roof → quant/memory traffic；
  • 长 context 内存紧 → KV/context；
  • 设备根本不在当前官方支持矩阵 → 先解决 support gate。

学生闭环 — AMD ROCm

硬件门槛：L0 preflight；有对应硬件时 L1/L2 做真机增强。

成本：0 元主路径，不要求集齐四个生态。

风险：safe；只做 build/device/runtime 检查和 benchmark。

替代路径：没有 AMD ROCm 硬件就只做 Experiment 41 的 preflight，并用已有 Evidence/官方资料完成生态映射。

能力目标

  • 把 hardware identity、driver/runtime、backend build、model artifact、execution config 分层记录。
  • 把同一 benchmark contract 迁移到 AMD ROCm，只替换厂商特有的 discovery/build 命令。
  • 知道“能运行”与“使用预期加速路径”是两个不同结论。

小实验 / 反馈

做 Experiment 41：vendor capstone preflight。真机时再把对应厂商的 exact version / device / backend log 填进 Experiment Card。

Retrieval Practice

  1. 为什么 HIP 语法近似 CUDA 不等于底层执行细节完全相同？
  2. rocminfo/amd-smi 和实际 LLM backend log 各证明哪一层？
  3. 为什么 gfx target/ROCm version 必须进入 Evidence？
  4. 如果某 AMD 卡理论很强但 backend fallback，你会把问题归到硬件还是软件层？

完成证据

提交一张 AMD ROCm evidence ladder：device identity → driver/runtime → backend build → model identity → exact argv → PP/TG/quality；每一层写“由什么命令或文件证明”。

如何迁移

四生态真正应该共用的是 Evidence 结构，而不是命令。换厂商后保持问题不变：我跑了谁、在哪跑、用什么路径、测了什么、什么仍未知。
