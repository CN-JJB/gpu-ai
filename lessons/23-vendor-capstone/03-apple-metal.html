Vendor Capstone · Apple · L0→L2

Apple / Metal / MLX 实战闭环：从统一内存预算到真实 LLM GPU 路径

Apple Silicon 的 capstone 不需要先学会写 Metal shader。你要能证明：模型 fit 在统一内存内、目标 runtime 确实利用 GPU/Metal、memory pressure 可接受、PP/TG/质量可复现，并知道 ANE 是否真的参与而不是凭 TOPS 猜。

Prerequisite Check

完成 unified memory、Metal execution model、M-series/ANE/MLX 三节。你应能区分“容量”“带宽”“GPU”“ANE”“runtime”。

真实问题：为什么 Mac 上模型“一键能跑”仍不足以判断这台机器适不适合你？

因为良好的应用体验可能把很多细节隐藏起来。你仍需要知道：

  • 模型权重/量化是什么；
  • 统一内存还剩多少 headroom；
  • 是否发生明显 swap/memory pressure；
  • MLX/llama.cpp 等 runtime 使用什么 device/backend；
  • PP 与 TG 谁是瓶颈；
  • 长时间运行是否热降频；
  • 同样质量条件下性能如何。

1. Apple evidence chain

exact Mac / SoC / memory capacity
→ macOS + Metal capability
→ application/runtime build
→ GPU/Metal execution path
→ model/quant + context
→ memory pressure / swap
→ PP/TG + quality
→ energy/thermal if relevant

与独显不同，Apple 路径还必须把系统共享内存压力纳入同一个 session。

2. Fit：先做统一内存预算

记录：

weights
+ KV cache
+ runtime buffers
+ macOS + background apps
+ concurrency
+ safety margin

不要把 total unified memory 全部交给模型。一个“刚好加载”的配置在长上下文或同时开浏览器/IDE 时可能进入 memory pressure。

3. MLX / MLX-LM：怎样证明 GPU 在工作？

使用 runtime/device selection、日志、Activity Monitor/Metal profiler（高级路径）与性能变化共同确认。不要仅用“CPU 没满”或“GPU history 有波动”作为唯一证据。

MLX 使用 lazy computation 时，还要确保 benchmark 真正触发 materialization/synchronization，否则只测到 dispatch/graph 构建时间。

4. llama.cpp / Metal path：为什么要与 MLX 分开记录？

同一 Mac 上不同 runtime 可能使用不同模型格式、量化 kernel、buffer 组织和 sampling pipeline。比较时必须记录 runtime build 和 exact model artifact。

正确结论可以是：“在模型 A、量化 Q、context C、协议 P 下，runtime X 的 TG 比 Y 高。”不要泛化成“MLX 永远更快”或“llama.cpp 永远更省内存”。

5. ANE：什么时候可以写进证据？

只有目标 framework/runtime 明确把相关 graph/operator 调度到 ANE，并能通过 profiler/runtime evidence 观察时。否则 ANE 只属于芯片能力背景，不能加进本次 LLM benchmark 的解释。

Worked Example：同一 32 GB Mac，短上下文正常，长上下文突然很慢

check model/quant unchanged
→ inspect context / KV growth
→ inspect memory pressure
→ inspect swap
→ inspect runtime allocation/cache
→ compare TG before/after pressure
→ reduce context or concurrency one variable at a time

如果降低 context 后 swap 消失、TG/latency 恢复，容量压力是很强的解释候选；仍需记录系统状态，而不是说“Mac 用久了会变慢”。

6. Thermal / power：笔记本与桌面同 SoC 名称也可能不同

持续 LLM workload 可能让无风扇/轻薄设备与主动散热桌面/高端笔记本出现不同稳态。测试要区分 cold burst 与 sustained run。

如果你关心移动使用，还应记录 wall/battery energy，而不只 token/s。

7. Benchmark protocol

固定 model revision/artifact、quant、prompt/token identity、context、batch、runtime version、device selection、warmup/repetition。记录 unified-memory pressure 与 swap 状态。PP/TG 分开；跨 quant/runtime 比较加入固定质量任务。

Why it matters

  • Apple 的“好用”不能替代容量/性能证据，但确实减少某些部署摩擦。
  • 统一内存让 memory pressure 成为 benchmark 环境的一部分。
  • MLX 与 Metal 是不同层，比较 runtime 要固定模型和协议。
  • ANE 只有被目标应用使用时才属于性能解释。
  • 不可升级内存使购买前的 fit/headroom 规划尤其重要。

常见误区

  • “Activity Monitor GPU 有波动 = 全部模型在 GPU”——证据太弱。
  • “MLX lazy，所以第一次命令很快 = kernel 很快”——可能尚未同步执行。
  • “ANE TOPS 高 = LLM 自动上 ANE”——必须有 runtime path。
  • “总内存够 = 不会 swap”——系统/其他进程也使用内存。
  • “同芯片不同机型 sustained performance 一样”——散热/功耗可不同。

实践路径

作者阶段准备 model-fit worksheet、MLX/llama.cpp 固定协议和 evidence template。以后你上课时有 Mac 就依次跑：memory budget → tiny model → target model → context sweep → PP/TG → quality → sustained run。

无 Mac

L0：使用官方 Metal/MLX 文档完成 evidence-chain 和 memory-budget 练习。不要购买硬件只为过课。

排错树

model loads?
 no → fit / format / runtime
 yes → expected GPU path active?
        no → device/backend/config
        yes → memory pressure high?
              yes → context/concurrency/headroom
              no → PP vs TG / thermal / kernel / host

Retrieval Practice

  1. Apple benchmark 为什么要记录 memory pressure/swap？
  2. MLX lazy execution 会怎样污染错误的计时方法？
  3. 为什么 MLX 与 llama.cpp 比较必须记录 exact model/quant/runtime？
  4. 什么时候 ANE 可以写进 LLM 性能解释？
  5. 短上下文快、长上下文慢时为什么先检查 KV 与 memory pressure？
  6. 为什么 sustained run 对无风扇/轻薄设备特别重要？

Decision Rule

Apple 本地 LLM 结论必须绑定 exact SoC/memory + runtime + model/quant + context + memory-pressure state。总内存、GPU core、ANE TOPS 任一单项都不能成为购买分数。

Transfer

统一内存系统的“系统竞争 + workload memory budget”思维可迁移到 APU/共享 HBM 系统；lazy execution/异步计时问题也可迁移到 CUDA/HIP，需要显式同步才能得到可信时间。
