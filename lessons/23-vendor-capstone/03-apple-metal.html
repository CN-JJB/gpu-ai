Vendor Capstone 3 — Apple Metal / Unified Memory

1. Mac 的 baseline 先看内存模型

system_profiler SPHardwareDataType SPDisplaysDataType

再复用 Experiment 28 读取：

  • hasUnifiedMemory；
  • recommendedMaxWorkingSetSize；
  • currentAllocatedSize；
  • Metal execution width。

2. 当前 llama.cpp macOS 构建默认启用 Metal

cmake -B build
cmake --build build --config Release

仍要用：

./build/bin/llama-bench --list-devices

证明实际设备路径。

3. 不要写“64GB 显存”

installed unified memory
!= safe GPU working set
!= runtime footprint

4. Mac 的典型诊断

  • 能装大模型但 TG 不高 → capacity 与 bandwidth 是不同 roof。
  • PP 弱 → 看 Metal kernel/FA/tensor path。
  • 长 context 开始挤压系统 → KV/working-set pressure。

5. Neural Engine 边界

Metal GPU benchmark 不自动代表 ANE。M5 GPU Neural Accelerator 也必须有 runtime/kernel Evidence。

学生闭环 — Apple Metal

硬件门槛：L0 preflight；有对应硬件时 L1/L2 做真机增强。

成本：0 元主路径，不要求集齐四个生态。

风险：safe；只做 build/device/runtime 检查和 benchmark。

替代路径：没有 Apple Metal 硬件就只做 Experiment 41 的 preflight，并用已有 Evidence/官方资料完成生态映射。

能力目标

  • 把 hardware identity、driver/runtime、backend build、model artifact、execution config 分层记录。
  • 把同一 benchmark contract 迁移到 Apple Metal，只替换厂商特有的 discovery/build 命令。
  • 知道“能运行”与“使用预期加速路径”是两个不同结论。

小实验 / 反馈

做 Experiment 41：vendor capstone preflight。真机时再把对应厂商的 exact version / device / backend log 填进 Experiment Card。

Retrieval Practice

  1. 为什么 Unified Memory 让“CPU offload vs GPU VRAM”这套离散卡语言需要改写？
  2. Metal device 可见与 MLX/llama.cpp Metal backend 可用分别证明什么？
  3. 为什么 working-set headroom 要和模型文件大小分开？
  4. Apple GPU/ANE 都存在时，为什么不能把两者性能混成一个 AI TOPS？

完成证据

提交一张 Apple Metal evidence ladder：device identity → driver/runtime → backend build → model identity → exact argv → PP/TG/quality；每一层写“由什么命令或文件证明”。

如何迁移

四生态真正应该共用的是 Evidence 结构，而不是命令。换厂商后保持问题不变：我跑了谁、在哪跑、用什么路径、测了什么、什么仍未知。
