Vendor Capstone 1 — NVIDIA CUDA

目标不是“CUDA 最快”，而是把 NVIDIA 的成熟软件栈变成一份可审计 baseline。

1. 先证明是哪张卡

nvidia-smi -L
nvidia-smi --query-gpu=name,compute_cap,driver_version,memory.total,pci.bus_id --format=csv

旧卡尤其要同时检查当前 CUDA/driver 生命周期。能被驱动看到，不代表最新工具链仍支持。

2. 当前 llama.cpp CUDA 构建

cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release

然后：

./build/bin/llama-bench --version
./build/bin/llama-bench --list-devices
backend 证据来自实际 build/device log，不来自“我装了 CUDA”。

3. Baseline

进入 Experiment 40，固定 model SHA、PP/TG、offload、KV、FA、threads。

4. 看到什么再优化什么

  • TG 接近 bandwidth roof → 优先研究 weight bytes / quant / memory behavior。
  • PP 弱、TG 正常 → 看 FA / matrix kernel。
  • 显存边缘化 → 看 KV/context/quant。
  • 双卡缩放差 → 回 Slice 11 看 P2P/topology/split。

5. CUDA 成熟也不能跳过实验

同一 NVIDIA 卡在不同 llama.cpp commit、quant、FA、context 下仍可能完全不同。

学生闭环 — NVIDIA CUDA

硬件门槛：L0 preflight；有对应硬件时 L1/L2 做真机增强。

成本：0 元主路径，不要求集齐四个生态。

风险：safe；只做 build/device/runtime 检查和 benchmark。

替代路径：没有 NVIDIA CUDA 硬件就只做 Experiment 41 的 preflight，并用已有 Evidence/官方资料完成生态映射。

能力目标

  • 把 hardware identity、driver/runtime、backend build、model artifact、execution config 分层记录。
  • 把同一 benchmark contract 迁移到 NVIDIA CUDA，只替换厂商特有的 discovery/build 命令。
  • 知道“能运行”与“使用预期加速路径”是两个不同结论。

小实验 / 反馈

做 Experiment 41：vendor capstone preflight。真机时再把对应厂商的 exact version / device / backend log 填进 Experiment Card。

Retrieval Practice

  1. 为什么“装了 CUDA toolkit”不等于这次 llama.cpp run 使用 CUDA backend？
  2. nvidia-smi 能证明 GPU 身份，但不能证明哪一层 kernel 路径？
  3. PP 弱/TG 正常和 PP 正常/TG 弱分别更像哪类 bottleneck？
  4. 旧 NVIDIA 卡能被 driver 识别时，还要额外检查什么生命周期问题？

完成证据

提交一张 NVIDIA CUDA evidence ladder：device identity → driver/runtime → backend build → model identity → exact argv → PP/TG/quality；每一层写“由什么命令或文件证明”。

如何迁移

四生态真正应该共用的是 Evidence 结构，而不是命令。换厂商后保持问题不变：我跑了谁、在哪跑、用什么路径、测了什么、什么仍未知。
