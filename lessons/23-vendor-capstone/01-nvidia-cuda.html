Vendor Capstone · NVIDIA · L0→L2

NVIDIA / CUDA 实战闭环：从“系统看到显卡”到“LLM 证明确实在 GPU 上跑”

本页不是安装命令抄写。真正目标是让你能独立证明一条 NVIDIA 本地 LLM 路径：硬件身份正确、driver/runtime 正常、应用 backend 正确、模型真实 offload、性能与质量有可复现记录。

Prerequisite Check

完成 NVIDIA 架构主线，知道 SM/warp/Tensor Core 只是能力；知道 VRAM fit 与 backend support 要先于性能。

真实问题：为什么“nvidia-smi 能看到卡”仍然不足以证明 CUDA LLM 正常？

nvidia-smi 只能证明驱动栈能识别设备并暴露部分状态。应用还可能：

  • 根本没编 CUDA backend；
  • CUDA runtime/library version 不匹配；
  • 模型格式对应 kernel 不支持；
  • 只有部分 layers offload；
  • 因 OOM/配置 fallback 到 CPU；
  • GPU 在工作，但瓶颈在 CPU/tokenization/storage。

1. 先画完整证据链

PCIe/device identity
→ NVIDIA driver
→ CUDA runtime/libraries
→ application CUDA backend
→ model/quant kernel
→ GPU offload observed
→ controlled benchmark
→ quality check
→ evidence packet

任何一层失败，都不要跳到“这张卡性能不行”。

2. Hardware identity：先确认“这是哪张卡”

记录至少：GPU name、UUID/PCI bus、VRAM total、driver version。多 GPU 系统还要确认目标进程使用的是哪一个 device。

为什么 UUID/PCI bus 重要？因为“GPU 0”的编号可能随环境变化，而 UUID/bus 更适合把 benchmark 与物理设备绑定。

3. Driver 与 CUDA runtime：两个版本概念不要混

驱动提供设备支持，并声明可兼容的 CUDA runtime 范围；应用可能携带/链接自己的 CUDA runtime 与 libraries。看到版本号时要标注它来自：

  • kernel/driver；
  • CUDA toolkit/compiler；
  • application bundled runtime/library；
  • PyTorch/other framework build。

“系统装了 CUDA 12.x”不自动证明某应用按那个 toolkit 构建。

4. Application backend：怎样证明不是 CPU build？

优先找应用自己的启动日志/build flags/device list。证据应回答：

  1. CUDA backend 是否编译进二进制？
  2. 检测到哪个 GPU？
  3. 加载模型时多少 layer/tensor offload？
  4. 是否出现 unsupported kernel/fallback 警告？
  5. 实际 allocation 与 VRAM 使用是否与模型规模相符？

5. Model fit：别等 OOM 才做预算

VRAM need ≈
weights
+ KV cache(context × concurrency)
+ runtime / compute buffers
+ temporary workspace
+ safety margin

如果预算已经超过显存，不要靠“也许能塞进去”开始 benchmark。先降低 context/并发、换量化、部分 offload 或换硬件。

6. Tensor Core 是否使用：不要用 GPU utilization 猜

高 GPU utilization 只能说明设备忙，不告诉你使用的是 general CUDA、Tensor Core 还是 memory stalls。真正需要时通过 profiler/kernel 名、library dispatch 与受控 dtype/shape 对比建立证据。

对于普通学生，本 capstone 不要求证明每条 Tensor instruction；只要求你不要把“有 Tensor Core”写成未验证的应用性能解释。

Worked Example：模型能跑但只有 3 token/s，怎么查？

1. confirm exact model / quant / context
2. confirm GPU offload count
3. watch CPU + GPU + VRAM
4. inspect application logs for fallback
5. run fixed tiny benchmark (PP and TG separate)
6. check clocks / power / thermal
7. compare with same build + same protocol baseline
8. change ONE variable

如果 CPU 100%、GPU 低，先查 fallback/tokenization；如果 VRAM 满且发生 host offload，查 fit；如果 GPU 高但 clocks 低，查 thermal/power；如果 PP 快 TG 慢，考虑不同 bottleneck。

7. 安装课为什么不能写死一条命令？

OS、driver、CUDA、package manager、application release 会变。稳定教材应该规定验证点，而动态资源提供当前安装步骤。你以后学习时按目标软件官方文档安装，并把版本/来源写入 session record。

8. Benchmark protocol：至少分开 PP 与 TG

Prefill/prompt processing 与 token generation 的算术强度、并行度和 memory behavior 不同。一个“总 token/s”很容易隐藏真实瓶颈。

固定：

  • model artifact + SHA；
  • quant；
  • context / prompt token identity；
  • GPU layers / flash attention / KV types 等 execution settings；
  • runtime build；
  • repetitions/warmup；
  • thermal/power condition。

9. Quality gate：快了不能默认质量没变

更换 quant、KV type、kernel/backend 或 model artifact 后，性能比较最好配对质量检查。质量不需要万能评分，但至少要有固定 corpus/task、tokenizer identity 与可重复输出。

Why it matters

  • NVIDIA 生态成熟也不意味着配置错误不会 fallback。
  • 把 driver/runtime/application build 分层，能大幅减少“玄学安装”。
  • 真实 offload + fixed protocol 才让二手卡 benchmark 有意义。
  • PP/TG 分开能把 compute-heavy 与 bandwidth-heavy 阶段区分。
  • 质量 gate 防止用“更快但不同模型/量化”的数字欺骗自己。

常见误区

  • “nvidia-smi 有卡 = CUDA 程序一定用卡”——还缺应用 backend/offload。
  • “装了 CUDA toolkit = 所有应用都用这个版本”——很多 binary 自带依赖。
  • “GPU 99% = Tensor Core 99%”——utilization 口径不同。
  • “OOM 就把 swap 开大”——GPU VRAM 与 host swap 不是等价扩容。
  • “网上 benchmark = 我的卡应达到”——协议/模型/build/功耗可能不同。

Retrieval Practice

  1. 为什么 nvidia-smi 成功只证明证据链的一部分？
  2. driver、toolkit、application-bundled runtime 如何区分？
  3. 怎样从日志/VRAM/offload 信息证明模型主要在 GPU 上？
  4. PP 与 TG 为什么应分开？
  5. GPU 99% 为什么不能证明 Tensor Core 被使用？
  6. 如果更换 quant 让 TG 快 30%，为什么还要质量 gate？

Decision Rule

只有“exact device + runtime/build + explicit CUDA backend/offload + fixed benchmark + quality evidence”组成的链，才可用于性能与购买判断。单个截图、理论规格或他人 benchmark 都只是较弱证据。

Transfer

把这条 capstone 迁移到 AMD/Apple/Intel：设备身份、runtime、application backend、真实执行路径、benchmark、quality 这六层不变，只换具体工具。

完成证据

完成本课后，保留一份 learner-owned completion artifact，至少包含：

  • 用自己的话画出或写出本节最小 mental model，并标出关键变量/资源层；
  • 完成本节小实验、worksheet 或无硬件 fallback；有真机时链接 raw Evidence，没有真机时明确标 L0 / DOCUMENTED / DEFERRED-HARDWARE；
  • 写一条绑定 Evidence 的 PASS / FAIL / UNKNOWN / BLOCKED 结论，说明它怎样影响本地 LLM 的容量、性能、兼容、成本或风险判断；
  • 写一句明确 non-claim：这份证据还不能证明什么。

只写“看完了”或抄规格表不算完成。课程要的是可复查的推理产物，而不是阅读打卡。
