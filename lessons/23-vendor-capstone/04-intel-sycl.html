Vendor Capstone 4 — Intel SYCL / Level Zero / XPU

1. 先证明 oneAPI 看到了 GPU

source /opt/intel/oneapi/setvars.sh
sycl-ls

目标 Intel GPU 通常应以 Level Zero GPU 设备出现。

2. 当前 llama.cpp SYCL 构建

cmake -B build \
  -DGGML_SYCL=ON \
  -DCMAKE_C_COMPILER=icx \
  -DCMAKE_CXX_COMPILER=icpx \
  -DGGML_SYCL_F16=ON

cmake --build build --config Release -j

当前 upstream 还提供：

./examples/sycl/build.sh

3. llama.cpp 自己也要看到设备

./build/bin/llama-ls-sycl-device
./build/bin/llama-bench --list-devices

4. dGPU / iGPU 不同

Arc dGPU → dedicated GDDR
Intel iGPU → shared system memory

不能把两者的“global memory”数字当同一种 VRAM。

5. 第一轮优化

  • PP 弱 → FA / oneDNN/backend path；
  • TG 弱 → quant/reorder/memory behavior；
  • FP16 vs FP32 build → 可以作为单变量 runtime-build A/B；
  • iGPU/dGPU 同时出现 → 先固定 device selection。
XMX 是硬件能力，不是“任何 Q4 都自动加速”的证据。

学生闭环 — Intel SYCL/XPU

硬件门槛：L0 preflight；有对应硬件时 L1/L2 做真机增强。

成本：0 元主路径，不要求集齐四个生态。

风险：safe；只做 build/device/runtime 检查和 benchmark。

替代路径：没有 Intel SYCL/XPU 硬件就只做 Experiment 41 的 preflight，并用已有 Evidence/官方资料完成生态映射。

能力目标

  • 把 hardware identity、driver/runtime、backend build、model artifact、execution config 分层记录。
  • 把同一 benchmark contract 迁移到 Intel SYCL/XPU，只替换厂商特有的 discovery/build 命令。
  • 知道“能运行”与“使用预期加速路径”是两个不同结论。

小实验 / 反馈

做 Experiment 41：vendor capstone preflight。真机时再把对应厂商的 exact version / device / backend log 填进 Experiment Card。

Retrieval Practice

  1. 为什么 Level Zero/SYCL device 可见不等于 llama.cpp 当前走高效 XMX path？
  2. oneAPI、PyTorch XPU、llama.cpp SYCL 之间是什么关系？
  3. 如果同一模型在 CPU fallback 也能跑，如何证明 benchmark 真在 Intel GPU？
  4. Intel 生态变化快时，哪些信息应该放 Intelligence 而不是稳定 Lesson？

完成证据

提交一张 Intel SYCL/XPU evidence ladder：device identity → driver/runtime → backend build → model identity → exact argv → PP/TG/quality；每一层写“由什么命令或文件证明”。

如何迁移

四生态真正应该共用的是 Evidence 结构，而不是命令。换厂商后保持问题不变：我跑了谁、在哪跑、用什么路径、测了什么、什么仍未知。
