Host Memory Pressure — 32GB RAM 只剩 2GB free，要慌吗？

1. 先别只看 Free

Linux：

MemFree

只是当前完全没被用的物理页。

更有意义的是：

MemAvailable

它估计“不发生 swap 的情况下，还能给新应用多少”。

低 MemFree 本身不是 OOM 证据。

2. 为什么 Free 会故意很低？

因为 RAM 空着没价值。

OS 会把读过的模型/文件留在：

page cache

下次可以少等 SSD。

3. File cache 和 anonymous memory 不一样

干净 file-backed cache：

需要时可以 reclaim
以后再从文件读回来

Anonymous：

heap
runtime buffers
stack

不能简单丢掉重读。

4. 一个 toy

RAM 32 GiB
anon 10
file cache 18
kernel/other 2

free = 2 GiB

如果教学假设：

cache 的 80% 可 reclaim

那么：

available_proxy
= 2 + 18×0.8
= 16.4 GiB

所以新申请 8 GiB 在这个 toy 里还能靠 reclaim 顶住。

5. 另一个 toy

RAM 32
anon 25
cache 3
other 2
free 2

同样假设 80% cache 可 reclaim：

available_proxy
= 4.4 GiB

要再申请 8 GiB：

shortfall = 3.6 GiB

这明显更危险。

6. 注意：这不是 Linux MemAvailable 公式

课程 toy 只是帮助理解：

free
+
部分可回收 cache

这个方向。

真正：

/proc/meminfo MemAvailable

让内核自己估。

7. SwapUsed 不为 0，也不能直接喊 thrashing

曾经被 swap 出去的页可以继续留在 swap。

当前有没有激烈交换，看窗口内：

Δpswpin
Δpswpout

8. Major fault

如果：

Δpgmajfault ↑
MemAvailable ↓
TTFT ↑

paging/refault pressure 是一个合理 hypothesis。

9. mmap 模型也可能被 reclaim

File-backed clean pages：

RAM pressure
→ reclaim
→ 以后访问
→ page fault
→ 再读

所以：

mmap 成功
!=
20GB 模型永远 resident

10. mlock 呢？

它想让页别被 swap/reclaim。

但代价：

这些 RAM 更不能给别人用

可能把压力转移到整个系统。

11. Host OOM 和 GPU OOM 分开

离散 NVIDIA/AMD：

host RAM
!=
GPU VRAM

你可以：

MemAvailable 20GB
但 CUDA allocation OOM

因为 VRAM 满了。

也可以反过来。

12. Apple 是特殊情况

Apple silicon 是 unified memory。

不能硬画成：

32GB system RAM
+
独立 16GB VRAM

CPU/GPU 共享统一内存架构，OS memory pressure/compression 更重要。

13. 一个更像 host pressure 的时间线

MemAvailable ↓
pswpout delta ↑
major faults ↑
server latency ↑

再结合 process VmSwap/RSS 和 logs。

14. 一个可能健康的时间线

MemFree 低
MemAvailable 稳
Cached 高
pswpout delta 0
latency 稳

这很可能只是 OS 在有效利用 RAM。

15. 实验不故意把机器撑爆

真实 lab 只读：

/proc/meminfo
/proc/vmstat
/proc/PID/status
GPU telemetry

不默认分配几十 GB 去诱发 OOM。

教材补全：Linux “free RAM 很少”不一定是坏事

Available 比 Free 更有意义

现代 OS 会尽量把空闲内存用于 page cache。于是：

free small
cached large
available still healthy

这不等于“内存马上用完”。真正重要的是系统还能否在不进入严重 reclaim/swap 的情况下满足新分配。

模型服务的主机 RAM 去哪里了？

runtime/process heap
model mappings/page cache
CPU-offloaded tensors
tokenizer / metadata
KV or buffers (backend dependent)
OS + other processes

所以 VRAM 足够也不代表 host RAM 可以忽略。

Worked Example：为什么 swap 让系统“没 OOM 但像死了”

假设工作集超过 RAM 后，大量活跃页面进入 swap：

page needed
→ disk read
→ CPU waits
→ request stalls
→ more reclaim

进程可能仍活着，却出现几十秒 TTFT 或 load stall。对交互服务，这和功能失败差别不大。

OOM 要分层

  • GPU OOM：device allocation 失败。
  • host allocation failure：进程内存不足。
  • OS OOM killer：系统选择杀掉进程。
  • container/cgroup limit：还没耗尽整机 RAM 就被限制杀死。

排错顺序

  1. 确认是 GPU OOM 还是 host/cgroup OOM。
  2. 看 available、swap in/out、major faults，而不只看 free。
  3. 检查是否发生 CPU offload 或模型 page cache 膨胀。
  4. 检查其他进程和容器限制。
  5. 再决定加 RAM、减 offload、减并发或换模型。

Decision Rule

主机内存的目标不是“永远没有 cache”，而是让真实 workload 的 working set 在可接受的 reclaim/swap 行为下稳定运行。
