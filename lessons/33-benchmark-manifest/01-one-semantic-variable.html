Benchmark Manifest — 给每个跑分一张身份证

1. “30 tok/s”几乎什么都没告诉你

至少还缺：

哪张 GPU？
哪个 runtime commit？
哪份 GGUF？
什么 quant？
多少 PP/TG？
什么 context？
哪个 prompt token 序列？
什么 sampler？
质量有没有退化？

所以我们把这些合成一个 machine-readable manifest。

2. Manifest 分三层

fixed
variant
audit

fixed：这轮 A/B 绝对不能偷偷变的实验协议。

variant：真正允许被比较的语义块。

audit：命令、raw 文件路径、时间戳等审计记录。

3. 为什么不能简单规定 model SHA 一样？

如果实验是：

Q8_0
→
Q4_K_M

GGUF 本来就不同：

SHA different
bytes different
quant different

但这三项其实是一个语义干预：

variant.model
“一次只改一个变量”应该理解为一个实验语义变量，而不是永远只能改 JSON 的一个叶子。

4. FlashAttention 又可以更严格

intentional_variable
=
variant.execution.flash_attention

这时 validator 只允许这个 leaf 改。

5. Quant A/B

intentional_variable
=
variant.model

允许：

artifact_sha256
artifact_bytes
quant

一起改变。

但如果 Prompt token hash 也变：

FAIL

6. 为什么 Prompt 必须进身份证？

Slice 31 已经证明：

same visible text
!=
same token IDs

所以真正冻结：

token_ids_sha256
token_count

最好再保存 messages/template/rendered hashes。

7. Quality corpus 也必须冻结

如果 candidate 偷换成更简单的 corpus：

candidate PPL 看起来更好

这种质量 A/B 完全无效。

所以：

fixed.quality_eval

不允许随 candidate 改。

8. Hardware A/B 怎么办？

intentional_variable
=
variant.hardware

理想情况下其余全部相同。

但跨 NVIDIA / AMD 时 backend 也必须变怎么办？

那就诚实叫：

system comparison

不要硬冒充 one-variable causal A/B。

9. Validator 能证明什么？

它能证明 manifest 层面：

只有声明的语义变量变了

它不能证明：

温度一样
后台进程一样
数据没造假
benchmark 没 bug

所以它是实验纪律工具，不是真相机器。

10. Evidence Packet

最后把：

manifest
profile
prompt manifest
raw PP/TG
telemetry
quality log
comparison

全部做 SHA256 索引。

以后哪怕半年后，你还能知道这组结论到底来自哪批原始文件。

学生闭环 — Benchmark / Workload Manifest

硬件门槛：L0 主路径；真实模型/硬件只用于增强。

成本：0 元。

风险：safe。

能力目标

  • 把“模型/输入/质量/benchmark 身份”变成可审计对象。
  • 能指出公式或配置的适用边界，不把近似写成事实。
  • 为后续硬件选择提供可重复的 workload contract。

小实验 / 反馈

做 Experiment 60：manifest validator；真实硬件时做 Experiment 61：real Evidence Packet。

Retrieval Practice

  1. 什么叫 semantic variable，而不是“命令行恰好只改一个 token”？
  2. 为什么 model SHA、runtime build、prompt token identity 都应该进入 manifest？
  3. A/B 两边同时换 model 和 backend 时还能归因给谁？
  4. PACKET 的 hash 能证明文件没变，但不能证明哪些事情？

完成证据

写一对 baseline/candidate manifest，明确 comparison_id、intentional_variable、fixed fields、raw evidence paths；让 validator 能指出任何意外多变量变化。

如何选择 / 迁移

遇到新模型或新 backend 时，优先冻结 身份 + 输入 + protocol，再谈性能或质量；不可比的数据宁可 BLOCKED，也不要硬排排行榜。
