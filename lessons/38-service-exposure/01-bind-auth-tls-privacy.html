Service Exposure / Privacy — 把 127.0.0.1 改成 0.0.0.0，发生了什么？

1. 这不是一个“小网络参数”

默认 loopback：

127.0.0.1:8080

通常只有本机能直接访问。

改成：

0.0.0.0:8080

服务开始监听所有 IPv4 interfaces。

你改变的是信任边界。

2. 但 0.0.0.0 也不等于“公网已开放”

还取决于：

firewall
router/NAT
VPN
cloud security group
host network

所以要看实际 socket + 网络路径，不能靠猜。

3. LAN 也不是认证

你的 LAN 可能有：

guest
IoT
roommate
compromised PC

而 LLM prompt 里可能有：

代码
私人文档
API keys
RAG 内容

4. Auth 和 TLS 分开

API key：

谁可以用

TLS：

路上别人能不能看明文

两个不是替代关系。

5. CORS 更不是 Auth

CORS 是浏览器规则。

curl、原生客户端不靠 CORS 做访问控制。

CORS
!= firewall
!= authentication

6. 当前 llama-server 默认值得记住什么？

host = 127.0.0.1
api key = none
metrics = off
slots endpoint = on

这套默认假设更接近：

personal local process

如果你把 host 扩到 LAN，就必须重新审视 auth/TLS/endpoints。

7. Metrics 也属于信息面

它可能不含 prompt 正文，但会暴露：

请求活动
token 数
吞吐
slot 压力

管理员需要，不代表普通客户端也需要。

8. slots/cache endpoint 更应该审计

普通聊天客户端只需要 chat/completion。

为什么它还应该能看到内部 slot 状态？

原则：

least exposure

9. Tools / Agent 是另一个风险等级

纯生成：

prompt
→ text

如果启用了：

read_file
write_file
shell execution
MCP
agent

模型可能影响真实主机资源。

“聊天 API 可以放 LAN”绝不能自动推出“shell/tool-enabled agent 也可以放 LAN”。

10. 日志也是隐私系统

检查：

prompt 是否落盘
response 是否落盘
保存多久
谁能读
有没有上传 telemetry

11. Evidence 不能把秘密也一起打包

不要把：

Authorization: Bearer sk-...
--api-key SECRET
cookie
私人 prompt

原样塞进 GitHub。

应该记录：

auth configured = yes
secret source = env/file

而不是 secret 本身。

12. Model license 和 llama.cpp license 也不同

你可以合法使用某个 runtime，不能因此自动推出：

模型 weights 可以随便重新发布

分享 Docker image / course bundle 前，要看 exact model license。

13. 这一章真正要你会做的

listen socket
→ network scope
→ auth
→ TLS path
→ endpoint exposure
→ logs/privacy
→ tools/actions
→ model license

然后给出：

LOCAL-ONLY
LAN-ACCEPTABLE-WITH-CONTROLS
REVIEW

而不是直接复制一段“公网部署命令”。

学生闭环 — Service Exposure / Privacy / Auth

硬件门槛：L0 模拟主路径；真实 server 增强 L1。

成本：0 元。

风险：默认 safe；涉及网络暴露时只在受控本地环境完成，先审计再开放。

能力目标

  • 从“单机 benchmark”升级到“用户看到的服务行为”。
  • 用 tail/SLO/capacity/fairness/exposure 约束系统，而不是只追总 tok/s。
  • 能通过 trace/metrics 解释一个服务为什么好用或不好用。

小实验 / 反馈

做 Experiment 70：service-exposure config linter；真实服务做 Experiment 71：real exposure audit。

教材补全：暴露服务时，先画 Trust Boundary

从“谁能连”开始，而不是从参数开始

same process
↓
same host
↓
trusted LAN
↓
VPN / overlay network
↓
public Internet

每向外跨一层，攻击面、身份校验、传输保护、日志与秘密管理要求都会上升。

Worked Example：家庭局域网并不等于“只有我”

假设你把聊天服务从 loopback 改为 LAN 可见。此时能接触它的可能不只是你的电脑，还包括手机、电视、IoT、访客设备，以及任何已经被攻陷的内网主机。

如果 API 没有认证，而模型又能读取私人 RAG 文档，那么“只是家里用”已经不足以构成安全边界。

四个不同控制面

控制解决什么不能替代什么
bind/firewall谁能建立网络连接身份认证
authentication你是谁链路加密
TLS传输机密性/完整性授权策略
authorization你能调用什么日志/隐私治理

Secrets 的正确证据方式

BAD:
--api-key my-real-secret

GOOD evidence:
auth_enabled = true
secret_source = environment
secret_value = REDACTED

课程证据包永远不需要你的真实 API key、cookie、token 或私人 prompt。

工具调用会把风险等级再抬高

纯文本生成的最坏结果通常是输出错误文本；如果模型被允许写文件、执行 shell 或操作外部系统，后果边界完全不同。此时要把工具权限、可访问目录、凭证和网络出口单独建模。

最小暴露检查单

  1. 确认实际监听地址与端口。
  2. 确认主机防火墙/路由实际允许的来源。
  3. 需要跨不可信网络时使用认证与加密。
  4. 关闭不需要的管理、metrics、slot/debug endpoints。
  5. 日志不保存不必要的 prompt/secret。
  6. 工具/agent 权限与普通 chat API 分离。

Decision Rule

只有在“连接来源、身份、传输、授权、日志、工具权限”都说得清楚时，才把本地模型服务从 loopback 扩出去。
