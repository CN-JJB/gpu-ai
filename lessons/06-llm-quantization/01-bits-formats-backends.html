LLM Quantization · Lesson 06 · L0

“4-bit 模型”到底是什么意思？

你会同时看到 FP16、AWQ、GPTQ、GGUF、Q4、EXL2、bitsandbytes。最危险的学法，是把它们全记成“压模型的格式”。它们其实分属不同层。

Prerequisite Check

你应能用 Lesson 05 做最基本的 weights + KV + buffer 内存预算，并知道 8 bit = 1 byte。建议同时完成 Foundation 02，理解 artifact bytes 与 SHA256；这样你不会把“Q4”文件名当作足够的模型身份。

真实问题

两个都写“4-bit”的模型，一个是 GGUF Q4，一个写 AWQ。为什么一个 llama.cpp 能跑，另一个要别的 backend？它们不是都 4-bit 吗？

先建立四层模型

数值表示→ 量化方法→ 序列化/容器→ backend + kernel

1. Datatype：数到底用什么精度表示？

FP32、FP16、BF16、FP8、INT8、低-bit packed weights 都在回答这一层。

W4A16 通常表示 4-bit weights + 16-bit activations。

它不意味着 accumulator、softmax、normalization 或所有 tensors 都在 4 bit 运算。

2. Quantization method：怎么把高精度权重变成低 bit？

GPTQ

post-training weight quantization 方法，核心是怎样控制低-bit 权重误差。

AWQ

利用 activation statistics 识别重要 weight channels，再设计 weight-only quantization。

GPTQ/AWQ 首先是“怎么量化”的方法，不是某种万能文件后缀。

3. Container：文件这只箱子怎么装 tensor？

Safetensors

它记录 tensor 名、dtype、shape、data offsets 等。Safetensors ≠ FP16，也 ≠ AWQ/GPTQ。

GGUF

llama.cpp 的 GGUF 实现包含 metadata、tensor name/dimensions、每个 tensor 的 ggml type 与 data blob。

GGUF 是箱子，不是“4-bit”的同义词。

一个 GGUF 可以装 F16，也可以装不同 quant types。

4. EXL2 为什么不好硬塞进一个格子？

ExLlamaV2 的 EXL2 是与该推理生态紧密结合的 quantized representation，还能在一个模型中混合不同 bit-width，去满足 target average bitrate。

现实项目名词会跨层。四层模型的价值是让你继续追问，而不是强迫所有名字只属于一个盒子。

5. 为什么“4-bit”不等于 4.000 bpw？

想一个最简单的 group quantization：

  • 每个 weight code：4 bit
  • 每 G 个 weights 共用一个 FP16 scale：16 bit

每个 weight 平均还要分摊 16 / G bits metadata。

7. Backend：文件能读不代表 GPU 有高效 kernel

parser+ model support+ quant op+ hardware kernel

所以四个判断完全不同：能下载、能加载、能正确生成、能高效生成。

8. 现实反例：兼容性不能脱离 backend

当前 Hugging Face Transformers 和 vLLM 都维护自己的 quantization compatibility 信息，它们对某些 method/hardware 的支持范围并不相同；vLLM 还明确提醒兼容矩阵会变化。

“AWQ 支持 AMD 吗？”不是完整问题。

完整问题是：哪个 backend、哪个版本、哪种 representation、哪代 AMD GPU？

易变支持快照放到 intelligence/，不写进稳定 Lesson。

9. GGUF 也不能脱离 runtime 讲性能

llama.cpp 把 GGUF 当原生模型 format，并有 CUDA/HIP/Metal 等后端。vLLM current docs 也有 GGUF path，但标记 experimental / under-optimized，并迁移到 plugin。

同一 GGUF artifact，在不同 runtime 上的 maturity、features、performance 可以不同。

10. Apple 是最好的迁移练习

llama.cpp upstream 把 Metal / Apple Silicon 列为 backend。这不是因为“GGUF 是 Apple 格式”，而是：

GGUF loader+ ggml quant types+ Metal backend→ Apple GPU

NVIDIA/AMD 也要经过各自 CUDA/HIP kernel path。

11. 选量化模型的正确顺序

  1. 先选 backend。
  2. 再看 hardware。
  3. 查 current compatibility。
  4. 算 capacity。
  5. 设质量底线。
  6. 看 decode/prefill/context/concurrency workload。
  7. 再 benchmark。

教材补全：量化不是“把 16 bit 直接除成 4 bit”

先区分三件事

numeric precision
quantization scheme
file/runtime format

例如“4-bit”只说明了很粗的位宽层级；不同 group size、scale/zero-point、mixed precision、校准方法和 kernel 支持会让质量、速度、占用完全不同。

Worked Example：为什么更小 quant 不一定更快

假设 Q4 权重更小，但 backend 对某种 Q4 kernel 支持较差，需要额外 dequant/packing 开销；另一个 Q5 格式虽然更大，却有更成熟的 kernel。结果可能出现：

Q4: smaller file, slower TG
Q5: larger file, faster TG

所以“位数更低 = 一定更快”是错误规则。

质量与性能要分开测

  • 容量：模型能否 fit，留多少 KV/headroom。
  • 性能：PP/TG/TTFT。
  • 质量：固定 corpus / task 的 PPL 或任务结果。

量化选择必须同时看三条轴。

实验预期

  • 更低位宽通常显著减少权重占用。
  • 质量损失通常不是线性的，也不是所有层/模型一致。
  • 不同 backend/硬件对同一格式的速度支持可能差很大。

排错

  1. 确认 exact quant 名称和模型 artifact SHA。
  2. 确认 runtime/backend 是否真的使用对应 kernel，而非 fallback。
  3. 固定 prompt/context/threads/GPU offload 等条件。
  4. 性能和质量分开记录，不能用“看起来回答还行”代替质量 gate。

无目标硬件怎么办？

可以先比较文件体积、格式元数据和公开 backend 支持，形成 hypothesis；只有真实 runtime benchmark 才能升级成性能结论。

Decision Rule

量化选择 = 容量 × 质量 × backend 实现。只根据“Q4/Q5/Q8”标签做硬件或模型决策，证据不足。
