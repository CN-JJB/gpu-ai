整机 System Integration — 为什么“综合 90 分”仍然可能不能买？

Prerequisite Check

开始前，你应该已经会把单项证据分成 hard gate、可优化的 soft tradeoff 和尚未闭合的 unknown，并理解兼容性、显存/内存容量、PSU/连接器、物理空间、软件支持、持续稳定性与预算都可能成为整机级约束。

如果还不熟：先不要做“总分”。把每个条件写成 PASS / FAIL / UNKNOWN / BLOCKED；任何不可接受的 hard-gate FAIL 都不能被其他项目的高分抵消，关键 unknown 也不能自动按 PASS 处理。

真实问题

你有一张看起来性价比极高的 GPU：显存大、价格低、benchmark 也不错，于是整套方案“综合评分 90 分”。但主板链路、机箱空间、PSU 连接器、runtime 支持或目标模型质量路径里只要有一个硬门槛没过，整机仍然可能不可用。

真正的问题是：在花钱之前，怎样把 GPU、主机、软件、模型、workload、SLO、功耗与风险证据合成一个可审计 dossier，并明确哪些 unknown 必须先关闭？整机设计不是把优点相加，而是先证明所有硬门槛同时成立。

学生闭环 — Whole-Machine System Integration

硬件门槛：L0 模型/设计主路径；真机实验按页面对应 L1–L3。

成本：0 元教学主路径；不要求购买、拆修或高风险改造。

风险：默认 safe；涉及 PSU/硬件时只做只读调查与厂商手册约束下的正常安装，不做带电拆装。

能力目标

  • 把“GPU 很强”升级成整机层的容量、稳定、供电、散热和长期运行判断。
  • 把 PASS / FAIL / UNKNOWN 与具体 Evidence 对齐。
  • 知道什么情况下应该 BLOCKED 或 REVISE，而不是为了完成课程强行 ACCEPT。

小实验 / 反馈

做 Experiment 90：whole-machine feasibility model；真实目标做 Experiment 91：real machine dossier。

Retrieval Practice

  1. 为什么任何一个 hard gate FAIL 都不能被其他优点“平均掉”？
  2. critical UNKNOWN 为什么应该 BLOCKED，而不是乐观当 PASS？
  3. 一台机器模型能装下，但 PSU/散热/软件 support 未证明，你能 ACCEPT 吗？
  4. whole-machine dossier 与零件清单的根本区别是什么？

完成证据

完成一张 machine hard-gate matrix：模型容量、runtime support、性能/质量、host RAM/storage、PCIe、PSU、thermal、网络/服务、成本/风险；每项 PASS/FAIL/UNKNOWN 并链接 Evidence。

如何选择 / 迁移

换 GPU、模型或平台后，从 hard gates 重新算，不继承旧机器的 PASS；任何新未知都回到 evidence collection，而不是靠经验口头补齐。

先做 Gate，再做 Preference

Step 1: define workload
Step 2: enumerate hard gates
Step 3: resolve critical unknowns

Unknown Debt

设计越靠近购买/部署，关键 UNKNOWN 的成本越高。一个成熟 dossier 应该显示：

unknown
→ why it matters
→ cheapest evidence to resolve it
→ owner / next action

依赖关系要显式写

某些 gate 会串联：

model/context
→ VRAM/KV
→ concurrency
→ serving SLO
→ power/thermal
→ PSU/cooling

改模型量化，可能同时改变显存、质量、速度、能耗；所以 revision 之后必须重新跑受影响的 gate。

Troubleshooting：Dossier 被 BLOCKED 时怎么找最短闭环？

  1. 先找 hard-gate blocker：不要先优化价格或跑分。列出所有 FAIL / UNKNOWN / BLOCKED，标出哪些会直接让整机不可用。
  2. 按依赖关系排序：优先关闭会同时影响多个后续判断的 unknown，例如 exact GPU identity、runtime support、PSU connector path、模型实际容量。
  3. 给每个 unknown 指定最小下一证据：文档可回答的就不要求买硬件；必须实测的则标记 DEFERRED-HARDWARE，而不是编一个结果。
  4. 一次只改变一个设计变量：换模型量化、换 GPU、加 RAM、换 PSU 都可能触发多个 Gate 重算；记录变更前后依赖，避免“综合评分”掩盖因果。
  5. 遇到冲突证据：保留冲突，不强行平均。提高证据等级、检查版本/型号/时间边界，直到可以解释为什么两份证据不同。
  6. 关键 unknown 仍未关闭：最终状态保持 BLOCKED / REVIEW。课程允许“现在还不能决定”作为成熟结论。

故障恢复的目标不是让 Dossier 看起来完整，而是用最少的新假设把最高风险的不确定性逐个关闭。

Decision Rule

FAIL 不能被平均；关键 UNKNOWN 不能被乐观填空；只有 all-required PASS 的候选才进入“哪个更值”的讨论。

Machine Dossier 的最终交付格式

每个 required gate 用同一结构：

gate:
requirement:
status: PASS / FAIL / UNKNOWN
evidence:
assumptions:
what would invalidate this PASS:
next action if UNKNOWN:

特别要写“什么会让 PASS 失效”。例如换 quant、context、runtime、第二张 GPU 或机箱，都可能让旧的容量/供电/热/软件结论需要重算。

Worked Example：只换模型量化，为什么可能触发五个 Gate 重跑？

quant changes
→ artifact bytes / fit
→ kernel support
→ PP/TG
→ quality
→ power/thermal/runtime buffers

所以 revision management 不是“只把 VRAM 那一格改掉”。Dossier 应显式记录依赖关系，并对受影响 gate 重新验证。

Unknown Closure Strategy

对每个 critical UNKNOWN，找最便宜、最安全、最能区分结果的下一步：

  • 能查 exact 官方文档就先不买硬件；
  • 能用 fixture/preflight 验 backend 就先不跑长 benchmark；
  • 能让卖家提供 identity evidence 就先不付款；
  • 只有必须真机测的项才留 DEFERRED-HARDWARE。

成熟工程不是“把所有测试都做一遍”，而是用最小 Evidence 逐个关闭最贵的未知。

Final States

FAIL on required gate
→ REVISE DESIGN

critical UNKNOWN
→ BLOCKED / DO NOT BUY YET

all required gates PASS
→ EVIDENCE-SUFFICIENT-FOR-HUMAN-REVIEW

即使全部 PASS，也不自动发出购买动作；市场价格、资金、退货条件与个人偏好仍属于最后的人类决策。

What this lesson does NOT prove

Dossier PASS 只对写明的 workload、时间点、硬件/软件 identity 与环境成立。它不是“一次认证永久有效”。任何关键依赖变化，都应触发对应 gate 的 revision。
