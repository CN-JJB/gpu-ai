Modern KV · L0→L1

现代 KV 设计：Sliding Window、Hybrid Attention、Latent Cache 为什么让旧公式失效？

“KV cache = 2×层数×context×KV heads×head dim×bytes”是非常好的起点，但不是所有现代模型的终点。有些层只看局部窗口，有些全局/局部交替，有些不直接保存传统完整 K/V。面对新架构，最重要的技能是识别历史状态到底保存什么、保存多久、每 token 读多少。

Prerequisite Check

你应会 MHA/MQA/GQA 的传统 KV 公式，并知道长 context 会增加容量和 decode memory traffic。

真实问题：为什么某模型标称 128k context，却没有按“所有层全 128k KV”占掉预想那么多显存？

可能因为它使用 sliding-window、hybrid/global-local attention、压缩/latent state 或其他稀疏历史机制。此时传统 dense full-attention KV 公式会高估或错误描述实际状态。

1. Sliding Window Attention：只保留/只关注最近 W 个 token

最直观形式：

full attention at token N:
attend 1 ... N

sliding window W:
attend max(1, N-W+1) ... N

当 N 远大于 W，单层需要参与 attention 的历史长度不再随总 context 无限增长，而接近固定窗口。

容量一定固定吗？

取决于 runtime 是否真的丢弃窗口外 KV，还是为了别的用途仍保留。模型架构的“attention receptive field”与 runtime 的“KV allocation policy”要分开验证。

2. Hybrid Attention：不是所有层都采用同一历史范围

某些模型让部分层做 local/sliding attention，间隔若干层做 global/full attention：

Layer 1 local W
Layer 2 local W
Layer 3 global N
Layer 4 local W
...

此时总 KV/compute 成本要按 layer type 分组，不能用单一窗口或单一 full-context 公式覆盖全部。

Worked Example：32 层，其中 24 层 window=4k，8 层 full context=32k

忽略其他差异，只看“token-history length factor”：

traditional all-full factor = 32 layers × 32k
hybrid factor = 24×4k + 8×32k

两者显著不同。这个例子只展示比例；真实 KV 还要乘 KV heads/head dim/dtype，并确认 runtime allocation。

3. Latent / Compressed KV：历史状态不一定直接保存完整 K/V

一些现代 attention 设计尝试把历史信息存成更小的 latent representation，decode 时从 latent state 重构/使用需要的 attention 信息。

这种设计的核心 tradeoff：

store less historical state
→ lower memory capacity/traffic
but
→ extra projection/reconstruction compute
→ specialized kernels/runtime support needed

所以“KV 省很多”可能把瓶颈从 memory 往 compute/kernel 移动。

4. 为什么新 attention 架构特别容易出现 backend lag？

传统 MHA/GQA kernel 已非常成熟；新结构可能需要新的 cache layout、fused kernel、quantization path。模型发布当天能被某框架“加载”，不代表所有 backend 已高效实现。

Model Dossier 要新增：

  • attention type / layer pattern；
  • cache state type；
  • window/global schedule；
  • runtime implementation status；
  • quality/context validation。

5. KV Quantization 与“架构级压缩”不同

KV quant 是把保存的 K/V 用更低精度存储；sliding/latent 则改变保存历史的结构或长度。两者可以叠加，但属于不同语义变量。

KV quant: same conceptual state, fewer bits
Sliding:  fewer historical positions
Latent:   different compressed state representation

6. Paged KV 也不是 attention architecture

Paged KV 主要解决 runtime 内存管理与碎片/动态分配：把 KV 分成 pages/blocks，便于多个序列增长与回收。它通常不改变模型“应该 attention 哪些 token”的数学语义。

因此要区分：

  • 模型层：MHA/GQA/sliding/latent；
  • 存储精度层：FP16/Q8/Q4 KV；
  • runtime allocation 层：paged/block KV。

7. Long context 的质量问题仍然存在

省内存不代表模型真的能利用超长历史。Sliding window 可能天然看不到窗口外细节；hybrid/global layers 提供更远信息通路；latent 设计有自己的训练语义。必须用与架构匹配的 long-context fixture 验证质量。

Why it matters

  • 避免用传统 full-KV 公式错误估算新模型。
  • 帮助理解“128k context”背后的实际 memory/attention pattern。
  • 区分模型架构优化、KV dtype 优化、runtime paging 三层。
  • 提醒新模型可能因 backend kernel 未成熟而无法兑现架构优势。

常见误区

  • “Sliding window 4k = 模型只能处理 4k 总 context”——可能有 global/hybrid 通路。
  • “有 sliding 就一定只分配 4k KV”——runtime policy 需验证。
  • “latent cache 就是 KV Q4”——结构压缩与低位存储不同。
  • “paged KV 减少模型理论 KV 大小”——主要解决分配/碎片管理。
  • “长 context 能 fit = 能正确利用远距离信息”——必须 quality test。

小实验

为三个 toy architecture 分别写 KV budget：全局 GQA、全 sliding、24 local + 8 global hybrid。只计算相对 token-history factor，再写需要补哪些字段才能得到真实 bytes。

预期观察：architecture pattern 会显著改变 KV scaling；但 runtime 实际 allocation 仍需后续测量。

无 GPU 路径

全部可用 config/纸面公式完成。真机阶段再核 runtime memory。

排错

  • 实际 KV 比公式大：查 allocator pages、padding、full/global layers、buffer。
  • 模型能长 context 但远信息找不到：检查 attention window/architecture 和 quality fixture。
  • 新模型特别慢：确认 backend 是否有 native attention/cache kernel，而不是 generic fallback。

Retrieval Practice

  1. Sliding window 如何改变每层历史长度 scaling？
  2. Hybrid attention 为什么要按 layer type 分组预算？
  3. Latent cache 用什么代价换更小历史状态？
  4. KV quant、sliding、paged KV 三者分别改变哪一层？
  5. 为什么 architecture 支持与 runtime allocation 不能混为一谈？
  6. 长 context fit 为什么仍需 quality fixture？

Decision Rule

遇到新 attention architecture 时，暂停套传统 KV 公式。先确认每层保存的 state、历史范围、dtype 与 runtime allocation，再计算容量；任何“长上下文优势”还必须通过实际 backend 与质量验证。

Transfer

未来出现新的 sparse/linear/recurrent attention，也用同一三问：保存什么状态？每个 token 读多少历史？额外计算/软件支持成本是什么？

Architecture State 与 Runtime Allocation：做一张双列表

模型语义层Runtime 实现层
哪些层 full/local/sliding是否真的裁掉窗口外 cache
保存 K/V 还是 latent state实际 layout、padding、page/block
理论历史范围实际 allocated/resident bytes
KV dtype 语义/允许选项backend 是否有 native kernel/fallback

模型论文/config 只能回答左列；目标 runtime/source/实测才能回答右列。两列合在一起才是本地部署的 KV 现实。

Worked Example：为什么“4k sliding window”仍可能看到大内存增长？

可能有多种完全不同的解释：

  • 只有部分层 sliding，仍有 global layers；
  • runtime 为简化实现仍保留更多历史 state；
  • paged allocator 预留 block；
  • 除了 KV，还有 weights、workspace、graph buffer；
  • 模型所谓 sliding 只限制 attention receptive field，不等于物理释放。

因此先测 memory delta，再对照 exact implementation，不能从模型术语直接猜 allocator 行为。

Modern KV Experiment Matrix

固定 model artifact/runtime/backend，按 context 做 sweep，并记录：

context
predicted semantic history factor
observed memory
PP / TG or latency
quality fixture
allocation policy / KV dtype

如果改变 KV dtype、paging、sliding override 或 backend，每次只改变一个 semantic/runtime variable。无 GPU 时只填写前两列中的 architecture prediction，并把 observed memory 标成 DEFERRED-HARDWARE。

Interpretation Branches

  • memory 早早趋于平缓：可能与 sliding/eviction 一致，再查实现与质量。
  • memory 继续线性增长：可能存在 global layers/保留策略/paging；不要立刻说 sliding 没生效。
  • memory 省很多但 TG 下降：latent/reconstruction/quant kernel 可能把成本转移到 compute。
  • fit 通过但远距离质量差：这是 semantic/quality gate，不是容量问题。

What this lesson does NOT prove

任何一种 sliding、hybrid、latent 或 paged 设计都不存在通用的“更好”。它们分别改变 state、history、allocation 或 compute tradeoff。只有绑定 exact architecture、runtime 与目标 workload，才能比较价值。
