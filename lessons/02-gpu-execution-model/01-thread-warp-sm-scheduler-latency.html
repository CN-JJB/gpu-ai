GPU Execution Model · Lesson 02 · L0 + optional L2

GPU 为什么要同时养很多 warp？

你已经知道 GPU 变成了高度可编程的并行机器。下一步不是背“CUDA Core 数量”，而是看清：逻辑 thread 怎样变成 warp/wavefront，block 怎样驻留到 SM/CU，scheduler 又怎样把等待藏在其他工作后面。

Prerequisite Check

先完成 Lesson 01，并能区分“GPU 架构代际”与“具体产品规格”。你只需要会整数除法和基本的 thread/任务概念；不会 CUDA 不阻塞本节。若 warp、scheduler 等词完全陌生，先把它们临时理解为“把很多线程分组并轮流发射工作的硬件组织”。

真实问题

显存访问很慢，为什么 GPU 还能保持很高吞吐？如果一个 warp 在等数据，SM/CU 难道就跟着一起发呆吗？

先记住这条链

thread→ warp / wavefront→ SM / CU residency→ scheduler→ latency hiding

1. Thread：你写的是很多“逻辑小工人”

CUDA thread 或 HIP work-item 是程序员表达并行工作的基本单位。一个 thread 可以有自己的索引、寄存器状态和控制流。

但别把它想成“一条 thread 对应一颗 CUDA Core”。GPU 会把大量逻辑 threads 组织成更大的执行组，再交给硬件调度。

2. Warp / Wavefront：scheduler 真正面对的是“组”

NVIDIA CUDA 把同一 block 内的 threads 划成 32-thread warp。AMD 对应概念通常叫 wavefront；HIP 也会使用 warp 这个兼容术语，但宽度依目标架构而变，不能把“AMD 永远 64”当成规则。

NVIDIA

warp = 32 threads

性能上要考虑 divergence、memory coalescing 和 partial warp。

AMD

wavefront / warp = target-dependent

CDNA/Instinct 常见 Wave64；现代 RDNA/HIP 常见 Wave32。可移植代码应查询 warpSize。

3. SM / CU：block 为什么必须“住在一起”？

一个 CUDA thread block 的全部 threads 在一个 SM 上执行；一个 HIP work-group 的 wavefronts 同样驻留在一个 CU 上。这样同组 threads 才能访问同一块 shared memory / LDS 并进行低成本同步。

一个 SM/CU 往往能同时驻留多个 blocks，也就能同时保留很多 warp/wavefront 的执行状态。

Resident 不是“这一拍正在算”。Resident 的意思是：它的执行上下文和所需资源已经占在 SM/CU 上，轮到它时可以继续。

4. Scheduler：一个组在等，就找另一个 ready 组

假设某 warp 发出 global-memory load，而下一条指令依赖这个结果。这个 warp 暂时不能继续。

GPU 的关键技巧不是等它，而是让 scheduler 从其他 resident warp 中挑一个 ready 的继续发射。AMD 的 wavefront scheduler 也是同一个稳定思路。

这和 CPU 操作系统线程切换很不一样：正常情况下 resident warp/wavefront 的程序计数器、寄存器等状态已经留在片上，不需要把整个上下文搬去内存再搬回来。

5. Latency hiding：没有消灭等待，只是别让流水线陪着等

下面的 L0 模型故意只保留一个机制：每个执行组做 4 条 compute instruction，然后发出一条长延迟 memory instruction，并等待 20 cycles。一个抽象 scheduler 每 cycle 最多发射一条指令。

6. Occupancy：为什么 registers 和 shared memory 会突然变重要？

想同时驻留更多 warp/wavefront，SM/CU 必须给它们留出执行状态和资源。问题是这些资源有限。

  • NVIDIA：register file、shared memory、最大 resident blocks/warps 等共同限制 occupancy。
  • AMD：VGPR、SGPR、LDS、warp slots/work-group limits 共同限制 occupancy。

所以一个 kernel 如果每 thread 要很多 registers，或者每 block 要很大一块 shared memory/LDS，同一个 SM/CU 能同时“养”的 blocks 和 warps 就可能变少。

7. 纠偏：100% occupancy 不是性能目标

Occupancy 是“能同时驻留多少”的指标，不是“有多快”的分数。

NVIDIA Best Practices 明确提醒：更高 occupancy 不总等于更高 performance。原因很现实：更多 registers 或更大的 shared-memory tile 可能让 occupancy 下降，却换来更高数据复用、更少 global-memory traffic 或更强 instruction-level parallelism。

真正要问的是：当前 kernel 是不是因为没有足够 ready warps 而暴露了 latency？如果不是，继续追 occupancy 可能没有收益。

这和本地 LLM 有什么关系？

  • GEMM：tile 越大，数据复用潜力越高，但 registers/shared memory/LDS 压力也可能更大。
  • Attention：Q/K/V tile、softmax 中间状态、shared-memory/LDS staging 都会占片上资源。
  • 量化 kernel：反量化、打包格式、向量化和寄存器中的中间值会影响 resource pressure。
  • 现代高性能 kernel：有时宁愿牺牲一部分 occupancy，也要换更好的 reuse、ILP、matrix-pipeline feeding 或更少内存流量。

如何选择 / 调查一张卡或一个 kernel？

  1. 不要用“CUDA Core 数量”直接推 thread 数或 LLM 性能。
  2. 查目标架构的 warp/wavefront size、SM/CU 资源和支持的软件栈。
  3. 看 kernel 的 block size、register usage、shared memory/LDS usage。
  4. 用 profiler 和真实 workload 判断 stall 与 utilization，而不是只盯 theoretical occupancy。
  5. 跨 NVIDIA/AMD 迁移时映射“作用”，不要把 SM 和 CU 的内部结构硬画等号。

教材补全：把 Thread / Warp / SM 变成可推理模型

Worked Example：为什么“更多线程”能隐藏延迟，却不能无限加速

假设一个 warp 发出 global-memory load 后需要等待很多周期。SM scheduler 可以先切去执行其他 ready warp：

warp A → memory wait
warp B → execute
warp C → execute
warp D → execute
...
warp A → data ready

这叫 latency hiding。它不是把 memory latency 消灭，而是用别的独立工作把等待时间覆盖掉。

什么时候更多 occupancy 不再有帮助？

  • 已经有足够 ready warps 隐藏延迟。
  • kernel 本身受带宽限制，更多 warps 只争同一条内存通路。
  • register/shared-memory 压力限制了实际可驻留 block。
  • 分支发散或依赖链让 warp 自身可执行指令不足。

实验预期

做线程/warp/scheduler 概念实验时，你应该观察到：

  • 较少独立工作时，延迟暴露更明显。
  • 增加可并行工作后，吞吐先改善，随后收益递减。
  • 单纯追求 occupancy 最大值，不保证 kernel 最快。

排错

  1. 先确认比较的是同一 kernel / input size。
  2. 看 register/shared-memory 使用是否改变。
  3. 看是否已经转成 memory-bandwidth bottleneck。
  4. 看 branch divergence / dependency 是否限制 ready work。

无对应 NVIDIA GPU 怎么办？

可以只用课程交互/纸上调度 trace 完成主目标，再把概念映射到 AMD wavefront/CU 或 Apple SIMD-group。学习目标是理解“成组执行 + 多组驻留 + scheduler 隐藏等待”，不是背 NVIDIA 名词。

Decision Rule

看到“更多 CUDA cores / 更高 occupancy”时，不直接推出更快。先问 workload 是否有足够并行、是否受 latency、bandwidth、register 或 branch 限制。
