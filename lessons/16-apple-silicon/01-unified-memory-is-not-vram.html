Apple Silicon 1 — Unified Memory：它不是“共享显存”，也不是“64 GB 免费 VRAM”

真实问题：为什么 64 GB Mac 能运行一些 24 GB 独显装不下的模型，但又不能说“它有 64 GB 显存”？

1. 先画离散 GPU

CPU
│
├─ system RAM
│
└─ PCIe / interconnect
        │ copy
        ▼
      GPU
      └─ VRAM

两个物理内存池意味着：

  • 模型可能同时在 RAM 和 VRAM 各有一份；
  • CPU→GPU 需要 transfer；
  • VRAM capacity 是独立硬限制。

2. Apple Silicon 把内存池放进一个 SoC 系统

CPU ─┐
GPU ─┼──── unified memory
ANE ─┤
I/O ─┘

M1 官方就把 Unified Memory Architecture 定义成一个高带宽、低延迟的单一内存池，SoC 各单元可以访问同一数据，而不必在多个物理内存池之间复制。

优势不是“RAM 变成 VRAM”。
优势是：CPU 与 GPU 不再天然被“system RAM vs dedicated VRAM”这堵物理墙隔开。

3. Metal 真的能看到这一点

Metal device 有：

hasUnifiedMemory

Apple Silicon 上为 true。

普通 Metal resource 默认：

MTLStorageMode.shared

表示 CPU/GPU 都可以访问这份 system-memory resource。

4. 但 shared 不等于“什么都不用管”

Apple 文档明确要求 CPU/GPU 对共享资源仍要正确同步。

CPU writes
→ command/dependency completes
→ GPU reads

如果顺序错了：

same address
+ wrong timing
= race / stale data

5. Framework 仍可能制造其他资源

Metal 还支持：

  • private GPU resources；
  • temporary buffers；
  • optimized layouts；
  • kernel workspaces。

所以：

Unified Memory
!=
"every app only has one copy forever"

6. 64 GB 机器到底有多少可以给 LLM？

统一内存同时要给：

  • macOS；
  • 浏览器/应用；
  • CPU；
  • GPU；
  • KV Cache；
  • runtime workspace；
  • 其他系统服务。

模型预算应该写成：

safe model budget
≈ installed unified memory
 - OS/apps reserve
 - runtime buffers
 - safety headroom

7. Metal 给了一个更靠谱的指标

recommendedMaxWorkingSetSize

Apple 把它定义为：GPU 在不影响运行时性能的前提下，大致可以分配的内存量。

还有：

currentAllocatedSize

所以真实实验应该记录它们，而不是把机器 RAM 数字改名叫“VRAM”。

8. Unified Memory 没有消灭 bandwidth

假设每生成一个 token 都要近似流过 20 GiB 权重：

200 GiB/s memory bandwidth
÷ 20 GiB/token
≈ 10 token/s theoretical bandwidth roof

这只是极简上限，但它解释一个现实：

Apple 本地 LLM 的 decode，经常首先应该看 memory bandwidth，而不是 GPU 核心数。

9. CPU/GPU/ANE 还会共享带宽

统一内存减少 copy boundary，但同一个内存系统也意味着多个单元的流量共享有限的物理通道。

GPU demand
+ CPU demand
+ other SoC traffic
> memory bandwidth

→ someone waits

10. 为什么 Pro / Max / Ultra 很关键

同样写着“M3”或“M5”，不同 tier 可以有完全不同的：

  • 内存容量；
  • 带宽；
  • GPU resources；
  • package 结构。

所以买 Mac 跑 LLM，必须记录：

exact chip tier
+ memory capacity
+ memory bandwidth

而不是只说：

"M4 很新"

学生闭环 — Unified Memory

硬件门槛：L0；真机增强 L1（Apple Silicon Mac）。

成本：0 元主路径；课程不要求购买对应平台。

风险：safe。

替代路径：没有 Mac 就完成统一内存预算与架构调查；有 Apple Silicon 再做 Metal/MLX inventory。

能力目标

  • 解释 Apple Silicon 的 CPU/GPU 共享物理内存为什么改变传统 host RAM vs VRAM 边界。
  • 区分 GPU、Neural Engine、Metal、MLX/Core ML 的职责层。
  • 用 working-set / memory pressure，而不是只看总统一内存，判断本地 LLM 容量风险。

小实验 / 反馈

做 Experiment 27：Apple unified-memory budget model；有 Apple Silicon 时做 Experiment 28：real Metal/MLX inventory。

Retrieval Practice

  1. 为什么“统一内存 64GB”既不是“独显 64GB VRAM”，也不是“GPU 只能拿很少内存”？
  2. 为什么“CPU 和 GPU 共享内存”不意味着任何数据访问都零成本？
  3. 模型能装进统一内存后，还要继续检查哪些带宽、working-set、backend 条件？
  4. 某模型能用 MLX 跑，与它能用 llama.cpp Metal 跑，证明的是同一件事吗？

完成证据

做一张 Apple 路径预算：总统一内存 → OS/应用余量 → 模型权重 → KV/context → runtime headroom，并把“已知/估算/待真机验证”分开。

如何迁移

Apple 的特殊性用来强化一个通用原则：逻辑内存模型、物理内存拓扑、runtime allocation policy 是三层，不要把营销容量直接等价成可用模型容量。
