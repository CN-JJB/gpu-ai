Apple Silicon（二）：Metal GPU 的 thread、SIMD-group 与 threadgroup

Apple GPU 也不是“CUDA 术语换名字”。本节建立 Metal 计算的基本映射：grid、threadgroup、thread、SIMD-group、threadgroup memory，以及这些抽象怎样决定并行度、同步和片上复用。

Prerequisite Check

你应知道 NVIDIA 的 thread/warp/block/shared memory 或 AMD 的 work-item/wave/workgroup/LDS 的粗略作用。这里只做“功能层类比”，不假设内部硬件相同。

真实问题：为什么把 CUDA kernel 机械翻译成 Metal 名词，常常跑得不理想？

因为不同 GPU 的 SIMD-group 宽度、片上资源、memory hierarchy、threadgroup 上限与最佳 tile 都可能不同。跨平台移植应该迁移算法的数据流，不是照抄 launch 参数。

1. Metal compute 的三层工作组织

grid
└─ threadgroups
   └─ threads
      └─ hardware groups threads into SIMD-groups

程序员决定 grid 和 threadgroup 的几何形状；硬件/编译器按 GPU 的执行宽度把线程组织为 SIMD-group。

Threadgroup 为什么重要？

同一 threadgroup 的线程可以使用 threadgroup memory 并进行组内同步，因此它是 tile、reduction、局部协作的自然边界。

device memory → cooperative load → threadgroup memory
                                   ↓
                         many threads reuse tile

2. SIMD-group：最接近 warp/wave 的功能类比

SIMD-group 代表一组以 SIMD 方式共同执行的线程。它在“成组执行、lane-level 操作、divergence 代价”上可以帮助你迁移 warp/wave 的直觉。

但不要写：

SIMD-group == NVIDIA warp == AMD wave

正确写法是：

same category: hardware-coordinated lane group
implementation details: vendor / GPU family specific

3. Threadgroup memory：为什么统一内存仍需要片上共享存储？

统一内存解决 CPU/GPU 共享物理内存的问题，不代表 GPU 每次访问大内存池都与片上 memory 一样快。高性能 kernel 仍需要在 register/threadgroup/cache 等更近位置复用数据。

纠偏：Unified Memory 是系统内存架构；threadgroup memory 是 GPU kernel 的快速片上协作资源。两者完全不同。

4. Occupancy / residency：线程越多并不总越快

一个 threadgroup 会消耗寄存器、threadgroup memory 与执行 slot。每组用得太多，会减少同一 GPU core/cluster 上可同时驻留的 groups；用得太少又可能无法提供足够工作隐藏延迟。

resources per group ↑
→ resident groups may ↓

but
resident groups ↑
≠ performance always ↑

和 CUDA 一样，occupancy 是约束，不是最终目标。

5. Memory access：连续 lane 访问为什么通常更友好？

GPU memory system 喜欢把相邻线程的相邻访问合并成更高效的 transaction。若每个 lane 随机跳跃，cache/transaction 效率可能下降。

这就是为什么矩阵/attention kernel 会花大量精力安排：

  • 数据 layout；
  • tile shape；
  • vectorized load/store；
  • threadgroup-memory bank/访问模式；
  • producer/consumer 顺序。

6. Branch divergence：SIMD-group 内不同路径发生什么？

如果同一组 lane 在条件分支上走不同路径，硬件通常需要掩码/分阶段执行不同路径，使部分 lane 暂时无工作。

if lane_condition:
  path A
else:
  path B

mixed lanes → some execution resources idle during each path

因此 branch 本身不是禁忌；真正的问题是分支是否在同一 SIMD-group 内严重发散，以及计算量是否足以掩盖。

Worked Example：把 reduction 从 CUDA 思维迁移到 Metal

不要先翻译 API 名。先写算法：

  1. 每个 thread 读取一个或多个元素；
  2. 先做 lane/SIMD-group 内 reduction；
  3. 若跨 SIMD-group，需要写入 threadgroup memory；
  4. 同步；
  5. 由较少线程做最终 reduction。

然后再用 Metal 的 simdgroup/threadgroup primitives 实现。这样迁移的是数据流和同步边界，而不是 CUDA 语法。

7. Metal、MPS、MLX 分别在哪一层？

层作用
Metal底层 GPU graphics/compute API 与 shading language
Metal Performance Shaders 等库提供优化好的常见计算/图形/ML primitives
MLX面向机器学习的高层 array/framework，Apple Silicon 上利用 Metal GPU
MLX-LM / llama.cpp 等更接近 LLM 应用的模型加载、量化、生成与服务

调优时越往下越能控制细节，但开发成本也越高。

Why it matters

  • 解释 Apple GPU 为什么也需要 tile/reuse/occupancy，而 unified memory 不是性能魔法。
  • 帮助你读 MLX/Metal kernel 性能问题，不把所有瓶颈归因于“内存带宽”。
  • 让你能把 CUDA/HIP 的并行算法迁移到 Metal，而不做错误的一比一硬件映射。
  • 为理解 Apple GPU family 代际与 MLX backend 打基础。

常见误区

  • “Metal thread = CPU thread”——GPU thread 是大规模数据并行执行实例。
  • “SIMD-group 永远固定某个宽度”——应以具体 GPU/API capability 查询。
  • “统一内存所以不需要 threadgroup memory”——系统共享内存与片上复用不同层级。
  • “threadgroup 越大越快”——资源占用和 workload shape 决定最优点。
  • “MLX 就是 Metal 的另一个名字”——MLX 是更高层 ML framework。

小实验与预期观察

做一个纸面 kernel mapping：选择 vector add、reduction、tiled matrix multiply 三种算法，分别写出 grid/threadgroup、是否需要 threadgroup memory、是否需要 barrier、可能发生 divergence 的位置。然后把同一表映射到 CUDA/HIP。

预期你会发现 API 名不同，但数据并行、局部复用和同步的核心问题高度可迁移。

无 Apple 硬件路径

本节 L0 通过 Metal 文档和纸面 mapping 完成。拥有 Mac 后再做 threadgroup-size/benchmark 小实验；不要求编写复杂 shader 才算完成。

排错

  • 改变 threadgroup size 后变慢：检查 occupancy、register/threadgroup-memory usage、边界线程浪费。
  • 结果错误：优先检查 barrier、跨 threadgroup 共享假设、buffer bounds。
  • GPU 利用率低：检查 workload 太小、CPU dispatch/tokenization、频繁同步、memory stalls。

Retrieval Practice

  1. grid/threadgroup/thread 各自解决什么组织问题？
  2. SIMD-group 与 warp/wave 可以在哪个层面类比，哪里不能？
  3. 为什么 unified memory 存在时仍需要 threadgroup memory？
  4. threadgroup 太大可能通过哪些资源限制降低 residency？
  5. 解释 branch divergence 为什么是“同组 lane 利用率”问题。
  6. 把一个 CUDA reduction 迁移到 Metal 时，为什么应先迁移数据流而不是术语？

Decision Rule

使用 Metal/MLX 性能时，先确认瓶颈属于 launch、compute、memory、synchronization 还是 host。不要用“Apple unified memory 很快”或“GPU cores 很多”替代 kernel 级解释。

Transfer

以后看到任何 GPU API，都先找四个抽象：work grouping、lane grouping、on-chip cooperative memory、synchronization。再看 vendor-specific 宽度和限制。
