Apple Silicon 2 — Metal GPU：Threadgroup、SIMD Group 与 Threadgroup Memory

Apple GPU 不是只能通过 ML 框架当黑箱用。Metal 有完整 compute execution model。

1. 软件层级

grid
└─ threadgroups
   └─ threads

这和 CUDA/HIP 的 grid/block/thread 可以做概念迁移，但名字和硬件实现不要强行等同。

2. 实际执行还有 SIMD Group

threadgroup
├─ SIMD group 0
├─ SIMD group 1
└─ ...

同一个 SIMD group 的线程并行执行同一段代码。

3. Divergence 还是老问题

lane 0..15 → branch A
lane 16..31 → branch B

如果硬件需要执行两个路径：

execute A
+ execute B
→ useful lane utilization falls

和 warp/wavefront 一样，控制流一致性很重要。

4. 千万不要背“Apple 一定 32-wide”

Metal 正式提供：

pipelineState.threadExecutionWidth

Apple 文档明确说：SIMD-group size 在 GPU 之间可能不同，尤其不同 Mac GPU。

课程规则：运行时 query，不要硬编码 32。

5. Threadgroup size 也不是固定数字

每个 compute pipeline 还会告诉你：

maxTotalThreadsPerThreadgroup

这个值受到 kernel resource 影响。

即使同一张 GPU：

kernel A
register/threadgroup memory small
→ more/larger active groups

kernel B
resource-heavy
→ lower limit / occupancy

6. Threadgroup Memory

Metal 的 workgroup-local scratchpad：

threadgroup memory
生态低延迟 cooperative scratchpad
NVIDIAshared memory
AMDLDS
Apple Metalthreadgroup memory

用途一样可以迁移：

  • GEMM tile；
  • attention tile；
  • reduction；
  • softmax；
  • 数据复用。

7. FlashAttention 的知识可以直接迁过来

device memory
→ load tile
→ threadgroup memory / registers
→ SIMD-group math
→ online reduction
→ write output

Apple GPU 仍然面对：

  • memory latency；
  • bandwidth；
  • reuse；
  • divergence；
  • resource pressure。

Unified Memory 没有让 kernel optimization 消失。

8. 为什么 Apple 不公开“SM 数”也能学？

NVIDIA/AMD 给开发者很多 microarchitecture 数字；Apple 更强调 API/runtime properties。

课程不应该编造：

Apple GPU core = exactly one SM

而应该用可迁移问题：

SIMD width?
threadgroup limit?
threadgroup memory?
register pressure?
device-memory bandwidth?
kernel occupancy?

9. 一个 Metal kernel 的正确实验流程

  1. 建立 compute pipeline；
  2. 读 threadExecutionWidth；
  3. 读 maxTotalThreadsPerThreadgroup；
  4. 选择 threadgroup size；
  5. benchmark；
  6. profile memory/occupancy；
  7. 再改 tile。

这比背“某代 Apple GPU 是多少宽”更能迁移。

学生闭环 — Metal execution model

硬件门槛：L0；真机增强 L1（Apple Silicon Mac）。

成本：0 元主路径；课程不要求购买对应平台。

风险：safe。

替代路径：没有 Mac 就完成统一内存预算与架构调查；有 Apple Silicon 再做 Metal/MLX inventory。

能力目标

  • 解释 Apple Silicon 的 CPU/GPU 共享物理内存为什么改变传统 host RAM vs VRAM 边界。
  • 区分 GPU、Neural Engine、Metal、MLX/Core ML 的职责层。
  • 用 working-set / memory pressure，而不是只看总统一内存，判断本地 LLM 容量风险。

小实验 / 反馈

做 Experiment 27：Apple unified-memory budget model；有 Apple Silicon 时做 Experiment 28：real Metal/MLX inventory。

Retrieval Practice

  1. thread / SIMD-group / threadgroup 与 shared/private storage 怎样映射到前面 GPU 执行/内存模型？
  2. 为什么“CPU 和 GPU 共享内存”不意味着任何数据访问都零成本？
  3. 模型能装进统一内存后，还要继续检查哪些带宽、working-set、backend 条件？
  4. 某模型能用 MLX 跑，与它能用 llama.cpp Metal 跑，证明的是同一件事吗？

完成证据

做一张 Apple 路径预算：总统一内存 → OS/应用余量 → 模型权重 → KV/context → runtime headroom，并把“已知/估算/待真机验证”分开。

如何迁移

Apple 的特殊性用来强化一个通用原则：逻辑内存模型、物理内存拓扑、runtime allocation policy 是三层，不要把营销容量直接等价成可用模型容量。
