Transformer Anatomy · L0→L1

Mixture of Experts：总参数、Active 参数、Resident 权重为什么必须分开？

MoE 最容易制造“参数量错觉”：一个模型可以有极大的总参数，但每个 token 只激活少数 expert。计算可能相对稀疏，然而权重仍要存放/搬运，routing 还会制造新的数据流和负载不均衡问题。

Prerequisite Check

你应理解 dense SwiGLU/FFN 的 up/gate/down 权重，以及 decoder 每层都会处理当前 token。

真实问题：一个“总参数 100B、每 token 激活 10B”的模型，应该按 10B 还是 100B 买显存？

两者都不能单独回答。计算工作量更接近 active experts；权重驻留容量通常更接近需要加载的总 expert weights；如果权重不全驻留，还会产生 CPU/SSD/跨 GPU 搬运。

1. Dense FFN 与 MoE FFN

Dense:
token → one shared FFN

MoE:
token → router → choose top-k experts
                  ├→ expert 3 FFN
                  └→ expert 7 FFN
              → combine outputs

Router 为 token 计算 expert score，选择 top-k，再把 token 送往对应 expert。

2. 三个参数量概念

概念含义硬件影响
Total parameters模型所有共享层 + 所有 experts文件/完整权重存储
Resident parameters当前运行时实际驻留在 GPU/CPU/内存的权重显存/主存容量
Active parameters某 token 实际参与计算的 expert + shared 参数每 token compute/traffic 的重要近似

在完全 GPU 驻留时，resident 可能接近 total；active 仍明显更小。

3. 为什么 Active 小不等于显存需求小？

假设每层有 8 个 expert、每 token 只选 2 个。你不能只加载两个固定 expert，因为不同 token 可能选不同 expert。若想避免频繁搬运，通常需要让更多/全部 experts 常驻可访问 memory。

top-2 compute
≠ only 2 experts need storage forever

4. Router traffic：稀疏计算引入了新的数据移动

在单 GPU 上，routing 主要是选择与不同 expert 权重访问；在多 GPU expert parallel 中，还可能把 token representation 发送到拥有目标 expert 的 GPU，再把输出发回。

GPU0 token
→ router chooses expert on GPU2
→ interconnect transfer
→ GPU2 expert compute
→ return / combine

所以 MoE 在多 GPU 上常成为compute + communication问题。

5. Load balancing：为什么专家不能总挤在少数几个？

如果很多 token 都路由到同一个 expert：

  • 该 expert/GPU 排队；
  • 其他 expert 闲置；
  • batch 中 token 分布不均；
  • 通信热点形成。

训练时常加入 load-balancing 策略；推理时真实 prompt 分布仍会影响 expert utilization。

Worked Example：8 experts、top-2

假设每个 expert FFN 权重 1 GB，另有 4 GB shared weights：

total weight storage ≈ 4 + 8×1 = 12 GB
active expert weight per token ≈ 4(shared conceptually reused) + 2×1

这只是教学简化。关键结论：每 token 的 expert compute 只涉及 2 GB expert 权重，但为了让任意 routing 立即可用，你可能仍要为 8 GB expert 集合安排 resident storage。

6. Offload MoE：为什么可能“能跑但一卡一卡”？

如果部分 experts 放 CPU/RAM，每当 router 选到未驻留 expert，就可能需要 PCIe/host access。若 routing 不可预测、cache hit 低，会产生明显 latency 抖动。

因此 MoE offload 需要观察：

  • 哪些层/experts resident；
  • host↔GPU traffic；
  • expert cache policy；
  • p50/p95 token latency，而不只平均 TG。

7. 为什么 MoE 的“参数效率”不等于本地部署效率？

MoE 可以用更大总参数容量而保持有限 active compute，这是模型设计优势；但本地设备常首先受内存容量限制。数据中心可以用很多 HBM GPU 分布 experts，本地单卡未必能享受同样的 system economics。

8. MoE 量化特别有吸引力的原因

因为大量 resident expert weights 占容量与带宽。量化可明显压缩总权重，使更多 experts 常驻 accelerator memory。但 quant kernel、质量与 routing traffic 仍需验证。

Why it matters

  • 避免用“active B”误算模型显存需求。
  • 避免用“total B”误判每 token compute 一定等同 dense 同参数模型。
  • 理解多 GPU MoE 为什么特别依赖互联和负载平衡。
  • 解释 expert offload 为什么可能产生 latency tail。
  • 帮助你判断大 MoE 是否适合单机垃圾佬方案。

常见误区

  • “MoE 只激活 2 个 expert，所以只存 2 个”——routing 会选择不同 experts。
  • “100B MoE 就和 100B dense 一样慢”——active compute 可以小很多。
  • “Active 10B 就等同 10B dense 的所有硬件需求”——resident storage/traffic 完全不同。
  • “多 GPU 只要把 experts 平均分就行”——token routing 可能不均。
  • “平均 token/s 正常就代表 offload 体验正常”——tail latency 可能很差。

小实验

画一个 8-expert top-2 toy router。为 16 个 token 随机/人为分配 expert，统计每个 expert 收到多少 token。再假设 experts 分布在两张 GPU，计算需要跨卡的 token 数。

预期观察：即使 expert 数平均分布，token workload 也可能不均，通信量取决于 routing。

无 GPU 路径

本课用纸面 routing/容量预算即可。真机 MoE benchmark 留到学习阶段。

排错

  • MoE 模型加载 OOM：先看 resident total，而非 active params。
  • 平均 TG 可以但偶发卡顿：检查 expert offload/host traffic/tail latency。
  • 多 GPU scaling 差：检查 expert placement、routing imbalance、interconnect。

Retrieval Practice

  1. Total、resident、active parameters 分别回答什么？
  2. 为什么 top-2 不意味着只需存两个 expert？
  3. MoE 多 GPU 为什么增加 all-to-all-like communication 问题？
  4. expert load imbalance 会怎样影响吞吐？
  5. 为什么 offloaded MoE 需要看 tail latency？
  6. 量化为什么对 MoE resident storage 特别有价值？

Decision Rule

评估 MoE 本地部署必须同时写 total/resident/active 三个规模，并记录 expert placement/offsload/互联。不得用 active parameter 数替代显存预算，也不得用 total parameter 数直接替代每-token compute。

Transfer

以后看到 shared experts、fine-grained experts、expert caching 等新设计，仍按四个问题拆：存多少、每 token 算多少、路由到哪里、为此搬多少数据。

MoE Deployment Packet：四张表必须同时存在

  1. Resident table：哪些 expert/层驻留在哪个 device/RAM；
  2. Routing table：每 token 选哪些 expert，top-k 与 shared expert 规则；
  3. Traffic table：token/activation 是否跨 device、跨 PCIe/互联；
  4. Latency table：平均 TG 之外至少保留 token/request tail 观察。

缺 resident table，就无法做容量判断；缺 routing/traffic，就无法解释多 GPU 或 offload；缺 tail，就可能把“平均很快但偶发卡顿”误判为体验正常。

Worked Example：8 experts 平均分两张卡，为什么仍可能严重不均衡？

假设 GPU0 放 E0–E3，GPU1 放 E4–E7。16 个 token 的 router 并不保证平均命中每个 expert。如果大多数 token 同时选择 GPU0 上的 experts，那么：

storage placement = balanced
does NOT imply
token workload = balanced

如果某些 token 还需要另一张卡上的 expert，就会出现 activation/token dispatch traffic。真正的 system cost 来自 routing distribution，不是只看每张卡放了几个 expert。

Offload 的三个不同状态

  • resident on accelerator：容量贵，但访问路径最直接；
  • resident in host memory：可扩大可运行模型，但可能带来 host/PCIe traffic；
  • not resident / load-on-demand：还可能引入更大的 page/load latency。

不同 runtime 的实现不同，Evidence 必须记录实际 placement，而不能仅凭“offload layers”字段猜 expert 行为。

Experiment Evidence

固定 exact MoE artifact、runtime、context、batch/concurrency。保存 total/resident/active 参数描述、expert placement、routing/traffic telemetry（若可得）、PP/TG、p50/p95 或逐 token latency、quality。无 GPU 时，用 toy router 生成 routing histogram 与跨卡 traffic count。

Interpretation Branches

  • OOM：看 resident total，不用 active params 安慰自己。
  • 平均 TG 好、p95 差：优先查 expert miss/offload/routing imbalance。
  • 多 GPU utilization 不均：检查 routing distribution 与 placement，而不是先怀疑某张卡坏。
  • 量化后容量改善但速度不升：检查 expert kernel、routing/traffic 与解包成本。

What this lesson does NOT prove

MoE 的 active parameter 数不能直接转换成 dense 等价速度，也不能直接转换成显存需求。不同 MoE 设计的 shared expert、expert size、routing、cache 与通信都可能不同；所有推论必须绑定 exact architecture。
