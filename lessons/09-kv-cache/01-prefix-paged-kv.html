KV Reuse · Lesson 09 · L0 + optional L1/L2

为什么同一份长前缀，第二次可以快很多？

长 system prompt、RAG 文档、多轮聊天历史经常会被一遍遍送进模型。Prefix Cache 的目标不是“把答案缓存下来”，而是把已经算过的 prompt KV 留下来，让后续请求跳过重复 prefill。

真实问题

我每次都把同一份 10K-token 文档发给模型，只换最后一句问题。为什么 server 不应该每次都把前 10K tokens 从头算一遍？

先分清四个“KV/cache”

概念复用什么主要解决什么
普通 KV cache同一个 request 的过去 tokensdecode 不重算整段历史 K/V
Prefix/Prompt cache不同 request 的共同 prompt prefix跳过重复 prefill
Paged/Block KVKV memory blocks/pages动态 allocation / sharing / eviction
Unified KVruntime 的共享 KV buffer/manager多 sequence KV 管理

Paged KV、Unified KV、Prefix Cache 不是三个同义词。

1. 普通 KV cache 已经解决了什么？

同一个 autoregressive request：

prompt tokens
→ prefill K/V
→ generate token 1
→ generate token 2
→ generate token 3

生成 token 3 时，不需要重新算 prompt 和 token 1/2 的全部 K/V，因为它们已经在当前 request 的 KV cache。

这是请求内部的复用。

2. Prefix Cache 多做一步：跨 request 复用

Request A：

[4000-token manual]
[question A]

Request B：

[4000-token manual]
[question B]

如果前 4000 tokens 的 tokenized prefix 完全匹配，并且对应 KV 仍在可复用 cache：

4000 prefix KV→ reuse→ only process new suffix

Request B 不必重新做那 4000 tokens 的 prefill。

3. 它省的是 Prefill，不是 Decode

这条边界非常重要。

shared prefix 4000 tokens → can be reused
new suffix 100 tokens     → still prefill
new answer 500 tokens     → still decode 500 new tokens

Prefix Cache 主要降低 prompt processing / TTFT，不会让新生成的 500 个 token 消失。

vLLM 官方也明确把它描述为 prefill optimization，而不是 decode acceleration。

4. llama-server 能直接告诉你复用了多少 prompt

current llama-server 的 response timings 示例包含：

  • cache_n：从 cache 复用的 prompt tokens；
  • prompt_n：这次真正重新处理的 prompt tokens；
  • prompt_ms；
  • predicted_n / predicted_ms。

所以一个很漂亮的 warm-cache Evidence 是：

cold:
cache_n  small
prompt_n large
prompt_ms large

warm:
cache_n  large
prompt_n small
prompt_ms small

predicted work:
still exists

5. “看起来一样”为什么不保证 hit？

模型真正看到的不是你的肉眼字符串，而是经过：

  • chat template；
  • tokenization；
  • system/tool formatting；
  • 可能的 multimodal inputs；
  • adapter/LoRA context；
  • runtime cache key。

所以：

visually same-ish prompt ≠ guaranteed identical cache prefix。

6. Prefix 一旦分叉，后面为什么不能继续复用？

两个 token 序列：

A B C D E F
A B C X Y Z

共同 state 只到：

A B C

从 X 开始，attention 历史已经不同。后面的 KV 不能假装还是第一条 request 的 state。

真实 runtime 还可能按 block/match boundary 截断 reuse。

7. Paged/Block KV 在这里有什么价值？

如果 KV 是固定 block/page pool：

KV block pool→ request references blocks→ reuse / free / evict

就更容易动态管理：

  • 不同长度 request；
  • prefix sharing；
  • fragmentation；
  • eviction；
  • offload。

vLLM 与 TensorRT-LLM 都公开使用 block/page pool 思维。

但：

有 paged KV 不代表所有 request 自动 cache hit。

8. llama.cpp Unified KV 为什么不能直接叫 PagedAttention？

current llama.cpp 有 unified KV 机制，让多个 sequences 使用共享 KV buffer/manager。

这和 vLLM/TensorRT-LLM 的 block/page pool 都属于“多 sequence KV 管理”，但它们不是同一个具体数据结构。

课程里必须写：

unified KV ≠ paged KV ≠ prefix cache

9. Cache 不是免费硬盘：它占容量

每保留一个可复用 prefix，都意味着某些 KV state 还占着 memory。

cache more prefixes
→ higher hit opportunity
→ less free capacity for new active KV

容量紧张时，旧 reusable state 需要被 evict。

vLLM 与 TensorRT-LLM 当前文档都描述有限 block pool 与 LRU-like eviction。

10. Hit rate 为什么会骗人？

比较：

Cache A

90% hit。

每次只复用 16 tokens。

Cache B

40% hit。

每次复用 4000 tokens。

哪个更有价值？不能只看 hit rate。

更应该看：

  • reused prompt tokens；
  • processed prompt tokens；
  • saved prompt ms；
  • TTFT；
  • cache memory cost。

11. L0：容量 0 / 1 / 2 / 3 个 prefix，会发生什么？

请求序列：

A, B, A, C, A, B

每个 request：

  • shared prefix = 1024 tokens；
  • unique suffix = 64 tokens；
  • new decode = 128 tokens。

cache 采用 LRU-like 教学模型。

capacityhitsevictionsprompt tokens processedsaved

无论 cache capacity 是多少：

decode tokens total = 6 × 128 = 768

完全不变。

这就是“prefix cache 省 prefill，不省新 token decode”的最小证据。

12. capacity=1 为什么 hit rate 居然还是 0？

访问：

A → cache A
B → evict A, cache B
A → evict B, cache A
C → evict A
A → ...
B → ...

这叫 working set 超过 cache capacity。

“cache 已经开启”不代表你的 workload 会有 hit。

13. 并发为什么可能让 warm-up 没你想的有效？

如果 8 个相同长 prefix 请求同时第一次到达：

第一个 request 的 prefix KV 可能还没成为可复用 state，另外 7 个已经开始 prefill。

所以 benchmark 必须区分：

  • cold；
  • warm sequential；
  • warm concurrent。

TensorRT-LLM 官方专门提醒了这种 reuse timing。

14. Prefix cache 还有安全问题

在多人/多租户 service：

cache hit
→ latency changes
→ may reveal whether some prefix/state exists

vLLM current design 提供 cache salt 来隔离 reuse domain。

本地单用户机器问题较小，但一旦把服务开放给别人：

cache policy 也是 tenant isolation policy。

  • cache_n；
  • prompt_n；

  • prompt_per_second；

  • TTFT cold/warm proxy；
  • server/model exact identity。

如果 warm request 的 prompt_ms 从 800 ms 降到 40 ms，但 predicted_ms 几乎不变，这是不是 cache “失效”？为什么反而正符合 prefix cache 的设计目标？
