AMD Architecture · 1/4 · L0→L1

AMD 架构主线（一）：GCN → Vega

AMD 不能用“NVIDIA 换名词版”来学。你需要先建立自己的 AMD 执行模型：CU、wavefront、SIMD、VGPR/SGPR、LDS 与 HBM/GDDR，然后再理解 GCN 为什么既服务图形又成为早期 ROCm/HPC 的重要基础。

Prerequisite Check

你应知道 GPU 通过成组线程和大量并行工作隐藏延迟，也知道 register/shared/cache/VRAM 是不同层级。无需会 HIP/OpenCL。

真实问题：为什么“64 个 CU”不能直接换算成“多少个 NVIDIA SM”？

CU 和 SM 都是 GPU 的大粒度计算组织，但内部 scheduler、SIMD 宽度、wave/warp 语义、寄存器资源、指令吞吐与每代变化都不同。把它们做一比一换算，会像把“汽车发动机缸数”和“电机数量”直接换算一样失真。

1. GCN 的基本执行图

work-items / threads
      ↓ grouped as
wavefront
      ↓ scheduled on
Compute Unit (CU)
      ├─ SIMD execution
      ├─ vector registers (VGPR)
      ├─ scalar path / SGPR
      └─ LDS (on-chip shared data)

这张图是你以后读 AMD kernel tuning 的起点。CUDA 的 thread/warp/SM/shared memory 可以帮助建立直觉，但不要因此假设内部完全等价。

Wavefront 是什么？

程序看到许多 work-item/thread，硬件把它们成组执行。GCN 经典语境中常见 wave64。遇到分支时，同一 wave 中不同 lane 走不同路径可能需要序列化部分工作，这和 SIMT/SIMD divergence 的一般规律一致。

2. Scalar + Vector：为什么地址/控制工作不必占满所有 lane？

如果某个值对整个 wave 都相同，例如某个循环计数或统一地址计算，把它在每个 vector lane 重算会浪费资源。GCN 提供 scalar 资源处理适合 wave-uniform 的工作，让 vector datapath 专注逐 lane 数据。

长期规律：GPU 高吞吐不仅来自“更多向量 ALU”，也来自把控制、地址、标量与向量工作放到合适的数据路径。

3. LDS：AMD 的片上协作存储

Local Data Share（LDS）是 CU 内用于 workgroup 协作的低延迟片上存储。它承担的教学角色与 CUDA shared memory 类似：

global memory → cooperatively load tile → LDS → reuse → compute

但相似不代表所有 bank、容量、同步和 occupancy 规则相同。写跨厂商 kernel 时必须读对应 ISA/tuning guide。

4. VGPR 压力为什么会限制 occupancy？

每个 wave 需要一定数量的 vector registers。一个 kernel 如果为每个 thread 使用大量 VGPR，同一个 CU 能同时驻留的 wave 数就会减少。

fixed register file
÷ registers per active wave
≈ maximum resident waves (one of several limits)

因此“减少寄存器”有时提高并发，但如果过度减少导致 spill 到更慢的 memory，性能反而下降。这个 tradeoff 与 NVIDIA 一样存在，但具体阈值要按 AMD 架构测。

5. GCN 为什么长期存在？

GCN 是一条持续多代演化的 ISA/架构家族，覆盖消费图形、APU、专业与计算产品。它为 AMD 后续 ROCm/HIP 计算生态提供了重要硬件基础，但“GCN”本身跨度很大，不能把一个时代的功能套到所有 GCN SKU。

6. Vega：更强 memory/compute 方向与 HBM 产品

Vega 时代继续优化 CU/graphics pipeline，并在部分产品中使用 HBM，强调高带宽与高吞吐计算。对 LLM 学习最有价值的是：

  • 开始更认真地区分 consumer Vega 与 compute-oriented Vega/Instinct；
  • 理解 HBM 的容量/带宽/封装特征；
  • 理解低精度/packed operations 的硬件能力仍需要软件映射。

Worked Example：Vega 64 和某 Instinct Vega 产品为什么不能只说“都是 Vega”？

  1. 先确认 exact chip / SKU；
  2. 记录显存类型与容量；
  3. 记录 memory bandwidth；
  4. 记录对应 precision claims；
  5. 确认显示输出、散热、供电与机箱适配；
  6. 最关键：确认今天目标 ROCm/runtime/backend 是否支持 exact device。

最后一项尤其重要：旧 AMD 计算卡的硬件能力可能仍在，但软件支持矩阵会随 ROCm 版本变化。

7. 为什么早期 AMD GPGPU 生态学习起来“更容易踩版本坑”？

硬件、驱动、ROCm、HIP runtime、kernel library、Linux distribution、应用 backend 形成一条兼容链。任何一层不支持，纸面规格都不能转化成可用 LLM。

GPU ISA/device
→ kernel driver
→ ROCm runtime
→ HIP/library
→ llama.cpp / PyTorch / other backend
→ model workload

因此 AMD 课程必须把“当前兼容性”放到 Intelligence，而不是在稳定教材里写死一个永远有效的支持列表。

Why it matters

  • 建立 AMD 自己的执行模型，避免把 CU 当 SM 的简单别名。
  • 理解 wave/LDS/VGPR 后，才能读 HIP kernel、occupancy 和性能分析。
  • 解释为什么旧 Vega/Instinct 卡“规格诱人”却必须先过当前软件支持 gate。
  • 为 RDNA wave32 与 CDNA matrix-compute 分叉做准备。
  • 理解 HBM/大带宽为何对部分模型/计算 workload 有吸引力。

常见误区

  • “1 CU = 1 SM”——没有固定换算关系。
  • “wave64 就是 AMD 的 warp32 ×2”——只可做非常粗的成组执行类比，内部语义/吞吐不同。
  • “Vega 有 HBM，所以一定适合所有 LLM”——容量、runtime、kernel、功耗同样关键。
  • “ROCm 支持 AMD，所以所有 AMD 卡都支持”——必须 exact device + exact ROCm version。

小实验与预期观察

建立一张 GCN/Vega capability card：CU、wave size、LDS、VRAM、bandwidth、current ROCm status 分列。不要填推测值。预期你会发现“架构事实”和“当前软件事实”必须分两栏维护。

无 AMD 硬件路径

L0 使用 ROCm/HIP hardware implementation 文档与课程 reference 完成。不要为验证历史架构购买旧卡。若将来有真实 AMD GPU，再用只读工具收集 device/runtime identity。

排错

  • ROCm 安装成功但应用看不到 GPU：分别检查 kernel driver、runtime device list、应用 build/backend。
  • 程序能跑但 CPU 很忙/GPU 很闲：确认是否 fallback 或只有部分 layers offload。
  • 理论带宽高但模型慢：检查 quant kernel、wave utilization、memory clock、power/thermal 与 host transfer。

Retrieval Practice

  1. 为什么 CU 与 SM 不能按数量直接换算？
  2. scalar path 对 wave-uniform 工作有什么意义？
  3. LDS 解决什么问题？为什么它不是无限快的替代 VRAM？
  4. VGPR 使用过多怎样影响 resident waves？为什么一味减少 VGPR 也可能失败？
  5. 为什么 Vega 的 HBM 不能单独决定本地 LLM 价值？
  6. 写出 AMD 从 GPU 到应用 backend 的软件兼容链。

Decision Rule

可以用 CU/wave/LDS/VGPR 解释 GCN/Vega 的执行与片上复用；不能仅凭 CU 数、HBM 或历史计算定位推荐旧 AMD 卡。当前 ROCm/backend 支持必须作为 hard gate 重新验证。
