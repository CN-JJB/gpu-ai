AMD 架构主线（二）：RDNA → RDNA2

RDNA 不是“GCN 改名”。它代表 AMD 为图形效率重新组织执行资源的一次重要转向。对本地 LLM 学习者，最值得理解的是 wave32、WGP/CU 组织、cache 与 memory hierarchy 如何改变旧 GCN 直觉，以及“游戏架构”为什么仍能通过 HIP/ROCm 或其他 backend 参与计算。

Prerequisite Check

你应能解释 GCN 的 CU、wave64、LDS、VGPR，以及为什么 exact ROCm/backend support 是现实 hard gate。

真实问题：为什么从 Vega 换到 RDNA，不能只拿 CU 数比较？

因为每代 CU 内的 SIMD、scheduler、wave width、cache、时钟目标和每 CU 工作量都会变化。架构重组后，“一个 CU 能完成多少工作”本身就变了。

1. RDNA 的目标：更适合高时钟、高效率图形 workload

GCN 跨越图形与计算很多年。RDNA 针对现代图形 workload 重新优化前端、执行组织与 cache。最容易观察到的概念变化之一是 wave32 成为重要执行模式。

Wave32 为什么不是“wave64 除以 2 = 性能翻倍”？

更窄 wave 可以降低某些控制流 divergence 的浪费，并让 scheduler 以更细粒度组织工作；但每条指令处理的 lane 数也不同，最终吞吐取决于 SIMD 组织、issue、寄存器、occupancy 和 workload。

wave64: one instruction conceptually covers more lanes
wave32: finer scheduling/control granularity

neither statement alone predicts performance

2. Work Group Processor：理解名字变化，不陷入“两个 CU 就是一个大 CU”

RDNA 文档常以 WGP 描述更高层级的资源组织。你需要学会从名称背后找实际共享关系：哪些 scheduler/compute/cache/LDS 资源归 CU，哪些在更高层共享。不要为了类比 NVIDIA 强行把 WGP 映成某种 SM 数。

3. Cache hierarchy：Infinity Cache 的思维准备

RDNA/RDNA2 继续强化 cache 与数据路径。RDNA2 的大容量片上 cache 思路（常以 Infinity Cache 营销）本质上是在部分 workload 中提高有效带宽、减少外部显存流量。

这和 Ada 大 L2 的阅读方法一致：

  • 先问 working set 是否能产生复用；
  • 再问 hit rate 是否减少外部 DRAM bytes；
  • 不要把 cache capacity 与 VRAM capacity 混为一谈。

4. RDNA2 的新图形专用能力对 LLM 意味着什么？

RDNA2 增加面向光追等图形能力，但 LLM 不会因为“同代游戏 feature 多”自动获益。真正相关的是通用/矩阵计算路径、memory、runtime 与 kernel。

学习规则：同一 GPU 上的 ray tracing、raster、matrix/general compute 是不同 datapath。不要把一个领域的营销峰值迁移到另一个领域。

5. 消费 Radeon 做本地 LLM：为什么软件层比硬件方框图更容易决定成败？

很多 Radeon 硬件理论上具备很强的并行与带宽，但目标框架是否支持 exact ASIC、操作系统、ROCm version 与 quant kernel，才决定你能否获得稳定 GPU offload。

因此对 RDNA 卡的现实调查顺序应是：

  1. exact GPU/device ID；
  2. 目标 OS；
  3. current ROCm/runtime support；
  4. 目标应用 build 是否含 HIP/Vulkan/other backend；
  5. 目标 quant/model 是否有对应 GPU kernel；
  6. 最后才跑 benchmark。

Worked Example：同价 Radeon 大显存 vs NVIDIA 小显存怎么思考？

假设 Radeon A 有更大显存、更高标称带宽，NVIDIA B 显存较小但 CUDA backend 更成熟。不要先选厂商。先做两棵树：

Fit tree:
model+KV+buffers <= usable VRAM ?

Support tree:
device supported ?
runtime starts ?
backend offloads ?
required kernels exist ?

如果 A 通过两棵树，它的大显存可能形成真正优势；如果 support tree 在你的目标软件上失败，纸面容量无法转化成可用方案。这就是“硬件价值 × 软件可用性”。

6. RDNA 与 CDNA 为什么要分开学？

AMD 后来把图形优化的 RDNA 与 HPC/AI 计算导向的 CDNA 更明确地区分。RDNA 的存在提醒你：消费 GPU 的设计目标不是“最大化 LLM”；CDNA 则会更关注 matrix compute、HBM、互联与数据中心。

Why it matters

  • 避免用 CU 数跨 GCN/RDNA 直接比较。
  • 理解 wave32 对控制流/调度粒度的意义，而不是把它当性能倍增按钮。
  • 学会把大 cache 与 VRAM 区分。
  • 建立消费 Radeon 的 support-first 调查顺序。
  • 为后续 CDNA 与跨厂商采购建立“硬件潜力 × 软件可用性”模型。

常见误区

  • “wave32 比 wave64 快一倍”——没有这种通用换算。
  • “Infinity Cache 很大，所以等于多了显存”——cache 与容量 hard gate 不同。
  • “RDNA 是游戏架构，所以不能计算”——它仍有通用计算能力，现实取决于 backend。
  • “ROCm 新版 = 我的 Radeon 一定支持”——exact device support 必须查当前文档。

小实验与预期观察

选择一张 GCN/Vega 和一张 RDNA/RDNA2 卡，做 architecture/SKU/support 三层表。只用可靠来源记录 wave mode、VRAM、bandwidth、cache，以及当前目标 runtime status。预期你会发现“架构升级”和“应用可用性升级”不是同一条时间线。

无硬件路径

使用 AMD ISA/HIP 文档和当前兼容矩阵做 L0。拥有 Radeon 后再做 L1 device inventory；不要求为课程买卡。

排错

  • HIP runtime 能看到卡但应用不能：检查应用是否按该 backend 编译。
  • Vulkan 能跑而 HIP 不能：说明“GPU 可计算”与“特定 runtime 支持”是不同命题。
  • 大显存卡仍 OOM：检查可用 VRAM、KV/context、runtime buffer、host/offload 配置。

Decision Rule

RDNA 候选先过 exact device + target backend 的可用性 gate，再谈容量、带宽、价格和性能。不能因为“AMD 性价比高”或“ROCm 麻烦”做厂商级一刀切结论。
