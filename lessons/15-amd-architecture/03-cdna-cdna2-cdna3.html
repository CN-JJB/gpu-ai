AMD Architecture · 3/4 · L0→L2

AMD 架构主线（三）：CDNA → CDNA2 → CDNA3

CDNA 是理解 AMD 数据中心 AI/HPC 路线的关键。这里要学的不是 MI 系列型号表，而是 AMD 如何把图形导向的设计约束放到一边，把晶体管预算更集中地投入矩阵计算、HBM、chiplet/封装与 GPU 间互联。

Prerequisite Check

你应理解 RDNA 为图形效率优化，而本地 LLM 的主要约束常包括模型 fit、memory bandwidth、matrix/general kernel 与软件支持。

真实问题：为什么 AMD 需要一条和 RDNA 分开的计算架构线？

游戏 GPU 必须承担图形前端、显示、光栅/光追等需求；数据中心加速器则更关心 FP/矩阵吞吐、HBM 容量与带宽、ECC、GPU 间通信和大规模部署。如果两类产品长期用完全相同的晶体管预算，很难同时做到最优。

1. CDNA：把“计算优先”写进产品目标

CDNA 延续 AMD 计算生态，同时把设计重心更明确放在 HPC/AI。对于学生，最重要的观察是：产品目标会改变硬件资源比例。

更偏 RDNA/消费图形更偏 CDNA/计算
图形前端、显示与游戏效率矩阵/向量计算吞吐
GDDR/消费板卡成本HBM 容量与带宽
单卡游戏 workload多卡/HPC/AI workload
消费散热/接口服务器形态、互联、可靠性

2. Matrix Core：不要只把它翻译成“AMD Tensor Core”

为了建立直觉，你可以说两者都属于矩阵专用 datapath；但实际支持的数据类型、指令、tile、累加和编程接口不同。更好的跨厂商抽象是：

matrix accelerator
→ supported numeric modes
→ instruction/library interface
→ kernel mapping
→ actual workload utilization

这样你不会因为名字相似就假设性能或语义相同。

3. HBM：为什么 CDNA 对“每秒搬多少模型字节”特别认真？

HPC/AI 经常同时需要很大工作集和高持续带宽。HBM 通过先进封装和宽接口提供高带宽，并常与大容量/ECC 计算产品结合。

对 LLM 的直觉：

  • 权重必须先放得下；
  • 小 batch decode 往往需要持续读取大量权重，bandwidth 可能形成 roof；
  • prefill/大 batch 更容易提高算术强度，让 matrix compute 更重要。

因此 CDNA 的 HBM + matrix 路线很符合大模型数据中心 workload，但家用价值还会被价格、形态、软件与功耗重新排序。

4. CDNA2：多 die / 互联思维进入 GPU 本身

现代高端加速器越来越难只靠单块巨大 die 扩展。多 die/package 设计把计算资源通过片上/封装互联组合起来。学生不必记封装细节，但要理解：“一张卡”内部也可能已经是分布式数据移动问题。

compute die A ↔ high-bandwidth package link ↔ compute die B
          ↘ HBM stacks / memory controllers ↙

这会影响 NUMA-like locality、memory mapping、kernel scheduling 和可用带宽。软件层必须尽量隐藏复杂性，但性能调优仍可能感受到拓扑。

5. CDNA3：chiplet、HBM 与 AI 数值路径继续系统化

CDNA3 继续把 compute die、I/O/memory die、HBM、低精度 matrix capability 与 scale-out/scale-up 互联作为一个系统设计。稳定教材应该记住方向，而不是把某个具体产品峰值写死：

  • 计算越来越依赖 chiplet/advanced packaging；
  • memory capacity/bandwidth 与 compute 同等重要；
  • 更低精度格式被硬件加速，但软件/数值语义决定是否可用；
  • 多 GPU 通信成为训练与大模型推理的重要瓶颈。

Worked Example：一张二手 MI 加速卡看起来“带宽巨大”，能不能当家用 LLM 神卡？

先禁止自己回答“能”或“不能”。按 gate 走：

  1. Physical：尺寸、被动/主动散热、机箱风道、供电、接口。
  2. Host：PCIe slot/lanes、主板 IOMMU/BIOS、PSU。
  3. Software：exact device 是否在目标 ROCm version 支持；目标 OS 是否合适。
  4. Backend：llama.cpp/框架是否真正有对应 HIP kernels。
  5. Model fit：可用 HBM 是否足够。
  6. Performance：真实 PP/TG/PPL/功耗，而不是用 HBM bandwidth 猜。
  7. Cost/risk：价格、噪声、能耗、维修、转售。

只有前六项有证据，才能谈性价比。

6. ROCm 为什么是 CDNA 价值的一部分？

数据中心加速器不是独立工作的硅片。HIP compiler/runtime、rocBLAS/hipBLASLt 等库、kernel library、framework integration 决定矩阵单元和 memory system 能否被应用使用。

硬件能力 × 软件 enablement = 实际可用能力。任意一边为零，应用价值都接近零。

Why it matters

  • 帮你区分 AMD 的图形 RDNA 与计算 CDNA，不再把所有 Radeon/Instinct 放一张核心数表。
  • 建立 HBM + matrix + interconnect 的数据中心 AI system 模型。
  • 为理解多 die/chiplet GPU 与多 GPU 拓扑打基础。
  • 解释为什么廉价退役加速卡既可能有巨大潜力，也有巨大部署风险。
  • 提醒你 current ROCm/backend support 是现实 hard gate。

常见误区

  • “CDNA 是没有显示输出的 RDNA”——产品目标和资源组织更深层地不同。
  • “Matrix Core = Tensor Core，规格可以直接横比”——数值模式、指令与实现不同。
  • “HBM 带宽高，所以 token/s 按比例高”——compute/kernel/shape/软件仍可能成为瓶颈。
  • “一张卡内部对程序来说永远是均匀资源”——多 die/chiplet 可能引入拓扑。
  • “服务器卡便宜就适合家用”——散热/供电/驱动/形态都可能是 hard gate。

小实验与预期观察

做一份“退役数据中心加速卡 preflight worksheet”，不需要购买。至少填写 physical、power、memory、ROCm support、target backend、model fit、expected bottleneck、unknowns 八栏。预期你会发现很多诱人的纸面指标会被部署条件拦截。

无硬件路径

本课主路径就是 L0 research + worksheet。真正的 MI 卡 benchmark 留到有合法、安全硬件环境时执行；教材只规定证据格式和解释方法。

排错

  • 设备在 PCIe 能枚举但 ROCm 不工作：分层检查 kernel driver/runtime/device support。
  • 应用启动但性能低：确认 kernel/library 是否使用 matrix path，检查 HBM clocks/power/NUMA/topology。
  • 服务器被动卡过热：停止负载；被动散热设计依赖机箱高风压，不能当普通开放式显卡使用。

  2. 为什么 Matrix Core 只能与 Tensor Core 做“功能类别”类比，不能规格直接换算？
  3. HBM 对 LLM 的 capacity 和 bandwidth 分别怎样影响？
  4. 为什么多 die GPU 让“一张卡”内部也出现数据局部性问题？
  5. 列出购买退役 MI 卡前至少六个 hard/soft gate。
  6. 为什么 ROCm/library 是硬件价值的一部分，而不是附属软件？

Decision Rule

看到 CDNA/MI 的高带宽和 matrix 峰值时，先做部署与软件 gate。没有 exact device/runtime/backend 的可重复证据，不得把服务器卡标成家用 LLM bargain。

Transfer

把 CDNA 与 Hopper/Blackwell 并排时，不比营销总分；比较 numerics、HBM、interconnect、software ecosystem、system form factor 与真实 workload。下一节回到更新的 RDNA/CDNA 方向，练习如何处理“同厂不同产品线”的信息。
