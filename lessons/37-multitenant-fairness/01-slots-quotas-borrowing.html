Multi-Tenant Fairness — “每人两个请求”为什么一点都不公平？

1. Request 不是统一成本单位

Tenant A:
2 requests × 1000 output tokens

Tenant B:
2 requests × 50 output tokens

HTTP 请求数一样。

GPU 工作量完全不一样。

公平应该先问：你要公平分什么资源？

2. LLM 的资源至少有这些

slot time
prompt compute
decode tokens
KV memory
context capacity
queue time

3. Toy：两 slots

10 tok/s per slot

A：

A1 = 100 tokens
A2 = 100 tokens

B：

B1..B4 = 10 tokens each

4. 看请求数

A = 2/6 = 33.3%
B = 4/6 = 66.7%

似乎 B 请求更多。

5. 看 output work

A = 200/240 = 83.3%
B = 40/240  = 16.7%

完全反过来了。

6. Global FIFO

如果顺序：

A1 A2 B1 B2 B3 B4

两个 slots 先被：

A1 + A2

占满 10 秒。

B：

mean wait = 10.5 s
p95 wait  = 11 s

但 GPU slot utilization：

100%

吞吐很好，公平性很烂。

7. 每 tenant 最多 1 active

开始：

A1 + B1

B 很快跑完：

mean wait = 1.5 s
p95 = 3 s
last B done = 4 s

但 A2 必须等 A1 完成。

结果：

makespan = 20 s
slot utilization = 60%

公平了，但浪费硬件。

8. Work-conserving borrowing

规则：

A/B 都有等待：
每人最多 1 slot

B 已经没活：
A 可以借空闲 slot

结果 B 仍然：

mean wait = 1.5 s

A2 可以在 4 秒开始：

makespan = 14 s
utilization ≈ 85.7%
公平和高利用率不是只能二选一，但 scheduler 必须显式设计。

9. 为什么 token quota 比 request quota 好一点？

例如：

每用户 max output = 512
每天 100k generated tokens

至少比：

每天 100 requests

更接近真实资源。

10. 但 token 也不是完美成本

1000 prompt tokens

和：

1000 decode tokens

硬件路径不一样。

长 context 还会吃更多 KV。

11. 所以 quota 可以是多维的

max concurrent
max prompt
max output
max context
token budget
KV budget
priority weight

12. Priority 也有坑

如果：

high priority 永远优先

而 high priority 一直有请求：

low priority 永远跑不到

这叫 starvation。

13. 不能只看 global p95

整体：

p95 TTFT = 500 ms

可能隐藏：

Tenant A p95 = 200 ms
Tenant B p95 = 8 s

所以共享服务必须做 per-tenant breakdown。

14. 最终 fairness report

request share
token share
active time
KV share
TTFT/E2E per tenant
reject rate

这样“公平”才是可测量的工程目标。

学生闭环 — Multi-Tenant Fairness

硬件门槛：L0 模拟主路径；真实 server 增强 L1。

成本：0 元。

风险：默认 safe；涉及网络暴露时只在受控本地环境完成，先审计再开放。

能力目标

  • 从“单机 benchmark”升级到“用户看到的服务行为”。
  • 用 tail/SLO/capacity/fairness/exposure 约束系统，而不是只追总 tok/s。
  • 能通过 trace/metrics 解释一个服务为什么好用或不好用。

小实验 / 反馈

做 Experiment 68：fairness model；有多用户服务时做 Experiment 69：real tenant report。

教材补全：公平不是“每人相同请求数”

先选公平对象

公平对象适合解决局限
active slots防止一个租户占满并发长请求仍可能长期占用
generated tokens控制 decode work不反映 prompt/prefill 与 KV
prompt tokens控制 prefill 压力不代表长 decode
KV/context保护显存容量调度实现更复杂
weighted share区分不同优先级要处理 starvation

Worked Example：一个“请求配额”如何被轻易绕过

policy:
10 requests / minute

Tenant A:
10 × 32 output tokens

Tenant B:
10 × 4096 output tokens

两者请求数完全一样，但 decode work 相差约 128 倍。Request-count quota 只约束 API 行为，不等于约束 GPU 消耗。

Work-conserving 是什么？

公平调度不应该在其他租户没有工作时故意让 GPU 空转。典型思想：

有竞争时：
按 quota/share 限制

没有竞争时：
允许借用空闲容量

这样既能保护小租户，又不会永久牺牲利用率。

Starvation 与 Aging

如果高优先级请求持续不断，低优先级可能永远排不到。常见补救思想是让等待越久的工作逐渐提高有效优先级，或者保留最低服务份额。

公平性要和 SLO 一起测

不要只报告总吞吐。至少按 tenant 分开看：

TTFT p95
E2E p95
completed requests
generated tokens
reject rate
queue wait

Decision Rule

先说明“公平分什么”，再谈 quota。如果 workload 的资源成本差异很大，单一 request-count quota 几乎一定不够。
