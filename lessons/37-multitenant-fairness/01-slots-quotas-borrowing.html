Multi-Tenant Fairness — “每人两个请求”为什么一点都不公平？

1. Request 不是统一成本单位

Tenant A:
2 requests × 1000 output tokens

Tenant B:
2 requests × 50 output tokens

HTTP 请求数一样。

GPU 工作量完全不一样。

公平应该先问：你要公平分什么资源？

2. LLM 的资源至少有这些

slot time
prompt compute
decode tokens
KV memory
context capacity
queue time

3. Toy：两 slots

10 tok/s per slot

A：

A1 = 100 tokens
A2 = 100 tokens

B：

B1..B4 = 10 tokens each

4. 看请求数

A = 2/6 = 33.3%
B = 4/6 = 66.7%

似乎 B 请求更多。

5. 看 output work

A = 200/240 = 83.3%
B = 40/240  = 16.7%

完全反过来了。

6. Global FIFO

如果顺序：

A1 A2 B1 B2 B3 B4

两个 slots 先被：

A1 + A2

占满 10 秒。

B：

mean wait = 10.5 s
p95 wait  = 11 s

但 GPU slot utilization：

100%

吞吐很好，公平性很烂。

7. 每 tenant 最多 1 active

开始：

A1 + B1

B 很快跑完：

mean wait = 1.5 s
p95 = 3 s
last B done = 4 s

但 A2 必须等 A1 完成。

结果：

makespan = 20 s
slot utilization = 60%

公平了，但浪费硬件。

8. Work-conserving borrowing

规则：

A/B 都有等待：
每人最多 1 slot

B 已经没活：
A 可以借空闲 slot

结果 B 仍然：

mean wait = 1.5 s

A2 可以在 4 秒开始：

makespan = 14 s
utilization ≈ 85.7%
公平和高利用率不是只能二选一，但 scheduler 必须显式设计。

9. 为什么 token quota 比 request quota 好一点？

例如：

每用户 max output = 512
每天 100k generated tokens

至少比：

每天 100 requests

更接近真实资源。

10. 但 token 也不是完美成本

1000 prompt tokens

和：

1000 decode tokens

硬件路径不一样。

长 context 还会吃更多 KV。

11. 所以 quota 可以是多维的

max concurrent
max prompt
max output
max context
token budget
KV budget
priority weight

12. Priority 也有坑

如果：

high priority 永远优先

而 high priority 一直有请求：

low priority 永远跑不到

这叫 starvation。

13. 不能只看 global p95

整体：

p95 TTFT = 500 ms

可能隐藏：

Tenant A p95 = 200 ms
Tenant B p95 = 8 s

所以共享服务必须做 per-tenant breakdown。

14. 最终 fairness report

request share
token share
active time
KV share
TTFT/E2E per tenant
reject rate

这样“公平”才是可测量的工程目标。
