Safe Upgrade / Rollback — 新版本快 20%，为什么我还是可能拒绝它？

1. Release 不是只看 version

runtime SHA
model SHA
config
workload
quality
SLO

这些一起才是 release 身份。

2. 先保住 baseline

不要：

把旧 llama-server 覆盖掉
把旧 GGUF 覆盖掉
然后再开始测试

否则 candidate 一坏，你没有真正的 rollback。

Known-good artifact 必须在升级前就可恢复。

3. 门槛必须先写

例如只是教学 policy：

ready <= 8s
first inference <= 9s
TG >= baseline
PPL ratio <= 1.02
TTFT p95 <= 500ms
SLO compliance >= 99%

这些值不是万能标准。

重点是：

先写
再跑 candidate

4. Good Candidate

TG:
50 → 54 tok/s

PPL:
5.0 → 5.05

TTFT p95:
400 → 450 ms

SLO:
99.5% → 99.3%

在这个 synthetic policy 下：

ACCEPT

5. Fast-but-Bad Candidate

TG:
50 → 60 tok/s

很好看。

但是：

PPL:
5.0 → 5.2

TTFT p95:
400 → 900ms

SLO:
99.5% → 92%

结果：

ROLLBACK
性能赢不能覆盖质量门和用户 SLO 失败。

6. Rollback 不是再 restart 一下

Candidate：

runtime B
model B
config B

Rollback 必须恢复：

runtime A
model A
config A

并验证 hashes。

7. 恢复身份后还没结束

还要：

/health ready
+
smoke inference

否则只是“文件看起来换回去了”。

8. Rollback 自己也可能坏

旧 binary 被覆盖
旧 model 被删
config 被改写
port 还被占
persisted state 不兼容

所以 rollback path 应该提前试过。

9. Runtime upgrade 和 model upgrade 要分开说

commit A → B

和：

Q8 → Q4

不是同一种变化。

如果一次全换：

runtime + model + config

可以叫 release comparison，但不要冒充 one-variable causal A/B。

10. Failed candidate 也要留 Evidence

Rollback 后保留：

candidate logs
manifest
PP/TG
PPL
serving trace
gate result

不然下次你只知道：

“好像以前升级失败过”

11. 发布流程

known-good baseline
→ policy
→ candidate identity
→ readiness
→ smoke
→ performance
→ quality
→ SLO
→ ACCEPT
     or
  ROLLBACK
→ rollback identity
→ readiness
→ smoke

这就是本地 LLM 也值得有的 release discipline。
