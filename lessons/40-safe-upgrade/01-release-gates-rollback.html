Safe Upgrade / Rollback — 新版本快 20%，为什么我还是可能拒绝它？

1. Release 不是只看 version

runtime SHA
model SHA
config
workload
quality
SLO

这些一起才是 release 身份。

2. 先保住 baseline

不要：

把旧 llama-server 覆盖掉
把旧 GGUF 覆盖掉
然后再开始测试

否则 candidate 一坏，你没有真正的 rollback。

Known-good artifact 必须在升级前就可恢复。

3. 门槛必须先写

例如只是教学 policy：

ready <= 8s
first inference <= 9s
TG >= baseline
PPL ratio <= 1.02
TTFT p95 <= 500ms
SLO compliance >= 99%

这些值不是万能标准。

重点是：

先写
再跑 candidate

4. Good Candidate

TG:
50 → 54 tok/s

PPL:
5.0 → 5.05

TTFT p95:
400 → 450 ms

SLO:
99.5% → 99.3%

在这个 synthetic policy 下：

ACCEPT

5. Fast-but-Bad Candidate

TG:
50 → 60 tok/s

很好看。

但是：

PPL:
5.0 → 5.2

TTFT p95:
400 → 900ms

SLO:
99.5% → 92%

结果：

ROLLBACK
性能赢不能覆盖质量门和用户 SLO 失败。

6. Rollback 不是再 restart 一下

Candidate：

runtime B
model B
config B

Rollback 必须恢复：

runtime A
model A
config A

并验证 hashes。

7. 恢复身份后还没结束

还要：

/health ready
+
smoke inference

否则只是“文件看起来换回去了”。

8. Rollback 自己也可能坏

旧 binary 被覆盖
旧 model 被删
config 被改写
port 还被占
persisted state 不兼容

所以 rollback path 应该提前试过。

9. Runtime upgrade 和 model upgrade 要分开说

commit A → B

和：

Q8 → Q4

不是同一种变化。

如果一次全换：

runtime + model + config

可以叫 release comparison，但不要冒充 one-variable causal A/B。

10. Failed candidate 也要留 Evidence

Rollback 后保留：

candidate logs
manifest
PP/TG
PPL
serving trace
gate result

不然下次你只知道：

“好像以前升级失败过”

11. 发布流程

known-good baseline
→ policy
→ candidate identity
→ readiness
→ smoke
→ performance
→ quality
→ SLO
→ ACCEPT
     or
  ROLLBACK
→ rollback identity
→ readiness
→ smoke

这就是本地 LLM 也值得有的 release discipline。

学生闭环 — Safe Upgrade / Rollback

硬件门槛：L0 模拟/设计主路径；真实服务或 Linux/NVIDIA 机器是增强。

成本：0 元。

风险：safe；不通过危险电气/固件修改来“制造”故障。

能力目标

  • 把长期运行问题拆成可观察、可复现、可回滚的工程问题。
  • 区分 startup / steady state / failure recovery / energy 等不同系统边界。
  • 任何优化或升级都保留 exact identity 与 rollback/evidence。

小实验 / 反馈

做 Experiment 74：release-gate model；真实环境做 Experiment 75：real rollback。

Retrieval Practice

  1. 为什么“新版本能启动”不是升级 PASS？
  2. 升级前必须固定哪些 model/workload/quality/SLO Evidence？
  3. rollback 如果没有 exact old build/artifact，还算真正 rollback 吗？
  4. 什么时候应该因为性能变快但质量回退而拒绝升级？

完成证据

写一个 release gate：旧/新 exact version、build flags、model hash、benchmark/quality/SLO threshold、rollback artifact；模拟一次 FAIL 并回滚。

如何选择 / 迁移

换 OS、runtime 或 GPU 后，先重建 timeline + identity + measurement boundary，再判断“更快/更稳/更省电”是否成立。

教材补全：升级不是“新版本能启动”

升级改变的变量远比版本号多

runtime version
backend/kernel selection
model loader
quant implementation
default flags
scheduler
API behavior
memory allocator
driver interaction

因此升级必须把“功能正确、性能、质量、资源占用、接口兼容”分开验。

一个最小 Release Gate

Gate例子
startup模型能加载并 Ready
correctness关键 API/模板行为符合预期
quality固定 corpus / prompts 不出现不可接受退化
performancePP/TG/TTFT 不越过阈值
resourceVRAM/RAM/KV 不产生新 hard fail
operationsrestart/metrics/logging 仍可用

Worked Example：TG +8% 但不能发布

old:
TG 50 tok/s
PPL 6.4
VRAM 20 GiB

new:
TG 54 tok/s
PPL 7.8
VRAM 23.8 GiB

如果你的质量 gate 要求 PPL 不超过既定阈值，或 24 GiB 卡必须保留 KV headroom，那么“更快”仍然不能发布。

Rollback 必须提前设计

真正的 rollback 不是“出问题以后再想办法装旧版”，而是发布前已经知道：

old binary/container
old config
old model artifact
old command/flags
rollback trigger
rollback verification

一次只升级一个语义变量

同时升级 driver、runtime、model、quant、prompt template，会让任何回归都无法定位。必要时可以做大升级，但必须承认它不适合根因归因。

Decision Rule

Release = 所有必要 gate 通过；Rollback = 已验证的恢复路径。“能启动”和“跑分更高”都不够。

Retrieval Practice

  1. 为什么 runtime 升级可能改变质量，而不只是速度？
  2. 为什么 rollback 需要固定旧 model/config，而不只是旧 binary？
  3. 哪些指标应该成为 hard gate，哪些只是 preference？
  4. 为什么一次改五个变量会破坏回归诊断？

Release Packet：升级前就把“拒绝条件”写死

每次 candidate 至少保存：

  • baseline/candidate exact runtime、model、config；
  • 变更说明与 intentional variable；
  • startup/readiness/smoke；
  • PP/TG/TTFT/SLO 等性能结果；
  • quality gate 与 raw outputs；
  • VRAM/RAM/resource delta；
  • rollback artifacts/hash 与验证结果；
  • ACCEPT / ROLLBACK 的具体触发条款。

Worked Example：Candidate 自己 PASS，但 Rollback 未验证

如果新版本所有性能/质量 gate 都通过，但旧 binary/model/config 已无法恢复，严格意义上 release 仍缺一项 operational safety evidence。对于高风险或长期服务场景，应先证明 rollback path，而不是把“应该装得回去”当证据。

Release 状态机

CANDIDATE
→ GATES-PASS
→ ROLLBACK-VERIFIED
→ ELIGIBLE-FOR-RELEASE
→ HUMAN RELEASE

any hard gate fail
→ ROLLBACK
→ verify baseline functional state

这不是要求家庭用户搭复杂平台，而是让升级有明确退出路线。

Failure Recovery

  • candidate 启动失败：保存日志，恢复 baseline，不边修边覆盖。
  • 质量失败：即使速度大涨也 rollback。
  • rollback 后 health 200 但 smoke 失败：继续视为未恢复。
  • 多个变量一起换：结论降级为 release/system comparison，不做单因素归因。

What this lesson does NOT prove

通过一套 release gate 不证明 candidate 对所有模型、请求形状和未来 driver 都没有问题。Gate 只对你明确覆盖的 deployment contract 有效。
