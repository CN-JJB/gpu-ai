GPU Memory & Tiling · Lesson 03 · L0 + optional L2

为什么 GPU 要把数据搬到片上再算？

上一节你看到 scheduler 靠很多 ready warp/wavefront 隐藏等待。这一节再往里走一步：如果同一份数据会被用很多次，最好的等待不是“藏起来”，而是尽量别反复去远处拿。

真实问题

LLM 明明做了海量矩阵乘，为什么高性能 kernel 还要费劲设计 tile、shared memory/LDS 和 register fragment？直接每个 thread 从显存读自己需要的数据不行吗？

今天只记一条主线

global VRAM/HBM→ shared memory / LDS→ registers→ math

这不是说数据永远必须按这条路走，而是高 reuse kernel 常用的层级：远处加载一次，近处使用很多次。

1. Registers：最快的临时工作台，但每个人桌面都很小

一个 thread 的 accumulator、循环变量和中间结果通常放 registers。NVIDIA registers 在 SM 上，AMD 的 VGPR/SGPR 等也属于 CU 上的 register resources。

好处很直接：结果留在 registers，就不用为了下一条乘加再去 shared/global memory 找回来。

但 register file 是有限的。每 thread 占得越多，同一个 SM/CU 能同时容纳的 threads/warps/wavefronts 就可能越少。

这就是上一节的 occupancy trade-off 第一次变成“看得见的东西”。

2. 一个反直觉坑：少用 registers 不一定更好

你可能会想：那就强迫编译器少用 registers，换更高 occupancy。

问题是装不下的值可能 spill。

  • CUDA：spill 常进入 local memory。这里的 local 指 thread-local 作用域，不表示物理上就在芯片旁边；它走 device/global-memory 路径。
  • AMD：类似压力可进入 private/scratch storage；ROCm profiler 甚至有 scratch-memory trace。

所以“occupancy 提高了”同时可能发生“每个 thread 多了高延迟 memory traffic”。只盯 occupancy 会把优化方向带反。

3. Shared memory / LDS：一张 block 内共享的工作台

如果一群 threads 都需要同一批数据，就可以合作把它从 global memory 搬到片上的 shared memory / LDS。

cooperative global load→ shared/LDS tile→ many reuses

NVIDIA Best Practices 直接用矩阵乘说明这个模式；AMD HIP performance guide 也把 tiled matrix multiplication 作为 shared memory/LDS data reuse 的典型用途。

4. Tiling：为什么一块数据可以“买”很多次计算？

考虑 C=A×B。最朴素的想法是：每个 output thread 自己沿 K 维循环，每次都从 global memory 拿一个 A 和一个 B。

但一个 A 元素往往会被同一 output tile 的很多列使用；一个 B 元素也会被很多行使用。

假设 tile width = 16：

  • block 合作加载 16×16 的 A tile；
  • 再加载 16×16 的 B tile；
  • 这两块数据在 shared/LDS 里供 16×16 个 output threads 重复使用；
  • 每个 thread 在 register accumulator 里完成一段 dot product。

概念上，一份 input tile 不再为每个 output 重复从 global 搬，而是搬一次、重用约 16 次。

5. L0：只数“要搬多少次”，先不碰真实 GPU

对 N=1024 的 FP32 方阵 GEMM，忽略 cache/broadcast，只数算法级 input-load requests：

方案threads/blockshared/blockinput load requests近似 AI
naive—02,147,483,6480.250 FLOP/B
tile 8640.5 KiB268,435,4561.992 FLOP/B
tile 162562 KiB134,217,7283.969 FLOP/B
tile 3210248 KiB67,108,8647.877 FLOP/B

tile 16 在这个简化模型里把 input-load requests 降到 naive 的 1/16。

这不是“真实显存读取量”。cache、broadcast、coalescing、prefetch 和编译器都会改变真实 transaction/DRAM bytes。这个实验只验证 reuse 的算法上限。

6. 为什么不直接 tile 1024？

因为片上资源不是无限的。

tile 变大通常让 reuse 变好，但同时会增加：

  • threads per block，或者每 thread 的工作量；
  • shared memory/LDS footprint；
  • register accumulators；
  • synchronization 与 layout 复杂度。

结果可能是 resident blocks 变少、occupancy 下降，甚至整个 GPU 同时没有足够多 output tiles 可跑。

NVIDIA 的 GEMM performance guide 把它概括成一个很实用的 trade-off：larger tile 更高效，但 smaller tile 可以提供更多 tile-level parallelism。

7. Coalescing 和 Tiling 是两门不同的生意

Coalescing

问：一批相邻 threads 的 global addresses 能不能合成少量宽 transactions？

解决“每一次搬运划不划算”。

Tiling / reuse

问：同一份远端数据到底要搬回来几次？

解决“总共要搬多少次”。

一个 kernel 可以 coalescing 很漂亮，却仍然因为重复读取太多而 memory-bound；也可以 reuse 很高，但 cooperative load 地址很烂，把 bandwidth 浪费掉。

8. Shared memory/LDS 也会堵车：bank conflicts

shared memory/LDS 并不是一个“无限端口 SRAM”。它被组织成 banks，以便并行访问。

如果一个 warp/wavefront 的多个访问撞到同一 bank 的不同地址，硬件可能需要序列化。

所以：

global memory layout 要考虑 coalescing，shared/LDS layout 要考虑 bank conflicts。

具体 bank 数、映射和广播规则随架构变化，不能把 NVIDIA 某代规则硬套 AMD。

9. 现在可以解释高性能 GEMM 为什么 occupancy 不一定高了

CUTLASS 的 GEMM 层级非常有代表性：

global tile→ threadblock shared tile→ warp fragment→ register accumulator

大的 accumulator 和 double buffering 会吃 registers/shared memory，所以这类 kernel 的 occupancy 可能并不高。

但只要换来了更高 data reuse、更好的 ILP、software pipelining 和更少 global traffic，总性能仍可能更高。

这和本地 LLM 有什么关系？

  • Linear / GEMM：weights 和 activations 被分 tile，尽量在片上重复使用后再丢弃。
  • Attention：tile 设计决定哪些 Q/K/V 或中间值能留在片上，而不是反复写回/读回 global memory。
  • Quantized kernels：packed weights、scale、dequantized fragments、accumulators 都会形成 register/shared/global trade-off。
  • Kernel fusion：价值之一就是让中间结果留在 registers/shared memory，更少往 global memory round-trip。

如何调查一个 kernel？

  1. 先看 global memory 中最贵的数据是什么。
  2. 看一个 tile 被重复使用多少次。
  3. 检查 loads/stores 是否 coalesced。
  4. 看 shared memory/LDS per block。
  5. 看 registers/VGPR/SGPR 与 spill/scratch。
  6. 看 occupancy，但不要把它当成绩。
  7. 检查 bank conflicts。
  8. 最后只认真实 throughput + profiler evidence。
