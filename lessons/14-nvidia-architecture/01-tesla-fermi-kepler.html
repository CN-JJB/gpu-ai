NVIDIA Architecture · 1/5 · L0→L1

NVIDIA 架构主线（一）：Tesla / G80 → Fermi → Kepler

这三代建立了今天 NVIDIA GPU 编程最底层的语言：统一可编程执行、SIMT、warp/SM、shared memory、cache、latency hiding、warp 内通信与并发工作队列。目标不是背年代，而是看清“现代 CUDA 为什么长成这样”。

Prerequisite Check

  • 知道 GPU 从固定功能走向可编程/统一执行；如果不熟，先回到 Lesson 01。
  • 不要求会 CUDA。看到 thread、warp、SM 时先把它们理解为“工作 → 成组调度 → 执行资源”的层级。

真实问题：为什么一张老 NVIDIA 卡不能只看 CUDA Core 数？

二手市场最常见的误判之一，是把不同年代的“核心数量”横向比较。架构改变了每个 SM 如何调度、如何访问片上存储、支持什么精度、能否并发、软件栈还能否使用。即使两个 SKU 的核心数接近，实际可用能力也可能属于完全不同的时代。

1. Tesla / G80：从图形流水线跨到 throughput computer

G80/Tesla 的历史意义不在于今天还值得买，而在于统一可编程处理器把图形 shader 与通用并行计算放进同一类执行资源。CUDA 随后把这种硬件暴露成可直接编程的计算平台。

program view                 hardware view
Grid                         GPU
└─ Block                     └─ SM
   └─ Threads                   └─ warps of threads

SIMT 可以先粗略理解为：程序员写很多独立 thread，硬件把它们成组调度。这样既保留线程式编程表达，又用成组执行获得吞吐。

为什么 shared memory 从一开始就重要？

如果每个 thread 都不断去高延迟显存取同一批数据，大量并行核心会被数据等待拖住。block 内共享的低延迟片上存储，让线程可以先协作搬一块数据，再多次复用。

naive:
thread → DRAM → compute → DRAM → compute

reuse:
threads cooperate: DRAM → shared tile
                    ↓
              many calculations

今天 GEMM、attention、reduction 的高性能 kernel 仍然大量依赖“分块搬运 + 片上复用”这个思想。

2. 第一代通用 GPU 的痛点：可编程不等于好用

有大量线程之后，科学计算和更复杂的通用 workload 很快暴露出几个问题：

  • 不规则内存访问很昂贵；
  • cache hierarchy 还不够成熟；
  • 双精度、IEEE 行为与可靠性需求更高；
  • 多个 kernel/数据传输需要更好的重叠；
  • 大规模计算需要更完整的地址空间与错误保护。

这告诉你一个长期有效的规律：“能执行 kernel”只是入场券；内存、调度、数值与可靠性共同决定计算平台成熟度。

3. Fermi：把 GPU 按 general-purpose compute 重新设计

片上存储层级更像一台真正的计算机

registers
   ↓
shared memory / L1
   ↓
shared L2
   ↓
GDDR DRAM

Fermi 引入更成熟的 cache hierarchy，并让 shared memory 与 L1 的片上容量可以按 workload 取舍。显式管理和硬件自动缓存开始共同工作。

为什么 cache 不是 shared memory 的替代品？

机制优势代价
shared memory程序明确控制布局、复用与协作要自己设计 tile、同步、避免冲突
cache自动捕获局部性，对复杂访问更省心命中与替换不完全由程序控制

高性能 kernel 往往不是二选一，而是让寄存器、shared、cache 各自承担适合的部分。

Fermi 为什么被 HPC 看重？

更成熟的 FP64、ECC、64-bit addressing、并发执行能力等，让 GPU 不再只是“便宜但语义弱的加速器”。对本地 LLM 初学者而言，重点不是去买 Fermi，而是理解：数据中心/计算架构经常会为了数值、可靠性和并发牺牲一部分纯图形性价比。

4. Kepler：执行资源变宽以后，喂不饱怎么办？

Kepler 把单个 SMX 做得更宽。硬件有更多执行槽并不自动等于更高性能，因为 scheduler 还必须找到足够的可运行工作。

more execution resources
+ not enough ready work
= idle slots

TLP：用更多 warp 隐藏等待

Thread-Level Parallelism 的直觉是：warp A 在等内存时，scheduler 切去运行 warp B/C/D。GPU 不一定让单个内存访问变快，而是通过大量可运行工作把等待藏起来。

ILP：同一个 thread/warp 也能提供独立工作

Instruction-Level Parallelism 指同一条执行流里有互不依赖的指令。它解释了为什么 occupancy 不是越高越好：如果每个 warp 已经能提供很多独立工作，更低 occupancy 也可能获得很好吞吐。

纠偏：Occupancy 是资源/调度状态指标，不是性能分数。100% occupancy 的 kernel 完全可能比 60% occupancy 更慢。

5. Kepler 的 warp shuffle：为什么它影响到今天的 softmax/reduction？

warp 内线程如果想交换值，早期常借助 shared memory 并同步。shuffle 允许 lane 之间直接交换 register value。

shared path:
reg → shared → sync → shared → reg

shuffle path:
reg(lane A) ↔ reg(lane B)

这对 reduction、prefix 操作、warp-local 数据交换很有价值。现代 attention/softmax kernel 的具体实现早已更复杂，但“尽量让数据停留在更近的地方”仍是核心思想。

6. Hyper-Q / Dynamic Parallelism：并发和表达能力不是免费性能

GK110 上的 Hyper-Q 增加独立工作队列，减少 host 侧不同 stream/process 被窄队列人为串行化的情况。Dynamic Parallelism 则允许 GPU kernel 发起新的 kernel 工作。

两者都说明 NVIDIA 在解决“GPU 不只是运行一个巨大 kernel”的问题。但你必须记住：

  • 更多队列只有 workload 真能并发时才有价值；
  • device-side launch 仍有开销；
  • 更强表达能力不代表每个程序都会变快。

Worked Example：为什么同为 Kepler 也不能只写“Kepler 支持 X”

同一 architecture family 内可以有不同 die / SKU / 市场定位。某些功能只存在于特定芯片或计算产品线。以后读规格时应写成：

architecture family
→ exact GPU chip / SKU
→ exposed feature
→ current driver/runtime support
→ target application's backend support

而不是从一篇架构白皮书直接推导“所有同代消费卡都支持”。

三代留下来的核心观念

阶段主要问题留下来的机制今天怎么用
Tesla/G80图形执行资源过度固定统一可编程 GPU + CUDA/SIMTthread/warp/SM 是后续理解入口

Why it matters：和本地 LLM 的真正连接

  • GEMM/attention tile：shared memory 与寄存器复用思想直接延续。
  • reduction/softmax：warp-level communication 仍是重要工具。
  • decode：大量线程和调度并不能消除显存带宽/访存等待，只能在有足够并行工作时隐藏一部分延迟。
  • 旧卡判断：架构机制、显存容量、带宽和当前 CUDA/runtime 支持必须同时看。
  • 数据中心 vs 游戏卡：计算产品可能为了 ECC、FP64、容量/互联等做不同取舍。

常见误区

  • “Kepler 核心更多，所以一定比 Fermi 快很多”：要看 workload、时钟、带宽、资源利用和软件。
  • “occupancy 越高越好”：它只是一个约束维度。
  • “有 cache 就不用 shared memory”：显式可控复用仍有价值。
  • “架构白皮书功能 = 所有 SKU 功能”：必须落到 exact SKU。

小实验与预期观察

完成 Experiment 23：NVIDIA generation feature traps。如果有 NVIDIA GPU，再做 Experiment 24：real NVIDIA capability inventory。

本课不要求得到某个“正确性能数字”。你应该得到的是一张证据表：哪些能力属于 architecture claim，哪些属于 SKU fact，哪些属于当前 runtime observation。

无对应老卡怎么办？

不买老卡。L0 主路径使用白皮书、规格页和 capability inventory。历史硬件的学习目标是建立因果模型，不是收藏。手里只有现代卡时，照样可以观察它仍然暴露的 thread/warp/SM、shared memory、cache 等后代概念。

排错思路

  • 工具显示的字段名与白皮书不同：先确认工具版本和字段语义，不做词面硬映射。
  • 某功能在 architecture docs 出现，但你的卡/driver 看不到：检查 exact SKU、compute capability、driver/runtime support。
  • benchmark 没比预期快：先判断是 compute、memory、launch、同步还是 host bottleneck，不从“代际更先进”直接推性能。

Retrieval Practice

  1. Tesla/G80 的“统一”为什么比单纯核心数量更重要？
  2. Fermi 的 cache hierarchy 为什么没有让 shared memory 失去价值？
  3. 用自己的话解释 GPU 如何用 TLP 隐藏内存延迟。
  4. 为什么 occupancy 100% 不是性能目标？ILP 在这里扮演什么角色？
  5. warp shuffle 为什么可以减少部分 reduction 的 shared-memory 往返？
  6. 同为 Kepler，为什么不能从 family 名称直接推断某个 SKU 支持 Hyper-Q/Dynamic Parallelism？
  7. 如果你看到一张 Kepler 旧卡非常便宜，除了价格至少还要检查哪些“当前事实”？

Decision Rule

你可以用 Tesla→Fermi→Kepler 解释现代 CUDA 执行/内存模型的来源；你不能因为某张旧卡具有这些历史机制就推断它今天适合本地 LLM。购买结论必须继续检查容量、带宽、precision/kernel、driver/runtime/backend、功耗和实际 benchmark。
