Local Inference · Lesson 07 · L0–L2

第一次跑本地 LLM，怎样证明它真的跑在你以为的硬件上？

看到模型吐出一句话，只证明“某个程序运行了”。课程真正要你证明的是：哪一个 backend、哪一份模型、哪条 CPU/GPU 路径、什么 context/offload 条件，以及结果能不能被别人复现。

Prerequisite Check

建议先完成 Foundation 01–02，以及 Lesson 05–06。你应会定位文件路径、记录 SHA256，并知道模型 fit 需要 weights + KV + buffers。没有 GPU 也可以继续：CPU baseline 就能完成本节证据闭环。

真实问题

我已经能聊天了。但它到底用了 CPU、CUDA、HIP 还是 Metal？为什么别人同一张卡比我快两倍？

这次先收集四个身份证

runtime+ device+ model artifact+ run config

1. Runtime identity：你跑的是哪一版 llama.cpp？

llama-cli --version
llama-cli --help

保存 build/version/commit。CLI 参数会演进，所以课程不要求你死背某个 flag，而要求你在实验当天先读当前 --help。

2. Device identity：编译了 GPU backend，不等于这次 run 真用了 GPU

llama-cli --list-devices

然后再看 startup log 或 benchmark metadata。需要区分：

  • binary 支持 CUDA/HIP/Metal；
  • 系统发现了 GPU；
  • 本次模型实际 offload 到了 GPU；
  • 对应 kernels 真正在运行。

“CUDA build 成功”不是“GPU acceleration 已验证”。

3. Model identity：模型名字不够，artifact 要能指纹识别

同一 model family 可以同时存在 FP16、多个 GGUF quant、不同 revision。Evidence 至少保存：

  • repo + revision（若来自 Hub）；
  • local filename；
  • file bytes；
  • SHA256；
  • loader/benchmark 报出的 model/quant metadata。
# Linux
sha256sum model.gguf

# macOS
shasum -a 256 model.gguf

4. CPU-only 不是失败路径

没有独显也可以完成第一次真实 LLM 实验。CPU baseline 能先证明：

  • artifact 能加载；
  • tokenizer/chat template 工作；
  • runtime build 没问题；
  • Evidence 流程可复现。

之后 GPU 只是把 execution path 换成 CUDA/HIP/Metal，并比较同一模型的变化。

5. GPU layer offload：第一次理解 hybrid inference

llama.cpp 支持 CPU+GPU hybrid inference。概念上：

0 GPU layers→ 部分 offload→ 更多/全部 GPU residency

offload 增加通常意味着：

  • GPU/统一内存压力增加；
  • CPU 端模型工作减少；
  • CPU↔GPU 数据路径变化。

但不是 GPU layers 越多一定越快。如果显存紧张、传输路径差、KV placement 或 backend kernel 不理想，曲线可以很复杂。

6. 第一次成功可以自动 fit；benchmark 不行

当前 llama.cpp CLI 提供自动 fit 机制，适合第一次“尽量别 OOM”。但自动策略可能根据设备内存改变未固定参数。

First success

目标：加载、生成、不 OOM。

允许 auto-fit。

A/B Benchmark

目标：两个结果能比较。

context、offload、threads、KV type 等必须固定并记录。

7. Context 是功能参数，也是容量参数

上一节已经推导：

context ↑ → KV cache budget ↑

所以“GPU 层都塞进去了”不代表换成 32K context 后仍然能 fit。跑 benchmark 时必须记录实际 context。

8. Threads 也不是越多越好

CPU generation/prompt processing 的最佳 thread count 会受 physical cores、SMT、NUMA 与 memory bandwidth 影响。

如果把 thread 数从 8 加到 32 反而变慢，不要先怀疑模型，先检查 oversubscription 与 memory bandwidth。

9. 第一次 benchmark 为什么要分 PP 和 TG？

llama-bench 官方把测试拆成：

PP · Prompt Processing

批量处理 prompt，更接近 prefill。

通常更容易形成高并行、高 arithmetic intensity。

TG · Text Generation

逐 token 生成，更接近 autoregressive decode。

通常更受 weight/KV memory traffic 影响。

这正好把前面的 Roofline 课程接到真实 LLM。

10. 为什么只报一个 tokens/s 还不够？

llama-bench 的 pp/tg 是非常好的 backend baseline，但官方说明 benchmark timing 不包含 tokenization 和 sampling。

真实交互体验还包括：

  • model load time；
  • time to first token；
  • inter-token latency；
  • sampling；
  • server queueing/concurrency。

所以这节只建立“可复现 backend baseline”，不假装完成了服务端 benchmark。

11. NVIDIA / AMD / Apple 怎么迁移？

平台llama.cpp 常见 backend容量心智模型
NVIDIACUDA独显 VRAM + host RAM
AMDHIP/ROCm独显 VRAM + host RAM
Apple SiliconMetalCPU/GPU 共享 unified memory
无 GPUCPUsystem RAM

Apple 不能把“VRAM”概念机械照搬：CPU/GPU 使用的是 unified memory。但你仍然要问 model + KV + runtime 是否有足够 headroom。

12. 第一次真正有用的 Evidence

至少保存：

  • llama.cpp commit/version；
  • OS / CPU / RAM / GPU；
  • driver/backend；
  • model repo/revision/file SHA256；
  • quant/model size/parameter count；
  • context；
  • threads；
  • GPU layers/offload；
  • KV type；
  • PP t/s ± stddev；
  • TG t/s ± stddev；
  • raw benchmark JSON。

教材补全：第一次跑通的目标不是“看到文字”，而是确认执行路径

最小证据链

model artifact
+ runtime version/build
+ backend/device detected
+ exact command
+ model load log
+ generated output
→ reproducible first run

只截图一段回答，没有办法证明到底是 GPU、CPU 还是别的 backend 在工作。

Worked Example：为什么“显卡利用率 0%”不一定等于没用 GPU

短 prompt、短输出时，采样工具可能错过瞬时 GPU 工作；反过来，显卡有利用率也可能只是桌面/其他进程。更可靠的证据是 runtime backend log + device allocation + 可重复性能差异。

第一次本地推理应该固定什么？

model file/hash
context
prompt
max output
sampling
GPU offload / backend
threads
runtime build

否则第二次“更快/更慢”时你连变化来自哪里都不知道。

实验预期

  • 首次 cold load 通常比后续 warm load 更慢。
  • GPU backend 正常时，模型加载日志应能看到设备/层分配等证据。
  • CPU fallback 时仍可能成功生成文本，但性能和内存路径不同。

排错顺序

  1. 文件是否完整、格式是否被 runtime 支持。
  2. runtime 是否识别目标 device/backend。
  3. 显存/RAM 是否足够，是否发生意外 offload/fallback。
  4. 命令参数是否被当前版本接受。
  5. 最后再比较性能。

没有独显怎么办？

CPU 路径也能完成“artifact → runtime → command → output → evidence”学习闭环。以后换到 GPU，只是替换执行后端，不改变证据方法。

Decision Rule

“能生成文本”只证明功能路径部分成立，不证明 GPU 正在加速，也不证明性能、质量或稳定性达标。
