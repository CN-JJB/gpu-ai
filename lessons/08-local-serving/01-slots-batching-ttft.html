为什么单用户很快，八个人一起用却像卡住了？

上一节你测的是单机、单请求 backend baseline。服务器世界多了两个变量：谁能立刻进入模型执行，谁必须排队；以及多个 active sequence 能不能一起形成有效 batch。

Prerequisite Check

你应完成 Lesson 07，能证明一次本地推理的 runtime、device、model artifact 与 run config，并知道 PP/TG 不是同一个性能阶段。不会部署公网服务不影响本节；先把 server 当成“同时管理多个请求的本地进程”。

真实问题

我的模型单用户能 30 tok/s。为什么开 8 个客户端以后，不是每人 30 tok/s，也不是总共 240 tok/s？

先画 server，而不是先看 GPU

clients→ queue→ slots→ active batch→ model

current llama-server 明确支持 multi-user parallel decoding 和 continuous batching。

1. Client concurrency 和 server slots 不是同一个数字

假设：

client concurrency = 8
server slots = 4

客户端可以同时发 8 个请求，但 server 并不因此拥有 8 份独立 GPU。

更可能看到：

4 requests processing
4 requests deferred / waiting

current llama-server 的 metrics 里就有：

  • requests_processing
  • requests_deferred

“有 8 个并发客户端”不是“GPU 正在做 batch=8”。

2. Slot 到底是什么？

在这节里，把 slot 理解成：

server 可以同时维护一个 active request/sequence execution state 的容量单位。

它不是：

  • 一个 CUDA core；
  • 一个 SM；
  • 一个 warp；
  • 一个 CPU thread；
  • 一份完整模型副本。

多个 slots 最终仍然共享同一个模型和同一套硬件资源。

3. Queue 为什么首先伤 TTFT？

用户点发送以后，到看到第一个有用输出，大致经历：

queue+ prompt processing+ first decode= TTFT

所以 slots 一满：

即使 active request 的 decode t/s 没变，后排请求的 TTFT 也可以暴涨。

4. 现在必须把三个 latency 指标分开

指标问的问题
TTFT多久开始说第一句话？
ITL开始说以后，相邻 token 间隔多久？
E2E latency整个请求多久结束？

一个系统完全可能：

  • TTFT 很差，但开始生成后很流畅；
  • TTFT 很好，但 token 一个一个蹦得很慢；
  • 总吞吐很高，但单个用户等得更久。

5. 为什么普通 streaming client 不能直接说“我测了精确 ITL”？

OpenAI-compatible streaming 返回的是 SSE chunks。

一个 chunk：

  • 可能是空 delta；
  • 可能对应一个 token；
  • 也可能包含多个 token 对应的文本；
  • 还会受到 HTTP buffering 影响。

所以 Experiment 12 会记录：

first non-empty stream delta → TTFT proxy
mean non-empty stream gap     → client-visible cadence proxy

不把 chunk gap 冒充精确 token-level ITL。

6. Continuous batching 解决什么？

想象两个 active request：

  • A 只剩 8 tokens；
  • B 还要 32 tokens。

如果是“整批一起开始、整批一起换下一批”的静态思路：

A finished
B still running
C waits
slot is effectively wasted

continuous batching 的核心思想：

A finished
→ C enters
→ active set becomes B + C
→ 不必等 B 完成

Continuous batching 的关键不是“batch 很大”，而是 active batch 可以动态换人。

时间线模拟：Static batch 和 Continuous admission 差在哪？

8 个请求长度不同。Static 模式要等这一批最慢请求结束才开下一批；Continuous 模式则某个请求一结束就补入新请求。拖动 slots，看 queue 与 first-service wait 如何变化。

每行是一个请求；■ 表示正在占用 slot，虚线点表示已到达但还在 queue。时间单位为教学抽象。

边界：这里每个 active request 每 tick 都得到同样进度，不模拟真实 GPU batching efficiency、KV traffic 或 token-level scheduler。它只解释 admission/slot 机制。

7. 为什么 batch 更多人，总吞吐可能上升？

decode 单请求常常要反复读取大量 weights，却只为一个 sequence 做当前 token 的工作。

多个 sequence 一起跑时，模型执行更容易形成：

same model step→ more sequences served→ aggregate work ↑

这和前面的 Roofline 思维一致：硬件利用率可能提高，aggregate tokens/s 可能上升。

8. 为什么每个人反而可能“说得更慢”？

因为 batch step 本身也更重。

active batch ↑
→ one decode step takes longer
→ each user's next token may arrive later

于是服务端出现经典 trade-off：

aggregate throughput ↑，不代表 per-request latency ↓。

9. L0：8 个请求同时来，slots 越多会发生什么？

我们造一个抽象 decode server：

  • 8 requests 同时到达；
  • 每个要生成 32 tokens；
  • 一次 decode step 给每个 active request 产生 1 token；
  • active requests 越多，step time 会增长，但低于线性增长。

模型使用：

step_time(batch) = 1 + 0.22 × (batch - 1)

两个方向同时发生：

  • 更多 slots 减少 queue，首 token 等待下降；
  • 更多 active requests 让 step 变长，active-user cadence 变慢；
  • aggregate throughput 因 batch amortization 上升。

这三个指标不是同一个方向。

10. Continuous batching 的 L0 反例

6 个请求长度：

8, 32, 8, 32, 8, 32 tokens
slots = 2

不是因为 continuous batching “让 GPU 变强”，而是因为短请求结束后，空 slot 更快被新请求填上。

11. Concurrency 还有一张账：KV

Slice 05 已经推导：

KV baseline ∝ active sequences × cached tokens

所以 slots 从 1 增到 8，不能只看 throughput。

你同时增加了：

  • live sequence state；
  • KV capacity pressure；
  • KV traffic；
  • 潜在 memory-bandwidth 压力。

current llama-server 还有 unified KV、prompt cache 等机制，所以不能简单写成 slots × ctx = real KV。真实内存要测。

12. 哪些 metrics 真正能帮你判断 server？

current llama-server metrics 中特别有用：

  • requests_processing：现在多少请求在做；
  • requests_deferred：多少请求在等；
  • n_busy_slots_per_decode：一次 decode 平均有多少 busy slots；
  • predicted_tokens_seconds：server generation throughput；
  • prompt_tokens_seconds：prompt throughput。

这使你可以区分：

client 发了很多请求
vs
server 真形成了有效 batch

教材补全：Serving 的第一课是“单请求优化”与“多请求调度”分开

Worked Example：两个用户为什么会互相影响

单用户时 GPU 可以把大部分资源用于一条 sequence；两个用户同时来，server 可能进行 batching 或轮流推进 decode：

user A token
user B token
user A token
user B token
...

aggregate throughput 可能提高，但每个用户 token 之间的间隔也可能变长。

Slot 是逻辑调度资源，不等于 GPU core

不同 server 对 slot/request/sequence 的定义不同。要理解它控制的是“同时有多少活动序列/请求”，而不是把硬件 SM/CU 平均切成几份。

Batching 的两种收益

  • Prefill：更大矩阵可能提高 compute utilization。
  • Decode：把多个 sequence 的一步合并，有机会提高硬件利用率。

但代价通常是更高 KV、调度开销和单用户 latency。

实验预期

  • 并发从 1 增长时，总吞吐可能先升。
  • 继续加并发后，TTFT/ITL/p95 会恶化。
  • 显存/KV 可能成为比 compute 更早出现的硬门槛。

排错

  1. 固定 prompt/output 分布。
  2. 确认并发是客户端并发还是 server active slots。
  3. 同时记录总吞吐和每请求 latency。
  4. 检查 queue 是否已在增长。
  5. 检查 KV/VRAM 是否逼近上限。

无 server 环境怎么办？

用纸上时间线或小型并发模拟也能学会“queue / active / completion / batching”关系；不需要先拥有高端 GPU。

Decision Rule

Serving 优化不能只追 aggregate tokens/s。至少同时看用户 latency、queue、并发和 KV/VRAM。
