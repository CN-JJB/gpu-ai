Observability — GPU 100% 到底是好事还是坏事？

1. 单个指标不能直接当根因

GPU util = 100%

可能代表：

GPU 正在满负荷干有用工作

如果：

TTFT/ITL SLO 都正常
没有 errors
clock 正常
temperature 正常

那它甚至可能是你想要的状态。

先看用户症状，再看资源信号解释症状。

2. 四类信号

Latency
Traffic
Errors
Saturation

放到本地 LLM：

TTFT / ITL / E2E
req/s / tok/s
HTTP/OOM/SLO miss
queue / slots / KV / GPU / thermal

3. Case A：排队

TTFT ↑↑
requests_deferred ↑
GPU util ↑
clock 基本不变
ITL 基本不变

更合理的假设：

queue/admission pressure

不是：

GPU 突然坏了

4. 为什么 ITL 可以正常？

已经拿到 slot 的请求继续正常 decode。

真正倒霉的是：

还在 queue 里的用户

所以先伤 TTFT。

5. Case B：温度 / clock

temp:
70 → 88 C

clock:
1800 → 1200 MHz

ITL:
50 → 95 ms

这时：

thermal/power/clock throttling

变成值得验证的 hypothesis。

仍然不能只凭相关性就宣布根因。

6. Case C：VRAM 95%

23.0 / 24 GiB
23.1
23.0
23.1

但：

TTFT stable
ITL stable
no OOM
no growth trend

这不能叫 memory leak。

7. 真正 leak-like 的证据更像

同样 workload state
→ VRAM 一轮比一轮高
→ 不释放
→ 最后 OOM

还要结合 runtime allocator/cache 行为。

8. 低 GPU 利用率同样不能直接买新卡

可能卡在：

CPU
tokenizer
storage
host-device sync
tiny batches
network/client
scheduler

9. 时间线比截图强得多

12:00:00 TTFT 200  deferred 0  clock 1800 temp65
12:00:10 TTFT 300  deferred 2  clock 1800 temp68
12:00:20 TTFT 600  deferred 5  clock 1780 temp70
12:00:30 TTFT1200  deferred 9  clock 1780 temp72

你开始能看到事件一起怎么变化。

10. Metrics / Logs / Trace 各干什么？

Metrics:
趋势、率、饱和

Logs:
错误、异常、启动失败

Request trace:
每个用户请求时间线

三类 Evidence 互补。

11. Alert 不应该只是 GPU > 90%

更有意义：

TTFT p95 连续越 SLO
requests_deferred 持续增加
error rate 超限
health 不 ready
OOM 风险

然后 resource telemetry 帮你解释。

12. Incident Packet

release identity
workload
client trace
server metrics
GPU telemetry
logs
hypothesis
action
follow-up A/B

这比：

“昨天好像特别慢”

有用得多。
