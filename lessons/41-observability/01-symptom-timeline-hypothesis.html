Observability — GPU 100% 到底是好事还是坏事？

Prerequisite Check

开始前，你应该能读懂最基本的服务信号：latency、traffic、errors、saturation，并知道 GPU utilization、clock、temperature、queue、slot 与 KV 都只是观测信号，本身不是根因。

如果还不熟：先遵守一个规则：先写“用户看到了什么症状”，再把同一时间轴上的系统信号拿来解释。不要从某个单点指标直接跳到“GPU 坏了”“驱动有问题”这类结论。

真实问题

用户说“今天模型突然很慢”，同时你看到 GPU 100%。这个现象既可能是健康的满负载工作，也可能伴随 queue 堆积、thermal throttling、内存压力或错误重试。单个 dashboard 数字无法区分这些路径。

真正的问题是：怎样把用户症状、事件时间线和多类 telemetry 拼成可证伪的 hypothesis，并用下一条最有区分度的证据决定该查 queue、GPU、memory、thermal 还是软件变更？可观测性的目标是缩小原因空间，而不是堆更多图表。

1. 单个指标不能直接当根因

GPU util = 100%

可能代表：

GPU 正在满负荷干有用工作

如果：

TTFT/ITL SLO 都正常
没有 errors
clock 正常
temperature 正常

那它甚至可能是你想要的状态。

先看用户症状，再看资源信号解释症状。

学生闭环 — Observability / Incident Diagnosis

硬件门槛：L0 模拟/设计主路径；真实服务或 Linux/NVIDIA 机器是增强。

成本：0 元。

风险：safe；不通过危险电气/固件修改来“制造”故障。

能力目标

  • 把长期运行问题拆成可观察、可复现、可回滚的工程问题。
  • 区分 startup / steady state / failure recovery / energy 等不同系统边界。
  • 任何优化或升级都保留 exact identity 与 rollback/evidence。

小实验 / 反馈

做 Experiment 76：incident diagnosis cases；真实服务做 Experiment 77：real incident evidence。

  3. 为什么 incident timeline 要记录 config/deploy/temperature/queue 等变化点？
  4. 只有一个相关性图时，什么时候还不能声称因果？

完成证据

完成一个 incident report：symptom、timeline、至少三个 hypothesis、支持/反驳证据、最小复现/下一测量、最终结论与 non-claims。

如何选择 / 迁移

换 OS、runtime 或 GPU 后，先重建 timeline + identity + measurement boundary，再判断“更快/更稳/更省电”是否成立。

教材补全：可观测性不是“多装几个 Dashboard”

诊断链条

symptom
→ timeline
→ correlated signals
→ hypothesis
→ discriminating test
→ result
→ next hypothesis / fix

指标的价值在于帮助你区分假设，而不是让图表越多越专业。

Worked Example：TG 突然从 50 掉到 30

至少有多种候选原因：

A thermal/power throttle
B concurrency increased
C context grew / KV pressure
D CPU/RAM/swap interference
E backend/kernel changed
F another process using GPU

只看 GPU utilization 不能区分这些。你需要时间对齐的 clocks、power、temperature、active requests、context/KV、RAM/swap、runtime identity 等信号。

先记录事件，再看指标

重要操作应该进入时间线：

14:01 deploy new runtime
14:03 first request
14:08 concurrency test begins
14:12 TG degradation begins
14:13 thermal limiter appears

没有事件时间线，监控图很容易变成“事后看云彩猜天气”。

Golden Signals 在本地 LLM 中怎么落地

  • Latency：TTFT、ITL/E2E、tail。
  • Traffic：req/s、prompt/output tokens、active/queued。
  • Errors：HTTP/runtime/backend/driver failures。
  • Saturation：slots、KV/VRAM、GPU、RAM/swap、queue。

再加模型服务特有的 PP/TG、cache hit、context distribution 等。

不要让监控污染实验

高频采样、verbose logging、profile 工具本身可能增加 CPU/I/O 开销。正式 benchmark 要记录监控采样频率，并尽量保持 A/B 一致。

Decision Rule

一个好 dashboard 应该能回答“下一步该验证哪个假设”，而不只是告诉你系统很忙。

“GPU 100%”“VRAM 95%”只是 signal，不是 hypothesis。好 hypothesis 应该能被新 Evidence 推翻，例如“TG 下降来自 thermal throttle”就应预测 clock/limiter/temperature 与 workload 时间线存在一致关系。

Worked Example：TG 下降但 GPU util 仍 100%

至少同时检查：

  • clock/power/temperature 是否变化；
  • context/KV 是否增长；
  • active/queued request 数是否变化；
  • runtime/backend/model identity 是否刚升级；
  • CPU/RAM/swap 是否出现干扰；
  • 是否有其他 GPU process。

如果只有温度升高但 clock 不变、用户 latency 不变，就没有足够证据把高温宣布为根因。

Observability Evidence Packet

保存时间同步的 request metrics、system/GPU telemetry、关键 logs、deploy/config events 与监控采样配置。正式 A/B 中监控本身也要固定，因为更高采样频率和 profiler 可能改变系统负载。

Failure Recovery

  • 没有统一时间轴：先对齐时间戳，不凭截图顺序猜因果。
  • 指标互相矛盾：保留矛盾并设计下一项 discriminating test。
  • 只有一个异常点：先确认持续性/重复性，不立刻改系统。
  • 监控造成明显开销：降频或分离 profiling run，明确 measurement boundary。

What this lesson does NOT prove

相关信号不能自动证明因果。Observability 的目标是更快缩小假设空间；真正 root cause 仍需复现、对照或能够区分竞争假设的实验。
