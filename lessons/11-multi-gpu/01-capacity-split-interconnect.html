Slice 11 — 单机多 GPU：显存能合起来，速度为什么不能直接相加？

真实问题：两张便宜的 12 GiB 显卡，能不能当成“一张 24 GiB 显卡”？如果模型确实能跨两卡加载，为什么 tokens/s 有时几乎不涨，甚至下降？

本节目标：把三件经常被混在一起的目标拆开：装得下更大的模型、降低单请求延迟、提高多请求吞吐。

1. 先分清你到底想要什么

目标典型方法是否要求跨卡通信
装下更大的单模型layer/model split通常需要
降低一个请求的延迟tensor/row parallel 类并行高频需要
同时服务更多独立请求两张卡各放一份模型可基本避免

2. 2×12 GiB 不是一块连续 24 GiB VRAM

GPU0 local VRAM: 12 GiB
GPU1 local VRAM: 12 GiB

要让一个 20 GiB 左右的模型跨两卡运行，runtime 必须把权重、KV 或其他状态按策略分到不同 GPU。每张卡仍有自己的本地显存分配，还要留给 KV、workspace、通信缓冲、重复状态和 allocator headroom。

因此更准确的说法是：

aggregate capacity requires software partitioning
usable model payload < simple sum of advertised VRAM

3. 三种最重要的拆分方式

3.1 Replicas / Data Parallel 思路

GPU0: whole model  → request A
GPU1: whole model  → request B

它最擅长提高独立请求吞吐。缺点很直接：模型必须在每张卡上都装得下，所以它不能帮助“单个超大模型跨两张小卡”。

3.2 Layer / Pipeline Split

layers 0..15  → GPU0
layers 16..31 → GPU1

one token:
GPU0 compute → activation transfer → GPU1 compute

这类拆分的第一价值通常是容量聚合。对于单 token 路径，前半层算完后后半层才能继续，因此“层数各一半”并不等于“单请求延迟减半”。

3.3 Tensor / Row Parallel

same layer:
GPU0 computes shard A
GPU1 computes shard B
        ↓
collect / reduce / merge
        ↓
next layer

这类方式确实能在同一层里并行更多计算，但代价是频繁的数据交换和同步，因此对 GPU↔GPU 互联更敏感。

4. 给 Roofline 再加一层：Interconnect Roof

前面我们已经学过 compute roof 和 memory-bandwidth roof。多 GPU 后，还要加入跨卡通信：

T_N ≈ T_compute / N
    + bytes_on_critical_path / effective_link_bandwidth
    + T_sync
    + T_imbalance

Speedup 与扩展效率：

S_N = T_1 / T_N
E_N = S_N / N

如果跨卡通信占比很高，GPU 数量继续增加时，计算部分虽然变短，但通信和同步不会按同样比例消失，于是 scaling efficiency 会掉下来。

5. 一个纯教学的双卡例子

假设单卡每 token 需要 10 ms；双卡理想计算部分降为 5 ms；每 token 的关键路径需要跨卡搬 64 MiB；同步固定 0.2 ms。

有效 P2P 带宽通信时间双卡总时间相对单卡 speedup
8 GiB/s7.81 ms13.01 ms0.77×
16 GiB/s3.91 ms9.11 ms1.10×
32 GiB/s1.95 ms7.15 ms1.40×
64 GiB/s0.98 ms6.18 ms1.62×
128 GiB/s0.49 ms5.69 ms1.76×

同样两张 GPU，互联不同，结论可以从“更慢”变成“明显更快”。这些数字是教学模型，不是任何真实显卡的 benchmark。

6. P2P：能互相看见，不等于能高效互传

多卡 runtime 能枚举两张 GPU，只能说明设备存在。真正需要问：

  • GPU0 能否直接访问 GPU1 的显存？
  • 路径经过哪些 PCIe bridge / host bridge / NUMA 节点？
  • 单向和双向实际带宽多少？
  • collective 通信表现怎样？

如果没有有效的 direct P2P，某些实现会经过 host memory staging，性能会显著不同。

7. PCIe 插槽“看起来一样”也可能完全不同

物理 x16 长度不等于电气 x16。主板可能是 x16/x4、x8/x8，或者第二槽经过额外 bridge、另一 root complex，甚至另一 NUMA node。垃圾佬判断多卡价值前，必须把拓扑当成 Evidence，而不是看槽长度猜。

8. NVLink / xGMI 一类高速互联解决什么

它们能抬高 interconnect roof，减少跨 GPU 通信时间。但仍不能推出“线性扩展”：软件拆分策略、collective、同步、负载不均、GPU 型号差异依然存在。

9. 为什么 Prefill 和 Decode 要分开测

Prefill 往往有更大的矩阵计算，更容易摊薄一次通信成本；Decode 则是逐 token 的延迟敏感路径，通信/同步占比更容易放大。因此：

multi-GPU PP speedup ≠ multi-GPU TG speedup

真实实验必须同时记录 prompt processing 与 text generation。

10. 异构垃圾卡最容易踩的坑

Layer split 有时可以给强卡多放一些层、弱卡少放一些层；但同步式 tensor parallel 会让快卡等待慢卡或慢链路。混卡不是不能用，而是更需要测量。

11. 买第二张卡前的判断顺序

  1. 目标是容量、单请求延迟，还是多用户吞吐？
  2. 模型是否本来就能放进一张卡？
  3. 主板两个槽的实际 lane / root / NUMA 拓扑是什么？
  4. P2P 是否可用？实测带宽多少？
  5. runtime 支持哪种 split？
  6. 单卡 PP/TG 基线是多少？
  7. 双卡同配置 PP/TG 是多少？
  8. 速度收益是否值得第二张卡的功耗、散热、插槽和电源成本？

12. 迁移到 Apple Silicon 时哪些概念保留

Apple Silicon 的统一内存 SoC 不能机械套用“两块独立 VRAM 经 PCIe P2P 相连”的模型。但可迁移的问题仍然成立：总容量、有效带宽、工作是否跨设备边界、并行策略和同步代价。

结论：多 GPU 不是“把显存和算力做加法”，而是先分工作，再为跨设备边界付通信和同步成本。垃圾佬真正要买的不是“第二张卡”，而是一个经过拓扑、P2P 和 workload 验证的系统方案。

学生闭环：学完这一页你要能做什么

硬件门槛：L0；真机增强路径 L3（两张可用 GPU）。

成本：教学主路径 0 元；不要求为了本课购买第二张卡。

风险：safe。只做模拟、只读 topology 与 benchmark，不刷 BIOS、不改电压。

替代路径：没有双卡就完成 Experiment 17；真实双卡 Experiment 18 留到以后。

能力目标

  • 把“总显存变大”和“单 token 更快”分成两个不同问题。
  • 解释模型切分为什么会引入跨 GPU traffic，以及 PCIe / NVLink / XGMI 为什么会改变收益。
  • 双卡缩放差时，先检查 split、P2P/topology、每卡工作量和通信，而不是直接怪某张卡。

小实验 / 反馈

先做 Experiment 17：multi-GPU interconnect roof model。有真实双卡时再做 Experiment 18：real multi-GPU scaling。

正确观察不是“2 张卡 = 2 倍速度”，而是把 capacity fit、compute work、communication bytes、link bandwidth 分开记账。

Retrieval Practice

  1. 为什么两张 24 GiB 卡能让 40 GiB 模型“装得下”，却不保证 TG 翻倍？
  2. 如果切分点每层都要跨卡传大 tensor，最先要估算什么？
  3. PCIe 与高速专用互联的差异在什么 workload 下最可能暴露？
  4. 如果 GPU0 90% 忙、GPU1 30% 忙，你会先怀疑哪三类配置？

完成证据

提交一张“双卡容量/通信账本”：模型如何切分、每卡驻留什么、哪里跨卡、预计 bottleneck 在 compute / memory / interconnect 哪一项，并注明尚未由真机证明的部分。

如何迁移

跨 NVIDIA/AMD/Intel 都问同一组问题：状态放哪里、算在哪里、每一步搬多少、链路多快、同步几次。

教材补全：多 GPU 先解决“放不下”，再讨论“更快”

Worked Example：两张 24 GiB 不等于一张 48 GiB

假设模型需要跨两卡切分。权重可以被分到 GPU0/GPU1，但每次层间、张量间的数据依赖可能需要经过 PCIe/NVLink/其他路径：

GPU0 compute
→ transfer
→ GPU1 compute
→ transfer / sync
...

总容量增加了，但 latency、同步和互联流量也进入关键路径。

常见切分思路

  • Layer/pipeline split：不同层放不同 GPU。
  • Tensor split：同一算子/矩阵跨 GPU 切。
  • Data parallel：复制模型，处理不同请求；更适合吞吐扩展而非单请求超大模型。

具体 runtime 支持哪一种，要查当前 backend。

实验预期

  • 两卡通常先带来 capacity 增长。
  • 单请求 TG 不保证线性增长，甚至可能下降。
  • 互联越慢、跨卡通信越多，扩展效率越差。
  • 不对称 GPU 会带来 load balance 与容量切分问题。

排错

  1. 确认每张 GPU 实际放了多少层/权重/KV。
  2. 记录 topology 与 link width/speed。
  3. 区分 P2P 可用、host-staged transfer 和 runtime fallback。
  4. 比较单卡 baseline 与双卡，不要只看双卡绝对数字。

只有一张 GPU 怎么办？

可以用纸上 split 与 interconnect accounting 完成主目标，并查自己主板 lane/topology。真正多卡 benchmark 留到有硬件时做，不影响理解课程。

Decision Rule

多 GPU 的第一问是“容量是否必须跨卡”，第二问才是“通信成本能否接受”。不要把 VRAM 相加直接当性能相加。
