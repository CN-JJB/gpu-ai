Intel Xe · 1/2 · L0→L1

Intel Xe（一）：EU → Xe-core → XMX，应该怎样建立执行模型？

Intel GPU 的术语变化很容易让人迷路：EU、Xe-core、subgroup、XMX、oneAPI。不要急着和 CUDA Core 做数量换算。本节先建立 Intel 自己的“并行执行 + 矩阵专用 + memory hierarchy”模型。

Prerequisite Check

你应理解 GPU 线程会被成组调度，也知道 NVIDIA warp / AMD wave / Apple SIMD-group 只能做功能类比。

真实问题：为什么“多少 EU”或“多少 Xe-core”不能直接变成 token/s？

因为产品代际改变了执行组织，且 LLM 性能还受 XMX/低精度 kernel、显存带宽、容量和软件 backend 影响。计数单位只有在同一架构、同一工作条件下才可能作为粗指标。

1. 从 EU 到 Xe-core：名称变化背后要看资源组织

Intel 早期/集成 GPU 文档常用 Execution Unit（EU）描述可编程执行资源；Xe 世代更常以 Xe-core 等更高层组织呈现。你应该问：

  • 一个调度组如何组织 threads/subgroups？
  • vector/ALU datapath 在哪里？
  • register/local memory/cache 怎样共享？
  • matrix/XMX 是否在同一 core tile 内？

而不是问“一个 Xe-core 等于几个 SM”。

2. Subgroup：Intel/SYCL 世界里的 lane group

SYCL/OpenCL 等模型使用 work-item/work-group，并提供 subgroup 抽象来描述一组在硬件上紧密协作的 lanes。

ND-range
└─ work-group
   └─ work-items
      └─ subgroup (hardware-coordinated lanes)

subgroup 可以做 shuffle、vote、reduction 等低层协作。它与 warp/wave/SIMD-group 属于相近抽象类别，但实际宽度和能力要查询设备。

3. XMX：Intel 的矩阵加速路径

Xe Matrix Extensions（XMX）是面向矩阵/AI 的专用计算资源。正确的比较方法与 Tensor/Matrix Core 一样：

hardware XMX
+ supported numeric mode
+ library/kernel mapping
+ application dispatch
= usable matrix acceleration

如果应用走的是普通 vector path，XMX 峰值不会自动出现。

4. DPAS/矩阵指令概念：为什么 layout 很重要？

矩阵专用指令通常要求特定 tile、数据布局和数据类型。高层 library 会负责大量映射，但 kernel 编写者必须考虑如何把 packed data 喂给指令。

这也解释了为什么模型量化格式与硬件位宽看起来“都 4-bit/8-bit”，仍可能需要专门 kernel 转换/解包。

5. Cache / local memory：Intel GPU 仍然受数据移动约束

不论叫 SLM（shared local memory）还是其他层级，核心思想相同：把可复用 tile 放到更近的片上资源，减少显存往返。Arc 等离散 GPU 还要区分本地 VRAM 与 PCIe host transfer。

Worked Example：Arc 16 GB 卡为什么可能很有吸引力，却仍不能只看显存？

大显存可以让某些模型通过 fit gate，但接下来必须确认：

  1. 目标 OS/driver 对 exact GPU 的稳定性；
  2. oneAPI/Level Zero/SYCL 或应用使用的 backend；
  3. 目标 LLM runtime 是否拥有 Intel GPU kernel；
  4. quant format 是否能利用 XMX/适合的数据路径；
  5. memory bandwidth、power/thermal 与真实 token/s；
  6. 价格是否补偿生态成熟度差异。

因此 Intel 候选卡常常是“规格看起来很好，软件证据决定最后能不能兑现”的典型教材。

Why it matters

  • 让你能读 Intel GPU 而不依赖 NVIDIA 术语翻译。
  • 理解 XMX 只是矩阵 datapath，应用必须有 kernel 映射。
  • 建立 subgroup/SLM 的跨厂商并行算法迁移能力。
  • 为判断 Arc 的大显存/价格优势是否能转化为 LLM 价值打基础。

常见误区

  • “EU 数可以与 CUDA Core 直接换算”——执行组织/吞吐口径不同。
  • “XMX 数多就等于 AI token/s 高”——还缺模型格式、kernel、memory。
  • “SYCL 是 Intel 专属语言”——SYCL 是跨厂商异构编程标准/生态，但实现和 backend 能力有差异。
  • “16 GB 显存通过 fit 就够了”——support/performance/quality/system/cost 仍要过 gate。

小实验与预期观察

建立四厂商术语映射表，只允许写“功能类别”而非等号：NVIDIA warp、AMD wave、Apple SIMD-group、Intel subgroup；NVIDIA shared、AMD LDS、Apple threadgroup memory、Intel SLM。为每项加一列“不可假设相同的参数”。

预期你会发现跨厂商知识真正可迁移的是数据流与调度问题，而不是计数单位。

无 Intel GPU 路径

L0 使用 Intel oneAPI/SYCL 与 GPU architecture 文档即可。后续如果有 Arc，再读取 device capabilities 和运行受控 benchmark；不要求购买。

排错

  • 系统看到 Arc 但应用没 GPU：检查应用 backend/build，而不是只看设备管理器。
  • XMX 没利用：确认数据类型、library/kernel、model format 和 dispatch。
  • 不同驱动版本表现差异：保留 driver/runtime identity，避免把动态软件行为写成架构事实。

Retrieval Practice

  1. 为什么 EU/Xe-core 数不能与 SM/CUDA Core 直接换算？
  2. subgroup 在并行编程里解决什么问题？
  3. XMX 要通过哪几层才能变成 LLM 实际加速？
  4. 为什么 matrix instruction 对 layout/packing 敏感？
  5. Arc 大显存通过了哪个 gate？还有哪些 gate 没过？
  6. 四厂商的 lane-group 抽象可以迁移什么，不能迁移什么？

Decision Rule

Intel 候选必须先证明 exact driver/runtime/backend + model kernel 可用，再让显存、带宽、XMX 和价格进入比较。没有软件证据时，纸面 XMX/TOPS 只算潜在能力。

Transfer

下一节进入 Arc/oneAPI/LLM 软件路线。把这一节的硬件层与下一节的软件层接成完整 evidence chain。

把 Intel 执行模型压成一张图

work-item
  ↓ grouped by software work-group
subgroup
  ↓ mapped onto hardware execution lanes
Xe-core vector / matrix datapaths
  ├─ registers: thread-local working state
  ├─ SLM: work-group-local reusable tiles
  ├─ caches: automatic data reuse
  └─ XMX: matrix path only when a matching kernel dispatches it
        ↓
local VRAM / system memory

这张图的价值在于：以后看到任何 Intel 性能问题，都先问“数据和线程卡在哪一层”，而不是先问 EU/Xe-core 数量。比如某个量化 kernel 已经 full offload，却 TG 仍低，问题可能在显存流量、解包、cache reuse 或普通 vector path；只有证据表明目标 kernel 确实 dispatch 到矩阵路径时，才应把 XMX 纳入解释。

Worked Example：为什么同样是 16 GB，两个 backend 的结果可以完全不同？

假设同一张 Intel GPU、同一个模型 artifact、同一个 context，Backend A 能完整 offload，但只走通用 vector kernel；Backend B 也完整 offload，同时为该量化格式提供适配的矩阵 kernel。两者都通过了 fit gate，但并没有通过同一个 execution-path gate。

问题Backend ABackend B
模型是否装得下是是
是否 GPU offload是是
是否有目标量化的矩阵 kernel未证明已证明
可否仅凭 XMX TOPS 预测 TG不可以仍然不可以

即使 B 使用 XMX，最终 token/s 仍可能被显存带宽、KV、host work、同步或调度限制。这正是“feature present → kernel uses feature → workload benefits”三层证据不能跳步的原因。

Experiment Evidence：这一节完成后要留下什么？

保存一张 Intel execution worksheet，至少包含：

  • work-item / work-group / subgroup 的关系；
  • Xe-core、SLM、cache、local memory、XMX 分别属于哪一层；
  • 你所调查设备的 subgroup capability 来源；
  • 一个“feature exists 但 application 未必使用”的反例；
  • 一个你明确拒绝做的跨厂商数量等价，例如 Xe-core = N 个 CUDA Core。

没有 Intel GPU 时也能完成：使用官方架构/SYCL 文档做只读 worksheet，并把所有设备相关数值标成 DOCUMENTED，不要伪装成 measured evidence。

Interpretation Branches

  • 设备枚举失败：先停在 driver/runtime 层，不能讨论 XMX 性能。
  • 设备可见但应用走 CPU：问题在 application build/backend，不是“Intel GPU 没算力”。
  • GPU full offload 但矩阵路径未知：只能证明 GPU execution，不能宣称 XMX-used。
  • 矩阵路径已证明但速度仍低：继续检查 memory traffic、quant unpack、host overhead、thermal/power 和 workload shape。

What this lesson does NOT prove

完成本节不会证明任何一张 Arc 卡“值得买”，也不会证明某个 SYCL/Vulkan/oneAPI backend 更快。它只让你建立一套不会被厂商名词变化带偏的执行模型。购买与性能结论必须等 exact device、软件链、模型 artifact 和实测 Evidence 都绑定后再下。
