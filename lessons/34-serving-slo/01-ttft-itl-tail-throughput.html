Serving Workload / SLO — 为什么 100 tok/s 仍然可能很难用？

1. Server 不是一个 tokens/s

用户真正经历：

发请求
→ 等
→ 第一字出现
→ 一直生成
→ 完成

所以至少要看：

TTFT
ITL
E2E
request throughput
token throughput
p95 / p99

2. TTFT

TTFT
=
first visible token
-
request arrival

里面可能混着：

queue
+ prompt processing
+ first decode/delivery
客户端 TTFT 不是纯 GPU Prefill 时间。

3. ITL

第一 token 出来以后：

token1 → token2 → token3 ...

相邻 token 的间隔就是 ITL。

但如果客户端只看到 SSE chunk：

一个 chunk
可能包含多个 tokens

所以 chunk gap 只能叫 proxy，不能硬叫真正 token ITL。

4. 一个常见现象

TTFT 很差
ITL 很好

说明可能：

前面排队很久
→ 一旦拿到 slot
→ decode cadence 仍然健康

5. Aggregate throughput 和用户速度也不是一回事

Continuous batching 可以让：

总 tokens/s ↑

但同时：

每个用户 ITL ↑

因为更多 active sequences 一起分享 GPU。

6. 为什么平均值会骗人？

12 个 synthetic TTFT：

100 105 110 115 120 125
130 135 140 145 150 1200

平均：

214.6 ms

看起来很棒。

但 nearest-rank p95：

1200 ms

尾部用户已经等了一秒多。

7. P95/P99 是什么？

粗略说：

p95
≈
95% observation 不超过这个值

但 percentile 有不同算法。

本课程 L0 用：

nearest-rank
ceil(p × N)

真实 Grafana/k6/Prometheus 报告时要记录工具算法。

8. SLO

比如你定义：

TTFT <= 500 ms
ITL <= 80 ms
至少 99% 请求满足

这才是真正的系统目标。

不是：

平均 TTFT < 500

9. 请求长度分布为什么必须记录？

短输出长输出
短 prompt轻长期占 slot
长 promptPrefill 重Prefill + Decode 都重

同样 10 req/s，负载可以完全不同。

10. Cache 也属于 workload

cold prompt
vs
warm prefix cache

TTFT 可以差很多。

所以不能把两种状态的结果放一张图里假装同一实验。

11. 当前 llama-server 可以看到什么？

Pinned 版本的 /metrics 可以看到：

processed prompt tokens
cached prompt tokens
predicted tokens
requests processing
requests deferred
busy slots/decode

客户端再记录 TTFT/E2E，就能把外部体验和内部状态对起来。

12. 最佳 concurrency 不是越高越好

真正目标：

maximize throughput
subject to
latency SLO
+
quality

比如 concurrency 16 的总吞吐最高，但 p95 TTFT 爆炸，那它就不是交互式服务的最佳配置。

13. 从现在开始 Serving Benchmark 必须记录

arrival distribution
prompt token distribution
output length distribution
slots
cache state
continuous batching
TTFT / ITL / E2E
percentiles
throughput
quality

这样“我的 server 很快”才开始变成一个可验证命题。
