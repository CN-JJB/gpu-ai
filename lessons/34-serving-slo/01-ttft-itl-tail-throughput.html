Serving Workload / SLO — 为什么 100 tok/s 仍然可能很难用？

1. Server 不是一个 tokens/s

用户真正经历：

发请求
→ 等
→ 第一字出现
→ 一直生成
→ 完成

所以至少要看：

TTFT
ITL
E2E
request throughput
token throughput
p95 / p99

2. TTFT

TTFT
=
first visible token
-
request arrival

里面可能混着：

queue
+ prompt processing
+ first decode/delivery
客户端 TTFT 不是纯 GPU Prefill 时间。

3. ITL

第一 token 出来以后：

token1 → token2 → token3 ...

相邻 token 的间隔就是 ITL。

但如果客户端只看到 SSE chunk：

一个 chunk
可能包含多个 tokens

所以 chunk gap 只能叫 proxy，不能硬叫真正 token ITL。

4. 一个常见现象

TTFT 很差
ITL 很好

说明可能：

前面排队很久
→ 一旦拿到 slot
→ decode cadence 仍然健康

5. Aggregate throughput 和用户速度也不是一回事

Continuous batching 可以让：

总 tokens/s ↑

但同时：

每个用户 ITL ↑

因为更多 active sequences 一起分享 GPU。

6. 为什么平均值会骗人？

12 个 synthetic TTFT：

100 105 110 115 120 125
130 135 140 145 150 1200

平均：

214.6 ms

看起来很棒。

但 nearest-rank p95：

1200 ms

尾部用户已经等了一秒多。

7. P95/P99 是什么？

粗略说：

p95
≈
95% observation 不超过这个值

但 percentile 有不同算法。

本课程 L0 用：

nearest-rank
ceil(p × N)

真实 Grafana/k6/Prometheus 报告时要记录工具算法。

8. SLO

比如你定义：

TTFT <= 500 ms
ITL <= 80 ms
至少 99% 请求满足

这才是真正的系统目标。

不是：

平均 TTFT < 500

9. 请求长度分布为什么必须记录？

短输出长输出
短 prompt轻长期占 slot
长 promptPrefill 重Prefill + Decode 都重

同样 10 req/s，负载可以完全不同。

10. Cache 也属于 workload

cold prompt
vs
warm prefix cache

TTFT 可以差很多。

所以不能把两种状态的结果放一张图里假装同一实验。

11. 当前 llama-server 可以看到什么？

Pinned 版本的 /metrics 可以看到：

processed prompt tokens
cached prompt tokens
predicted tokens
requests processing
requests deferred
busy slots/decode

客户端再记录 TTFT/E2E，就能把外部体验和内部状态对起来。

12. 最佳 concurrency 不是越高越好

真正目标：

maximize throughput
subject to
latency SLO
+
quality

比如 concurrency 16 的总吞吐最高，但 p95 TTFT 爆炸，那它就不是交互式服务的最佳配置。

13. 从现在开始 Serving Benchmark 必须记录

arrival distribution
prompt token distribution
output length distribution
slots
cache state
continuous batching
TTFT / ITL / E2E
percentiles
throughput
quality

这样“我的 server 很快”才开始变成一个可验证命题。

学生闭环 — Serving Workload / SLO

硬件门槛：L0 模拟主路径；真实 server 增强 L1。

成本：0 元。

风险：默认 safe；涉及网络暴露时只在受控本地环境完成，先审计再开放。

能力目标

  • 从“单机 benchmark”升级到“用户看到的服务行为”。
  • 用 tail/SLO/capacity/fairness/exposure 约束系统，而不是只追总 tok/s。
  • 能通过 trace/metrics 解释一个服务为什么好用或不好用。

小实验 / 反馈

做 Experiment 62：tail-latency trace；有 llama-server 时做 Experiment 63：real serving trace。

Retrieval Practice

  1. 为什么 aggregate tokens/s 高不代表单个用户体验好？
  2. TTFT 里可能混入哪些非-prefill 时间？
  3. 为什么 SSE chunk gap 不能无条件叫 token ITL？
  4. 平均延迟很好但 p95 爆炸时，你应该相信哪个与 SLO 更相关？

完成证据

定义一个真实 workload 的 arrival、prompt/output 长度分布、concurrency/cache state，并给出 TTFT/ITL/E2E/throughput 的 SLO 与 percentile 算法。

如何选择 / 迁移

换 vLLM、llama-server 或其他 runtime 后，指标名字可以变，但仍围绕 latency / traffic / errors / saturation + workload contract + per-user SLO 做判断。

教材补全：从“看指标”到“写 SLO”

先建立一个端到端时间轴

arrival
  ↓ queue wait
service start
  ↓ prefill
first token
  ↓ decode token gaps
last token
  ↓ response finished

任何延迟指标都必须绑定到这条时间轴上的两个点。没有起点和终点定义，数字就没有可比性。

Worked Example：为什么 80 tok/s 也可能输给 45 tok/s

系统TTFT p95Decode用户感受
A4.0 s80 tok/s前四秒像死机，之后很快
B0.45 s45 tok/s很快开始回答，持续输出

如果 workload 是交互聊天，B 可能明显更好；如果是离线长文本批处理，A 的 aggregate throughput 反而可能更重要。“更快”必须先说明是哪一种体验目标。

把 workload 写完整

request mix =
prompt length distribution
+ output length distribution
+ arrival pattern
+ concurrency
+ cache state
+ streaming mode

至少固定这些变量，才有资格比较两个 runtime、两个 GPU 或两个 batching 设置。

实验预期

  • 提高并发通常会先改善硬件利用率与 aggregate throughput；继续提高后，queue 与 tail latency 会恶化。
  • 长 prompt 会更明显影响 TTFT；长 output 会更明显占用 active slot 与 decode 时间。
  • warm prefix/cache 结果不应与 cold 结果直接混算。

排错顺序

  1. 先确认计时点是不是客户端、反代还是 server 内部。
  2. 把 queue、prefill、decode 分开，不要只看 E2E。
  3. 检查请求长度分布是否变化。
  4. 检查并发和 cache state 是否一致。
  5. 最后才怀疑 GPU 本身。

Decision Rule

买卡或升级前，不接受“平均 tok/s 更高”作为 serving 证据。至少要同时给出 workload、TTFT/ITL 或等价延迟指标、tail percentile 与 aggregate throughput。

没有多用户环境怎么办？

用离线 trace 或固定并发脚本也能完成学习目标。目标不是伪造线上流量，而是学会把 arrival、queue、service、tail latency 分开。

Retrieval Practice

  1. 为什么客户端 TTFT 不能直接叫 Prefill latency？
  2. 为什么 aggregate tokens/s 上升时，单用户 ITL 仍可能恶化？
  3. p95 很差但平均值很好，说明了什么？
  4. 比较两张 GPU 的 serving 能力前，至少要固定哪五类 workload 变量？
