Tokenizer & Sampling · L0→L1

Tokenizer、Chat Template、Logits、Sampler：同一个模型为什么“提示词看起来一样”却可能不是同一 workload？

性能和质量实验最容易被“文本看起来一样”骗到。模型实际接收的是 token IDs；聊天模型还会经过 chat template；输出则由 logits 和 sampler 决定。只要这些身份改变，你就可能已经换了实验 workload。

Prerequisite Check

你应知道输入文本先变 token，再经过模型生成下一 token。无需理解 BPE/Unigram 的全部训练算法。

真实问题：为什么同一句“你好”，不同 runtime 可能得到不同 token 数、不同 TTFT，甚至不同回答？

可能因为 tokenizer revision、special token policy、chat template、BOS/EOS、generation prompt、encoding bug 或 sampling 参数不同。

1. Tokenizer：文本不是模型的直接输入

UTF-8 text
→ tokenizer rules/vocabulary
→ token IDs
→ embedding vectors
→ model

不同 tokenizer 会把同一字符串切成不同 token sequence。性能上，prompt token 数改变会改变 prefill 工作；质量上，token boundary 也会改变模型实际看到的序列。

2. Tokenizer identity 不只是 vocab 文件名

可复现时至少考虑：

  • tokenizer files/revision；
  • normalization/pre-tokenization；
  • special token map；
  • BOS/EOS policy；
  • added tokens；
  • runtime tokenizer implementation。

课程 Experiment 57 会保存 rendered bytes 与 token-ID SHA，就是为了把“提示词身份”变成证据。

3. Chat Template：用户消息怎样变成模型训练过的格式？

聊天模型通常不是直接接：

User: 你好

而是按模型定义渲染 role token、分隔符、system prompt、assistant prefix 等：

[special system tokens] ...
[special user tokens] 你好 ...
[special assistant prefix]

模板错了，模型仍可能输出文字，但质量/停止条件/角色行为都可能异常。

4. Rendered text 与 token IDs 都要固定

两个 runtime 可以渲染出看起来相同的文本，但 special-token parsing 不同；也可以 token IDs 相同但日志显示文本形式不同。严谨实验同时保存：

  • messages JSON/hash；
  • chat template hash；
  • rendered bytes/hash；
  • token IDs/hash；
  • token count。

5. Logits：模型不是直接“选择答案”

每一步模型输出 vocabulary 上的一组分数（logits）。经过 softmax 等处理后可以理解为 next-token probability distribution。

hidden state
→ vocab projection
→ logits for every token
→ sampler
→ chosen token

模型 weights 固定时，logits 还会受到 context/token sequence 与数值/kernel 影响；最终 token 则进一步受到 sampler 影响。

6. Temperature：不是“创造力按钮”这么简单

temperature 改变 logits 分布的尖锐程度。低 temperature 更集中在高分 token；高 temperature 让低分 token 相对更有机会。

但它不修复错误 prompt，也不保证高温更“聪明”。

7. Top-k / Top-p / Min-p：候选集过滤

  • top-k：只保留最高的 k 个候选；
  • top-p：保留累计概率达到阈值的最小候选集合；
  • min-p：按相对最高概率的阈值过滤低概率 token（具体实现语义应查 runtime）。

不同 sampler 可以组合，且执行顺序/实现细节可能影响结果。比较质量时必须记录完整 sampler chain。

Worked Example：为什么 greedy 更适合某些可复现质量 fixture？

如果你的目标是比较 quant/backend 是否改变 deterministic JSON 输出，随机 sampling 会引入额外噪声。可以使用 greedy/固定 deterministic policy，让输出差异更容易归因模型/runtime。

但如果目标是评估真实聊天创作体验，则固定一个合理 sampler/seed，多次采样更接近实际使用。实验设计取决于问题。

8. Seed 为什么也不是“绝对复现保证”？

固定 seed 只控制随机数的一部分。不同 runtime、不同 kernel、不同浮点顺序可能产生稍微不同 logits，随后 sampling 分叉。精确 token-for-token 复现还需要更严格的环境一致性。

9. Stop tokens / EOS：为什么模型会不停说或提前停？

chat template 与 tokenizer 定义了 special EOS/end-of-turn token；runtime 必须正确识别。错误 stop config 可能让模型：

  • 生成到 max tokens；
  • 泄露下一角色模板；
  • 过早截断。

Why it matters

  • 性能实验必须固定 token identity，否则 prompt 长度不一致。
  • 质量实验必须固定 chat template/sampler，否则不是同 workload。
  • 解释跨 runtime “同模型不同回答”的大量来源。
  • 为 perplexity、quality gate、benchmark manifest 建立身份基础。

常见误区

  • “文本一样 = prompt 一样”——token/template 可能不同。
  • “temperature=0 就保证跨 runtime 完全一样”——数值/实现仍可能分叉。
  • “seed 固定就绝对复现”——环境差异仍可影响。
  • “chat template 只是 UI 格式”——它是模型输入语义。
  • “top-p 数值一样就等价”——sampler order/implementation 需确认。

小实验

使用 Experiment 57 或纸面路径：同一 messages 用两个不同 template 渲染，比较 rendered bytes、token count、token IDs。再设计 greedy 与随机 sampler 两种质量 fixture，说明各自适合回答什么问题。

预期观察：少量模板字符/special token 就可能改变 token sequence；随机 sampling 会扩大输出方差。

无 GPU 路径

Tokenizer/模板实验可以完全在 CPU/L0 完成，不需要生成大模型。

排错

  • 输出角色错乱：先查 chat template/end-of-turn，不先怪量化。
  • 不同 runtime PP 不可比：核 token count/token-ID SHA。
  • 固定 seed 仍不同：确认 tokenizer/template/model/runtime 与 deterministic capability。

Retrieval Practice

  1. 为什么文本字符串不是完整 prompt identity？
  2. chat template 怎样改变模型实际输入？
  3. 为什么 rendered SHA 和 token-ID SHA 都值得保存？
  4. temperature/top-k/top-p 分别改变 sampling 哪一层？
  5. 固定 seed 为什么不保证跨 runtime token-for-token 一致？
  6. 什么时候 greedy fixture 比随机聊天更适合质量 A/B？

Decision Rule

任何性能/质量对比先固定 tokenizer、chat template、rendered/token IDs 与 sampler semantics。只要 token identity 或 sampler chain 改变，就把它当作新的 workload/语义变量，而不是“同一句 prompt”。

Transfer

以后做 RAG、agent/tool calling、structured output 时，prompt identity 会更复杂；仍用 messages → template → rendered bytes → tokens → sampler/stop 的链记录。
