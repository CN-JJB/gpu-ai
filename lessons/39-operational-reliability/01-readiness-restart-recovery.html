Operational Reliability — 进程活着，为什么还不能接请求？

Prerequisite Check

开始前，你应该知道一个本地 LLM 服务至少包含进程、监听 socket、模型加载、后端初始化与一次真实推理路径，并理解 liveness 和 readiness 是不同问题。

如果还不熟：先用这条最小链路继续：process alive → socket reachable → model ready → smoke inference passes。只要其中任一步没验证，就不能把“进程没退出”写成“服务已经可用”。

真实问题

你重启本地 LLM 后看到进程已经起来、端口也能连接，于是立刻让上层应用恢复流量；但前几批请求持续 503、超时，甚至第一次推理还因为模型或 backend 初始化失败。

真正的问题是：怎样定义“已经恢复到可接真实请求”的可验证状态，并在重启、崩溃或断电后证明系统能重复回到这个状态？可靠性不是“今天能跑”，而是故障发生后仍能按已知步骤恢复。

1. 启动不是一个瞬间

process spawn
→ socket 能连
→ health 返回
→ model loaded
→ first inference
→ warm steady state
这些时间点不能统称一个“启动时间”。

2. Liveness

进程存在：

PID alive

只能说明它还没退出。

它可能正在：

加载模型
分配显存
初始化 backend

3. Readiness

当前 pinned llama-server：

/health = 503
Loading model

表示还在加载。

等到：

/health = 200
status=ok

才是它定义的 model-ready。

4. Port open 也不够

如果：

HTTP 已经能收到 503

那端口显然已经可达。

但模型仍没 ready。

listener available
!= model ready

5. Health 200 仍不等于你的 workload 可用

还可能有：

错误 chat template
context 不够
grammar/tool 路径错误
第一请求冷启动

所以部署完成最好再做：

tiny smoke inference

6. 我们测四个时间

t_spawn
t_first_http
t_health_200
t_first_inference_done

得到：

listener recovery
readiness recovery
usable smoke recovery

7. Restart 会发生什么？

进程里的：

KV
prefix cache
一些 runtime warm state

通常应该先按“丢了”处理，除非你有明确 save/restore 证据。

8. 所以健康恢复后也可能更慢

health 200
→ first request cold
→ later requests warm

服务是 healthy，但还没达到 steady-state latency。

9. Restart 还会偷偷换身份

例如原来：

Q4 model
CUDA build
ctx 32k

重启脚本不小心变成：

Q5 model
different commit
ctx 8k

端口还是 8080，不代表系统一样。

10. Graceful drain 和 kill 也不是一个东西

理想 drain：

停止接新请求
→ 等现有请求完成
→ stop

直接 process terminate：

可能打断 active request

即使操作系统给了进程清理机会，也不能自动叫“drain”。

11. 不要 sleep 10 然后祈祷

正确 poll：

connection refused?
503 loading?
200 ready?
process exited?
timeout?

这些状态本身就是诊断证据。

12. 真实实验只碰自己启动的子进程

课程脚本强制：

127.0.0.1

并且只 terminate 它自己 spawn 的 PID。

不安装：

systemd
launchd
Windows service
开机启动

13. 最终目标

restart
→ identity unchanged
→ health ready
→ smoke inference
→ warm performance

这才是“服务恢复了”的完整说法。

教材补全：进程活着，不等于服务 Ready

把健康状态拆成三层

Liveness:
进程还活着吗？

Readiness:
现在能正确接新请求吗？

Functional probe:
真的能完成一个代表性推理吗？

模型仍在加载、GPU backend 初始化失败、KV allocator 异常时，进程可能完全“活着”，但绝不应该接流量。

Worked Example：自动重启为什么会变成重启风暴

假设模型启动需要 40 秒，而 watchdog 20 秒没看到 ready 就杀进程：

start
20s → killed
restart
20s → killed
...

系统表面上“配置了自动恢复”，实际永远无法进入 ready。恢复策略必须理解正常 startup 时间。

可靠启动顺序

process starts
→ runtime/backend init
→ model load
→ warmup / first functional probe
→ READY
→ receive traffic

重启前要区分可恢复状态

  • 普通请求失败：不一定需要重启整个 server。
  • 模型进程崩溃：可以由 supervisor 重启。
  • GPU/driver 状态异常：进程重启可能无效，需要更高层恢复。
  • 硬件/供电/散热故障：继续自动重试可能掩盖真正问题。

Recovery Evidence

可靠性不能只写“systemd/容器会自动重启”。至少验证：

kill/restart event
→ model reload
→ readiness becomes true
→ representative request succeeds
→ logs identify the event

State 要分类

Local LLM server 常见状态包括模型文件、配置、cache、会话/业务状态和日志。重启是否丢失状态，取决于这些东西存在哪里，不能一概而论。

Decision Rule

恢复能力必须用一次真实的“失败 → 恢复 → 功能验证”闭环证明，而不是用“配置了 restart policy”证明。

Retrieval Practice

  1. Liveness 与 Readiness 有什么本质区别？
  2. 为什么启动时间未知时，watchdog 可能制造 restart loop？
  3. 什么时候进程重启不足以解决故障？
  4. 恢复成功为什么必须包含功能请求，而不只是 PID 出现？

Recovery Drill：把“恢复了”变成四个可验证检查点

failure / stop event
→ process restored
→ readiness restored
→ representative inference succeeds
→ warm steady state restored

每个箭头都记录时间与 Evidence。只看到 PID 回来，最多证明 supervisor 启动了进程；只有 representative inference 成功，才证明业务路径恢复；只有 warm performance 回到 policy 范围，才证明 steady-state 也恢复。

Worked Example：Health 200，但第一请求失败

这种情况应写成 readiness probe PASS, functional probe FAIL，而不是“服务已恢复”。可能的下一步包括检查 model/template/backend、cold initialization、context/grammar/tool path。状态要精确到失败层。

Recovery Evidence Packet

  • baseline exact runtime/model/config identity；
  • failure/stop method 与时间；
  • spawn/listener/readiness/functional-probe 时间点；
  • stdout/stderr/logs；
  • 第一请求与 warm requests 的 latency；
  • rollback/restart 后 identity recheck；
  • 未恢复时的 STOP/BLOCKED 原因。

Failure Recovery 边界

课程主线只对自己启动、可控的测试服务做故障演练。不为了“练可靠性”制造电气故障、强刷固件或破坏系统状态。真正硬件/驱动级故障应先保护设备与 Evidence，再按安全文档处理。

What this lesson does NOT prove

一次 restart drill PASS 不证明 24/7 永久可靠，也不证明 supervisor policy 能处理所有故障。它只证明指定 failure mode 在指定环境下有一条已经验证的恢复路径。
