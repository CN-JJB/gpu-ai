Operational Reliability — 进程活着，为什么还不能接请求？

1. 启动不是一个瞬间

process spawn
→ socket 能连
→ health 返回
→ model loaded
→ first inference
→ warm steady state
这些时间点不能统称一个“启动时间”。

2. Liveness

进程存在：

PID alive

只能说明它还没退出。

它可能正在：

加载模型
分配显存
初始化 backend

3. Readiness

当前 pinned llama-server：

/health = 503
Loading model

表示还在加载。

等到：

/health = 200
status=ok

才是它定义的 model-ready。

4. Port open 也不够

如果：

HTTP 已经能收到 503

那端口显然已经可达。

但模型仍没 ready。

listener available
!= model ready

5. Health 200 仍不等于你的 workload 可用

还可能有：

错误 chat template
context 不够
grammar/tool 路径错误
第一请求冷启动

所以部署完成最好再做：

tiny smoke inference

6. 我们测四个时间

t_spawn
t_first_http
t_health_200
t_first_inference_done

得到：

listener recovery
readiness recovery
usable smoke recovery

7. Restart 会发生什么？

进程里的：

KV
prefix cache
一些 runtime warm state

通常应该先按“丢了”处理，除非你有明确 save/restore 证据。

8. 所以健康恢复后也可能更慢

health 200
→ first request cold
→ later requests warm

服务是 healthy，但还没达到 steady-state latency。

9. Restart 还会偷偷换身份

例如原来：

Q4 model
CUDA build
ctx 32k

重启脚本不小心变成：

Q5 model
different commit
ctx 8k

端口还是 8080，不代表系统一样。

10. Graceful drain 和 kill 也不是一个东西

理想 drain：

停止接新请求
→ 等现有请求完成
→ stop

直接 process terminate：

可能打断 active request

即使操作系统给了进程清理机会，也不能自动叫“drain”。

11. 不要 sleep 10 然后祈祷

正确 poll：

connection refused?
503 loading?
200 ready?
process exited?
timeout?

这些状态本身就是诊断证据。

12. 真实实验只碰自己启动的子进程

课程脚本强制：

127.0.0.1

并且只 terminate 它自己 spawn 的 PID。

不安装：

systemd
launchd
Windows service
开机启动

13. 最终目标

restart
→ identity unchanged
→ health ready
→ smoke inference
→ warm performance

这才是“服务恢复了”的完整说法。
