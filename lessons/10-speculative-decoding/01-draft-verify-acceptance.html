Decode Acceleration · Lesson 10 · L0 + optional L1/L2

为什么让小模型先猜，反而不会把大模型答案带偏？

Speculative Decoding 最容易被误解成“小模型先写答案，大模型偶尔检查”。真正的结构恰好相反：draft 只负责便宜地提案，target 仍然负责验证和最终采样。它优化的是 autoregressive decode 的串行等待。

真实问题

大模型本来一个 token 一个 token 地生成。如果让一个小模型先猜 4 个 token，再让大模型检查，为什么会更快？猜错了怎么办？会不会改变大模型质量？

先看原来的串行墙

target(history)       → token 1
target(history + 1)   → token 2
target(history + 1,2) → token 3
target(...)           → token 4

四个新 token，需要四次串行 target step。

下一步必须等上一步 token，因为它会进入下一步的 history。

1. Speculation 插入一个便宜的 Proposer

history→ cheap proposer→ d1 d2 d3 d4

proposer 可以是：

  • 更小的 draft model；
  • 历史 n-gram lookup；
  • MTP head；
  • EAGLE-style learned proposer；
  • 其他更便宜的多-token predictor。

共同要求只有一个：

提案必须比 target 一个 token 一个 token 串行跑便宜很多，而且猜得够像 target。

2. Target 不是被替代，而是一次验证一段

draft 给出：

d1 d2 d3 d4

target 可以把这段 continuation 放进一个 batched verification forward 里一起评分。

4 draft tokens→ 1 target verify batch→ accept / reject

原始 speculative decoding/sampling 论文利用的正是：在低 batch、硬件利用不足时，target 并行评分几个位置的延迟，可能远小于串行跑几次 target。

3. Draft 猜错了怎么办？

用最容易理解的 greedy 类比：

draft : A B C D
target: A B X ...

前两个 draft 和 target 一致，可以接受。

到 C 发生 mismatch：

accept A B
take target X
discard old C D suffix

为什么 D 也不能继续？

因为 D 是在 draft history A B C 上猜的；正确 history 已经变成 A B X。

一旦历史分叉，旧 draft suffix 就不再属于正确 autoregressive chain。

4. 随机采样不是简单“token 相等就接受”

Temperature / top-p 等 stochastic sampling 下，正确 speculative sampling 会使用 acceptance/rejection/correction 规则。

原始论文的关键保证不是：

draft 输出质量足够好，所以大概和 target 一样。

而是：

在正确 verifier / rejection-sampling 算法下，最终样本保持 target distribution。

现实 runtime 仍可能因为 floating-point、batching、随机种子和非确定性 kernel 出现逐字差异，所以不要把 lossless 理解成“每次输出 byte-identical”。

5. Acceptance Rate 是什么？

acceptance rate
= accepted draft tokens
/ generated draft tokens

current llama.cpp 就会打印 generated / accepted draft token statistics。

直觉：

  • acceptance 高：draft 做的大部分工作被 target 留下；
  • acceptance 低：大量 proposal 被丢掉。

但 acceptance 不是最终成绩。

6. 为什么 90% acceptance 也不保证一定快？

Spec round 有成本：

draft generation
+ target verification
+ acceptance/correction
+ extra memory/state

如果 draft model 本身太重：

accepted tokens 很多
但 draft cost 也很大
→ total latency 仍可能没赢

所以真正比较：

每单位 speculative-round 成本，最终能让 target sequence 前进多少 token？

7. 一个最小 Expected-Progress 模型

假设：

  • 每个 draft token 独立以概率 p 沿链被接受；
  • draft length = D；
  • 一旦第一个失败，后续 draft suffix 作废。

期望 accepted prefix：

E[accepted]
= p + p² + ... + p^D

简化地把 mismatch 时 target 给出的 correction token 也算作前进一步：

E[progress]
≈ 1 + p + p² + ... + p^D

这是教学模型，不是每个 runtime 的精确内部公式。

9. 30% acceptance 时为什么长 draft 反而亏？

D=4 以后，新增 proposal 大部分位于很后面。

要活到第 4 个 draft token：

p^4 = 0.3^4 = 0.0081

只有 0.81% 的简化机会。

但你每一轮仍然为：

  • draft 4/8 个 token；
  • 更大的 verify batch；
  • 额外 state；

付成本。

acceptance 低时，long draft 的尾部往往是昂贵的废稿。

10. 60% acceptance 为什么 D=2 比 D=8 更好？

这就是 tuning 的意义。

更长 draft 确实让 expected progress 继续增加：

D=2 → 1.96
D=8 → 2.47

但 round cost 从：

1.32 → 2.04

涨得更多。

所以 optimum 不一定在最大 D。

11. Draft model 也要占显存

two-model speculation 可能多出：

  • draft weights；
  • draft KV cache；
  • draft runtime buffers；
  • 独立 offload placement。

如果你的目标模型本来刚好塞进 GPU：

load draft
→ VRAM headroom disappears
→ target layers spill/offload
→ target becomes slower

最后可能“spec 算法更聪明，整机反而更慢”。

12. N-gram proposer 为什么适合垃圾佬实验？

current llama.cpp 有不需要第二个模型的 history/n-gram proposer。

它寻找：

previous token pattern
→ likely repeated continuation
→ cheap draft

优点：

  • 额外模型内存小；
  • 容易做 baseline vs spec；
  • 代码重写、重复文本可能 acceptance 很高。

缺点：

  • 开放式新内容没模式可抄，acceptance 可能低；
  • 性能强烈依赖 workload。

13. 为什么 speculative decoding 更偏低 batch / 低 QPS？

上一节 continuous batching 已经让多个 active requests 一起跑。

如果 target 在高并发时已经被喂得很饱：

baseline target utilization high
→ batched verification advantage shrinks
→ proposer overhead becomes more visible

vLLM 当前官方也把 speculative decoding 定位在 medium-to-low QPS、偏 memory-bound 的场景；TensorRT-LLM 同样强调 low batch size。

单用户 2× speculative speedup，不能直接写成 8 用户 server 也 2×。

硬件门槛：L0 无需 GPU。真实 speculation 可先用 n-gram/draftless path，two-model draft 是可选高阶路径。

教材补全：Speculative Decoding 的收益来自“少走 target model 的串行 decode 步数”

Worked Example

普通 decode：

target → token1
target → token2
target → token3
target → token4

speculative path：

draft proposes: t1 t2 t3 t4
target verifies a block
→ accept several
→ only then continue

如果一次能接受多个 draft token，target 的串行步数减少；如果大量 draft 被拒绝，额外 draft 计算和 verification 可能得不偿失。

Acceptance Rate 不是唯一指标

真正收益还取决于：

draft speed
target verification efficiency
accepted tokens per target step
extra memory
scheduler overhead
batch/concurrency behavior

实验预期

  • draft 与 target 越匹配，acceptance 往往越好。
  • draft 太重时，即使 acceptance 高也可能没有净收益。
  • 短输出可能被初始化/调度开销淹没。
  • 不同 sampling 参数会改变 acceptance。

排错

  1. 先固定 target、draft、prompt、sampling。
  2. 同时测 baseline target-only。
  3. 记录 acceptance 以及最终 TG/latency，不只看 acceptance。
  4. 检查 draft 是否引入额外显存/CPU bottleneck。

无支持该功能的 runtime 怎么办？

用手工概率/trace 模型理解“proposal → verify → accept/reject”即可。不要为了体验 feature 更换整个环境；先学机制。

Decision Rule

只有相对 target-only baseline 的端到端性能提升，才算 speculative decoding 成功。高 acceptance 本身不是最终目标。
