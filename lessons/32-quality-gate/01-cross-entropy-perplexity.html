LLM 质量门 — 快了，不代表优化成功

1. GPU 教程为什么必须讲质量？

因为你会不断做：

FP16 → Q8 → Q4
KV FP16 → Q8
old backend → new backend
FA off → on

如果只记录 tokens/s：

更快
=
成功

这个结论不成立。

优化目标必须同时有性能和质量。

2. 模型每一步都在猜“下一个 token”

真实下一个 token 是 y。

模型给它的概率：

p(y | prefix)

概率越高，说明模型越不意外。

3. 为什么用 -log？

NLL = -ln p
正确 token 概率NLL
1.00
0.5~0.693
0.01~4.605

很自信地给正确答案极低概率，会被重罚。

4. 一段文本取平均

Cross Entropy
=
mean(-ln p(correct token))

然后：

Perplexity
=
exp(Cross Entropy)

同一测试条件下：

越低越好

5. 小例子

correct-token probabilities:
0.5
0.25
0.125
0.5

得到：

CE ≈ 1.2130
PPL ≈ 3.3636

如果量化后变成：

0.48
0.22

0.45

则：

CE ≈ 1.3373
PPL ≈ 3.8087

这个 synthetic 例子里 candidate 预测变差。

6. 最危险的错误：跨 tokenizer 比 PPL

Tokenizer A：

一句话 → 8 tokens

Tokenizer B：

一句话 → 13 tokens

概率分解已经不是同一个问题。

所以不能简单说：

A PPL 5
B PPL 6
→ A 模型一定更强

7. PPL 也不是 ChatGPT 式“好不好用”

Instruction finetune 可能：

  • 更会听指令；
  • 更会聊天；
  • 但普通文本 PPL 反而高一点。

所以：

PPL = predictive-fit instrument
not universal assistant score

8. 它为什么特别适合比较量化？

因为你可以固定：

同一个 source model
同一个 tokenizer
同一个 corpus
同一个 runtime
只换 quant

这就是非常干净的 A/B。

9. KL 又是什么？

PPL 看正确 token。

KL 可以更细地比较整个 token distribution。

KL = 0
→ 两个 distribution 完全相同

llama.cpp 当前 perplexity 工具就有用高精度 logits 做量化 KL 比较的路径。

但日志文件可能巨大，不要无脑开启。

10. 为什么还需要自己的 Task Fixtures？

你的目标可能是：

写代码
中文问答
JSON 输出
RAG
tool calling
长上下文找信息

Wikitext PPL 不会替你回答这些。

所以还要有自己的回归集。

11. Fixture 怎么设计？

可以是：

exact
contains
regex
JSON schema
multiple choice
domain-specific test

版本化保存。

12. Stochastic sampling 不适合当唯一质量证据

两次输出文字不同，可能只是随机路径不同。

更好的比较：

teacher-forced PPL/logprob
+
greedy/controlled fixtures

13. 没有万能 ΔPPL 阈值

不要背：

ΔPPL < 0.1 一定安全

正确做法：

我的 workload
允许多少 quality loss
换多少速度/显存收益？
