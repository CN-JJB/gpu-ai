Quality Gate · L0→L1

Cross-Entropy 与 Perplexity：为什么“更快”必须配一个质量 Gate？

量化、backend、KV 精度或 kernel 变化可能让模型更快，也可能改变输出质量。Perplexity（PPL）不是万能智能分数，但它提供一种可重复、机器可读的语言建模质量信号，特别适合检查“同一模型家族/同一 corpus 下，改动是否明显伤害预测分布”。

Prerequisite Check

你应知道模型每个位置输出 next-token logits/probabilities，也知道 tokenizer/corpus identity 必须固定。

真实问题：Q4 比 Q6 快 20%，我们能直接说 Q4 更好吗？

不能。性能只是 tradeoff 一轴。更低位量化可能引入误差；不同 backend/kernel 也可能有数值差异。你至少需要一个固定质量 signal，加上目标任务 fixture，才能判断速度收益是否可接受。

1. Cross-Entropy 的直觉

对于 corpus 中每个真实 next token，模型给它一个概率 p。如果模型很确定正确 token，p 较高；如果很意外，p 很低。

单 token 的 negative log-likelihood：

loss = -log(p_true_token)

对很多 token 取平均，就是 cross-entropy loss 的核心直觉。

2. Perplexity 是什么？

Perplexity 通常是平均 cross-entropy 的指数：

PPL = exp(mean_cross_entropy)

直觉上可以粗略理解为模型面对文本时的“有效困惑程度”。在同 tokenizer、同 corpus、同预处理、同 evaluation method下，更低通常表示对该 corpus 的 next-token prediction 更好。

3. 为什么 PPL 不能跨任意模型直接排行？

因为 tokenizer 会改变 tokenization，corpus/preprocessing 会改变评估对象，context/evaluation implementation 也可能改变值。特别是不同 vocabulary/tokenizer 的模型，PPL 的直接可比性很弱。

规则：PPL 最适合做“受控 A/B”，不是全互联网统一智商榜。

4. PPL 适合检查什么？

  • 同 base model 的不同 quant artifact；
  • 同模型同 corpus 的 backend/build 数值回归；
  • KV dtype/部分执行变量对质量的明显影响；
  • 模型 conversion 是否出现异常。

前提是 evaluation identity/argv 与 tokenizer/corpus 全部固定。

5. PPL 不擅长检查什么？

  • instruction following；
  • 代码可执行性；
  • 中文写作偏好；
  • RAG 引用正确性；
  • 工具调用/JSON schema；
  • 长上下文检索能力。

这些需要目标任务 fixture。课程质量 gate 因此是：

PPL / distribution signal
+ target deterministic tasks
+ human review where needed

Worked Example：Q6 vs Q4

固定同一 base revision、tokenizer、quality corpus、runtime、evaluation argv。得到：

baseline Q6: PPL = P6
candidate Q4: PPL = P4
performance: PP/TG measured separately

解释时计算 PPL delta/ratio，但不自动设“0.5% 一定可接受”。阈值由你的任务目标决定。再跑 JSON、中文、coding 等目标 fixture，才能形成完整 tradeoff。

6. Corpus identity：文件内容必须真的固定

只记录文件名不够。保存 corpus SHA256、bytes、fixture revision。哪怕只改一个换行/预处理，严格实验里也已经是新 corpus。

7. Tokenizer identity：为什么最容易被忽略？

PPL 是按 token 计算。换 tokenizer 等于改变评估单位和概率空间。必须固定 tokenizer revision/identity，不能把两个不同 tokenizer 的 PPL 小数做简单高低比较。

8. Evaluation argv：一个 flag 也可能改变语义

context/chunk、BOS、stride、batch 或工具版本都可能改变 evaluation。课程 I30 要求 quality identity 与实际 argv token-for-token 绑定，正是为了避免“同 corpus 但评法变了”。

9. 机器可读 metric 与原始输出

不要只把终端里 PPL 数字手抄进表。保存：

  • quality command record；
  • stdout/stderr；
  • executable/build identity；
  • corpus/identity hashes；
  • 机器提取的 PPL value/uncertainty（若工具提供）；
  • PACKET integrity。

这样以后可以重新验证数字是否来自原始输出。

10. PPL 变化的统计/实际意义

非常小的 PPL 差异可能来自数值噪声或对实际任务无意义。课程不会把 PPL 差直接变成“质量下降 X%”。把它当描述性信号，并结合任务 fixture。

Why it matters

  • 防止只追 token/s，把量化质量损失藏起来。
  • 提供机器可重复的 regression signal。
  • 训练你固定 tokenizer/corpus/evaluation identity。
  • 让性能×质量 tradeoff 可以被审计。

常见误区

  • “PPL 低 = 聊天一定更聪明”——任务覆盖有限。
  • “不同 tokenizer PPL 可以直接比”——评估单位不同。
  • “同文件名 corpus 就相同”——要 hash。
  • “PPL 高 2% = 质量差 2%”——不是这种线性语义。
  • “随机聊天几次没感觉差，就不用 quality gate”——证据太弱。

小实验

先做 L0：给三组 toy next-token probabilities 手算 negative log loss 和相对 PPL。然后设计一份 quality identity：tokenizer、corpus hash、fixture revision、evaluation argv。

真机阶段再用 Experiment 59/61 采真实 PPL，不在教材里填虚构值。

无 GPU 路径

数学直觉与 identity 设计全部可在 L0 完成。

排错

  • PPL 差异异常巨大：先查 tokenizer/corpus/model identity 和 BOS/context，不先归因量化。
  • 工具输出多个 Final/metric：不要猜，明确 parser 支持范围或人工 review。
  • 跨 runtime PPL 不一致：固定 evaluation semantics，再调查数值/kernel。

Retrieval Practice

  1. Cross-entropy 如何惩罚模型给真实 token 很低概率？
  2. PPL 为什么最适合受控 A/B 而不是万能排行榜？
  3. 为什么 tokenizer identity 是 PPL 可比性的 hard condition？
  4. PPL 不能覆盖哪些实际 LLM 能力？
  5. quality corpus 为什么要 hash？
  6. 为什么性能提升必须与 PPL/target-task evidence 配对？

Decision Rule

任何 quant/backend/execution 优化只有性能证据没有质量证据时，只能说“更快”，不能说“更好”。PPL 只在固定 tokenizer/corpus/evaluation identity 下做描述性比较，并与目标任务 fixture 联合判断。

Transfer

以后换成 KL、task score、exact-match 或 human eval，同样先固定 evaluation identity、原始 evidence 和解释边界。

Quality Gate 不是一个万能阈值，而是一份预先写好的 Acceptance Policy

在看到 candidate 结果前先定义：

baseline artifact:
candidate variable:
exact tokenizer/corpus/eval argv:
PPL signal to record:
target-task fixtures:
hard failure conditions:
human-review conditions:

课程不规定所有模型都用同一个“PPL 允许增加 X%”。不同任务、模型和量化目标的可接受范围不同；关键是阈值或 review 规则要在看结果前定义，避免结果导向地移动门槛。

Worked Example：PPL 几乎没变，但 JSON fixture 失败

假设 candidate 比 baseline 快，PPL 变化很小，但固定 JSON-schema fixture 开始频繁输出无效 JSON。正确结论不是“PPL 没问题所以 candidate 更好”，而是：

distribution-level regression: small / acceptable by policy
target-task correctness: FAIL
overall candidate: BLOCKED for this deployment

质量 gate 是多信号组合；任何目标任务 hard requirement 都不能被平均 PPL 覆盖。

反过来也成立：PPL 变差不等于所有任务都同比例变差

如果 PPL 有明显变化，应该触发调查与更强 target-task review，而不是把 PPL delta 直接翻译成“聊天能力下降同样百分比”。PPL 是概率分布信号，不是用户效用的线性单位。

Evidence Packet

  • baseline/candidate exact model artifact identity；
  • tokenizer revision/hash；
  • corpus bytes/hash；
  • evaluation executable/build 与 exact argv；
  • raw stdout/stderr + machine-readable metric；
  • target-task fixture revision 与 raw outputs；
  • 预先定义的 acceptance/review policy；
  • 最终 PASS/BLOCKED 与 non-claim。

Failure Recovery

  • PPL 异常：先核 identity、BOS/chunk/context/eval semantics。
  • 只有 candidate 失败：确认唯一变量后再考虑量化/kernel 数值问题。
  • PPL 正常、任务失败：保留任务 failure，不能用 PPL 覆盖。
  • 不同 tokenizer：停止直接 PPL 比较，改用适合的同任务指标。

What this lesson does NOT prove

一份 quality gate 只覆盖它实际测到的 corpus 与任务。它不能证明“模型所有能力没有退化”，也不能把 human preference、事实性、安全性、长上下文与工具调用全部压成一个数字。

完成证据

完成本课后，保留一份 learner-owned completion artifact，至少包含：

  • 用自己的话画出或写出本节最小 mental model，并标出关键变量/资源层；
  • 完成本节小实验、worksheet 或无硬件 fallback；有真机时链接 raw Evidence，没有真机时明确标 L0 / DOCUMENTED / DEFERRED-HARDWARE；
  • 写一条绑定 Evidence 的 PASS / FAIL / UNKNOWN / BLOCKED 结论，说明它怎样影响本地 LLM 的容量、性能、兼容、成本或风险判断；
  • 写一句明确 non-claim：这份证据还不能证明什么。

只写“看完了”或抄规格表不算完成。课程要的是可复查的推理产物，而不是阅读打卡。
