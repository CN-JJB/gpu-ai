Storage / Model Loading — 为什么第二次启动突然快很多？

1. GGUF 从磁盘到可推理，中间不止 SSD

GGUF
→ filesystem
→ page cache
→ mmap/read
→ host memory
→ GPU upload
→ backend init
→ health ready
→ first inference
“模型加载时间”不是一个单独的磁盘带宽数字。

2. 最粗糙的读盘模型

T_read
≈
model bytes / effective source bandwidth

20 GiB 模型，如果真的完整从：

0.2 GiB/s HDD

读出来，光读就约：

100s

3. 换 3 GiB/s NVMe

20 / 3
≈ 6.67s

启动当然可能快很多。

但这仍然没包含：

parse
alloc
GPU upload
backend init

4. 第二次为什么可能更快？

Linux 普通文件读和 file-backed mmap 会经过 page cache。

第一次访问以后：

SSD/HDD
→ RAM page cache

第二次可能：

RAM page cache
→ process

而不是重新等磁盘。

5. 所以第二次测出来 15 GiB/s？

不要马上说：

我的 SSD = 15 GiB/s

你可能测到的是：

RAM + page cache

6. 更危险：第一次也不一定冷

你今天早上已经跑过模型。

或者：

indexer
backup
另一个进程

读过它。

所以：

run1 = cold

没有证据就不能这么写。

7. mmap 也经常被误解

mmap(file)

首先是把文件建立到虚拟地址空间的映射。

它不等于：

return 之前已经把全部 20 GiB
从 SSD copy 到 RAM

页面可以在之后访问时 fault 进来。

8. Linux 怎么看一个文件有多少页在 cache？

如果系统有 util-linux 的：

fincore

它可以提供 file-page residency evidence。

但它仍然不能告诉你：

SSD controller cache
GPU upload bottleneck
backend init bottleneck

9. 为什么课程不让你 sudo drop_caches？

因为它会影响整个主机的 page cache，不只是你的模型。

默认实验宁可写：

initial cache state = UNKNOWN

也不为了造一个“漂亮 cold benchmark”去扰动整台机器。

10. 读文件本身会改变实验

你先：

sha256sum 20GB.gguf

然后再测“cold startup”。

SHA 已经把文件读了一遍，可能把大量页面放进 cache。

测量动作自己也可能改变 cache state。

11. GPU upload 是另一个阶段

离散 GPU 全 offload 时，weights 还要进入 device memory。

粗略：

T_ready
≈
T_read/page-fault
+
T_host
+
T_device_upload
+
T_backend

这些阶段实际可能有 overlap/lazy behavior，所以只是 mental model。

12. SSD bandwidth 和 VRAM bandwidth 完全不是一个东西

Startup：

storage → host → GPU

steady decode：

weights resident in VRAM
→ VRAM bandwidth / kernels

因此：

慢硬盘
≠
steady TG 永远慢

13. Synthetic 20 GiB

sourceBWsimple readysteady TG
HDD-like0.2 GiB/s102.67s50 tok/s
SATA-like0.5 GiB/s42.67s50 tok/s
NVMe-like3 GiB/s9.33s50 tok/s
page-cache-like20 GiB/s3.67s50 tok/s

这些全是教学数字。

14. 真正实验怎么写结论？

pass1:
initial cache UNKNOWN
read prefix 512 MiB
2.1 GiB/s

pass2:
after same-file access
8.7 GiB/s

正确：

second pass was faster after same-file read

错误：

SSD speed = 8.7 GiB/s

15. 最后分开测四件事

file/read behavior
startup readiness
first inference
steady PP/TG

这样你才知道升级 SSD 到底是在优化哪一段。

学生闭环 — Storage / Model Loading / Page Cache

硬件门槛：L0 模拟/设计主路径；真实服务或 Linux/NVIDIA 机器是增强。

成本：0 元。

风险：safe；不通过危险电气/固件修改来“制造”故障。

能力目标

  • 把长期运行问题拆成可观察、可复现、可回滚的工程问题。
  • 区分 startup / steady state / failure recovery / energy 等不同系统边界。
  • 任何优化或升级都保留 exact identity 与 rollback/evidence。

小实验 / 反馈

做 Experiment 80：storage/load model；Linux 真机做 Experiment 81：real startup。

Retrieval Practice

  1. 为什么第二次启动更快可能只是 page cache warm，而不是 SSD/模型本身变快？
  2. mmap 与“整个模型立刻读进 RAM”是同一句话吗？
  3. startup time 与 steady-state TG 为什么要分开？
  4. NVMe 更快在哪些情境下可能几乎不改变 decode tok/s？

完成证据

设计 cold/warm startup A/B：记录模型文件、load mode、page residency/cache 状态、startup time、steady inference；不要把 warm-cache 结果冒充磁盘性能。

如何选择 / 迁移

换 OS、runtime 或 GPU 后，先重建 timeline + identity + measurement boundary，再判断“更快/更稳/更省电”是否成立。
