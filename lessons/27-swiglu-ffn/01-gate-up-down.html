LLM 架构 4 — SwiGLU / FFN：Attention 之外的另一块“大肉”

很多 LLM 性能讨论只盯 Attention，但 dense decoder 每层还有一个很大的 FFN。

1. 先看老式两层 FFN

x [M,d]
→ W1 [d,d_ff]
→ activation
→ W2 [d_ff,d]

忽略 bias：

参数 ≈ 2 × d × d_ff

2. SwiGLU 为什么变成三块大矩阵？

gate = x W_gate
up   = x W_up

z = SiLU(gate) ⊙ up

out = z W_down

于是：

W_gate [d,d_ff]
W_up   [d,d_ff]
W_down [d_ff,d]

参数约：

3 × d × d_ff
这里的 gate 不是 MoE router。它是 dense vector gating；gate/up 两个大 projection 都要算。

3. SiLU 是什么？

SiLU(x)
=
x × sigmoid(x)

然后它和另一条 up projection 做逐元素乘法：

SiLU(gate) ⊙ up

这给 FFN 加了乘法门控，而不是单纯 ReLU/GELU 一条支路。

4. 为什么 LLaMA 不是直接用 4d 的 SwiGLU？

经典 FFN 如果：

d_ff = 4d

两矩阵参数：

2d × 4d = 8d²

如果 SwiGLU 还保持 4d：

3d × 4d = 12d²

会明显膨胀。

LLaMA 论文描述采用大约：

(2/3) × 4d = 8d/3

这样三矩阵的粗参数预算重新回到：

3d × 8d/3
≈ 8d²

但真实模型一定以 config 的 intermediate_size 为准。

5. 一个 4096 hidden 的实际量级

用：

d = 4096
d_ff = 11008

SwiGLU FFN 每层：

3 × 4096 × 11008
=
135,266,304 weights

而一个 4096-wide 的传统 MHA Q/K/V/O：

4 × 4096 × 4096
=
67,108,864 weights

FFN 是：

≈ 2.016×

attention projections。

6. 这和显存带宽有什么关系？

仅这层 FFN，如果 FP16：

135,266,304 × 2 bytes
≈ 258 MiB

如果 effective 4.5 bpw：

≈ 72.56 MiB

这是一层，不是整个模型。

Decode 每生成一个 token，又要使用这些 weight matrices。

所以 TG 的 weight streaming 不只是 Attention weights，FFN 往往是更大的那一块。

7. Prefill 为什么更容易吃满 GPU？

假设 prompt 512 token：

[512,4096] × [4096,11008]
→ [512,11008]

同一份 weight matrix 为 512 行 token 做工作。

矩阵很大，weight reuse / arithmetic intensity 高。

8. Decode 突然只剩一行

[1,4096] × [4096,11008]
→ [1,11008]

权重还是那么大，但有效 token rows 变成 1。

所以：

compute per weight byte ↓
memory-bandwidth importance ↑

9. 一个只看 weight 的 Roofline 直觉

三块矩阵大约有：

6 M d d_ff FLOPs

权重存储：

3 d d_ff × bits/8 bytes

所以：

AI_weight ≈ 16M / bits

FP16 时：

M=1   → ~1 FLOP/byte
M=512 → ~512 FLOP/byte

真实 kernel 还要算 activation、dequant、cache，所以这不是 benchmark；它只是解释 PP/TG 为什么进入不同 Roofline 区域。

10. FlashAttention 为什么可能 PP 大涨、TG 小涨？

因为 FlashAttention 优化的是 attention I/O。

模型后面仍有：

Q/K/V/O
+ FFN gate/up/down
+ norm/residual
+ LM head

如果 TG 的最大字节来源是 FFN/其他 weight streaming，那么 Attention 加速不会让整模型同比例加速。

11. Quant 为什么对 FFN 很关键？

FFN 是大权重块。

16-bit
→ 8-bit
→ 4.x bpw

可以大幅减少 storage / memory traffic。

但是课程前面那条规则不变：

Q4 storage
!= native INT4/FP4 matrix compute

backend/kernel 仍决定真正执行路径。

12. 以后看 config，别漏 intermediate_size

hidden_size
intermediate_size
hidden_act

这几个字段会告诉你 FFN 到底有多宽。

两个都叫“8B”的模型，FFN/attention 比例也可能不同。
