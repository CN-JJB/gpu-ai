Serving Capacity — 2 req/s × 3 秒，为什么系统里平均有 6 个请求？

Prerequisite Check

开始前，你应该理解上一节的 request timeline，能区分 queue wait、active service time 与端到端 latency，并知道本地 LLM 的 active sequence 会消耗 slot、计算时间和 KV cache。

如果还不熟：先记住三个量就够继续：λ = 单位时间完成的请求数，W = 一个请求在所定义边界内停留的平均时间，L = 同一边界内平均同时存在的请求数。三者必须来自同一个系统边界。

真实问题

你只有一台本地 LLM 主机，想知道“最多能同时服务几个人”。直接把显存除以一个固定 KV 数字，或者把平均并发向上取整，都可能得到危险答案：burst、长 context 与慢 decode 会同时把 queue、slot 和 KV 压力推高。

真正的问题是：在给定 arrival pattern、请求长度和 SLO 下，系统能稳定承载多少 active work，何时会先撞到 slot、KV、显存或 tail-latency 硬门槛？Little's Law 用来做容量 sanity check，而不是替代真实 trace 与资源测量。

1. Little's Law

L = λ W

这里：

L = 平均有多少东西在系统里
λ = 每秒通过多少
W = 每个东西平均待多久

2. 最简单例子

2 req/s
×
3 s/request
=
6 requests

平均有 6 个请求 somewhere in system。

“平均 6 个”不是“每时每刻正好 6 个”，更不是“配 6 个 slot 就完事”。

3. 最大陷阱：你说的“system”到底是什么？

端到端：

arrival
→ queue
→ active
→ completion

此时：

L_system
=
queued + active 的平均数

但 server slots 一般更接近：

active requests

所以不能直接：

ceil(L_system)
=
slots

4. 把它拆成三份

W_system
=
W_queue
+
W_active

于是同一个 throughput λ 下：

L_system = λW_system
L_queue  = λW_queue
L_active = λW_active

并且：

L_system
=
L_queue
+
L_active

10. 但 Peak 呢？

同一个 trace：

average system = 3.0
peak system    = 5

average active = 2.7
peak active    = 4

所以如果你只按平均 2.7 配 3 个 slots，突发时仍然会排队。

11. 和 KV 怎么接？

假设只是教学 proxy：

每个 active sequence
≈ 1.5 GiB KV

平均：

2.7 × 1.5
=
4.05 GiB

Peak：

4 × 1.5
=
6 GiB

这已经差了快 2 GiB。

真实模型还更复杂，因为每个 sequence 的当前 context 不一样。

12. Queue 中的请求为什么不能直接乘 KV？

它还没被 server admission 到 active model sequence 时，通常没有同等 active KV。

所以：

L_system × KV

可能把排队请求也算成 active KV。

13. Little's Law 不能给你 p95

两个 workload 可以：

λ 一样
mean W 一样

但：

一个非常平稳
另一个偶尔卡 10 秒

所以 tail latency 仍然回 Slice 34 测。

14. 服务器过载时更不能乱套

如果长期：

arrival rate
>
completion rate

queue 会越来越长。

这时拿 arrival rate 乘一个旧的平均 latency，不是在做容量规划，是在掩盖 overload。

15. 对垃圾佬很实用的一点

如果你的两张便宜 GPU 因 PCIe 导致 TG 变慢：

W_active ↑

要维持同样请求吞吐：

L_active = λW_active ↑

于是：

需要同时存活的 sequences ↑
KV 压力 ↑

所以 GPU “速度慢一点”和“显存够不够”会在 Serving 里重新耦合起来。

硬件门槛：L0 模拟主路径；真实 server 增强 L1。

成本：0 元。

风险：默认 safe；涉及网络暴露时只在受控本地环境完成，先审计再开放。

能力目标

  • 从“单机 benchmark”升级到“用户看到的服务行为”。
  • 用 tail/SLO/capacity/fairness/exposure 约束系统，而不是只追总 tok/s。
  • 能通过 trace/metrics 解释一个服务为什么好用或不好用。

教材补全：Little's Law 不是“算 slot 个数”的公式

三个量必须来自同一个边界

L = λW

如果 W 是：
arrival → completion

那么 L 必须是：
queue + active

如果 W 是：
service start → completion

那么 L 才更接近：
active only

最常见的错误，是把端到端 W 和 active-only L 拼在一起。

Worked Example：平均并发够了，为什么还会爆？

假设稳态吞吐 0.8 req/s，平均 active time 4 s：

L_active = 0.8 × 4 = 3.2

这只说平均 active requests 约 3.2。若 arrival 有 burst，瞬时 active 可能到 6；如果每条 sequence 在当前 context 下需要 1.2 GiB KV：

average KV proxy ≈ 3.84 GiB
burst KV proxy   ≈ 7.20 GiB

容量设计必须同时看平均、峰值、分布和安全余量。

KV 不是固定“每请求 X GiB”

KV/request
≈ function(
  layers,
  kv heads,
  head dim,
  dtype,
  current context,
  cache policy
)

GQA、滑窗、量化 KV、paged cache 都会改变这个关系。所以课程里的固定 GiB/request 只能当教学 proxy。

容量规划四步

  1. 定义 workload：arrival、prompt/output 长度、并发目标。
  2. 测服务时间与 queue 时间分布。
  3. 用 Little's Law 做 sanity check，而不是唯一容量答案。
  4. 再用真实 KV/VRAM telemetry 验证 slot 数与 context 上限。

常见误区

  • 误区：平均 active=4，所以 4 slots 足够。
    纠正：burst 和 tail 会造成排队。
  • 误区：更多 slots 一定提高吞吐。
    纠正：可能先把 KV 吃满，再让每条 sequence 变慢。
  • 误区：显存还有 2 GiB，所以还能再开一条。
    纠正：还要留 workspace、allocator fragmentation 和增长中的 context。

Decision Rule

slot/concurrency 必须由 workload × service time × KV/VRAM 共同决定。不能只看一张卡“有多少 GiB”。
