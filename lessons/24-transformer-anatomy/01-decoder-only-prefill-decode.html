Transformer Anatomy · L0→L1

Decoder-only Transformer：一次生成为什么天然分成 Prefill 与 Decode？

本地 LLM 的很多“怪现象”——长提示词首字慢、生成阶段 token/s 低、KV cache 越来越大、同一 GPU 的 PP 与 TG 差很多——都可以从 decoder-only Transformer 的两阶段执行解释。

Prerequisite Check

你只需要知道模型由多层重复 block 组成，输入文本会先变成 token。不会矩阵乘法也可以先用“把一批向量乘以权重”理解。

真实问题：为什么一个模型的“速度”至少要有两个数字？

当你把 2000-token prompt 交给模型，它可以一次并行处理很多已有 token；但开始生成后，第 N+1 个 token 必须等第 N 个 token 产生。这两种计算形状完全不同。

1. Decoder-only 的最小结构

tokens
→ embedding
→ [norm → attention → residual
   → norm → FFN/MoE → residual] × L layers
→ final norm
→ vocabulary projection
→ logits
→ sampler chooses next token

每生成一个新 token，它又被送回模型，继续下一轮。

2. Prefill：把已有 prompt 一次“读进去”

Prefill 已经知道整段 prompt，因此同一层可以对很多 token 并行做大矩阵计算，并构建每层的 KV cache。

prompt: t1 t2 t3 ... tN
      ↓
process many positions in parallel
      ↓
produce KV for positions 1..N

矩阵 shape 较大时，GPU 更容易利用矩阵单元和大量并行度，因此 prefill 常表现得更 compute-heavy。

3. Decode：每轮只有一个/少量新 token

生成阶段必须自回归：

history + token N
→ compute token N+1
→ append KV
→ history + token N+1
→ compute token N+2

单用户小 batch 时，每轮新工作规模较小，但每层仍要读取大量模型权重，因此权重流式读取与 memory bandwidth 常变得更重要。

4. 为什么 PP 与 TG 要分开？

Prefill / PPDecode / TG
已知 token 数很多每轮 1 或少量
并行度高低得多
矩阵形状大更像 matrix-vector / skinny GEMM
常见瓶颈compute + memorymemory bandwidth / kernel overhead
用户感受首 token 前等待文字流出速度

因此一个“总 token/s”会混掉两种系统行为。

5. Attention 在 Prefill 与 Decode 中也不同

Prefill 要为整段 token 建立 Q/K/V，并处理 causal attention；decode 只为新 token 生成新的 Q/K/V，但 query 必须读取已有历史的 K/V。

decode at position N:
Q_new attends to K_1..K_N
using V_1..V_N

所以 context 越长，decode attention 读取的 KV 历史越多；现代 GQA/MQA、KV quant、sliding window 等机制正是在控制这个成本。

6. KV cache：为什么不每轮重算整个历史？

历史 token 的 K/V 在确定模型和位置后不会变化。把它们缓存起来，可以避免每生成一个 token 都从头计算整段历史。

代价是显存/统一内存随：

layers × context tokens × KV heads × head dimension × bytes × K/V

增长。后续 KV 专课会精算。

Worked Example：为什么长 prompt 会 TTFT 高，但生成后还算流畅？

假设用户贴入 12k token 文档。系统首先要 prefill 12k token 并建立 KV，因此首 token 等待明显；一旦完成，decode 每轮只新增一个 token，尽管会读长 KV，仍可能稳定以某个 TG 输出。

反过来，一个 prompt 很短的聊天可能 TTFT 极低，但如果模型权重大、显存带宽不足，TG 仍然慢。

7. Batch / concurrency 为什么改变瓶颈？

多个序列同时 decode，可以把多个新 token 组成更大的矩阵，提高计算资源利用率；但也增加 KV cache、调度和 memory pressure。服务端的吞吐优化经常通过 batching 换取单请求 latency。

8. 从模型结构映射到 GPU 选择

  • Weights fit：决定模型是否能完整驻留 accelerator memory。
  • Memory bandwidth：小 batch decode 很关注。
  • Matrix throughput：prefill/大 batch 更容易利用。
  • KV capacity：长 context/多并发决定额外内存。
  • Kernel/backend：决定理论硬件能否被实现利用。

Why it matters

  • 解释 PP/TG 为什么不是同一性能指标。
  • 解释长 prompt、长 context、并发分别增加什么成本。
  • 让显存预算从“模型文件大小”升级为 weights+KV+buffers。
  • 为 attention、GQA、speculative decoding、serving batching 建立共同底座。

常见误区

  • “模型每个 token 都从头读完整 prompt 并重算全部 K/V”——KV cache 避免了大量重算。
  • “Prefill 快的 GPU decode 一定同比例快”——两阶段瓶颈不同。
  • “context 只影响首 token”——decode 也要访问更长 KV。
  • “batch 越大越好”——吞吐增加可能牺牲 latency/显存。

小实验与预期观察

用纸面或课程 benchmark fixture 比较 512、4096、16384 token prompt，固定输出 128 token。先预测：TTFT/PP 工作会怎样变，TG 是否完全不受影响，KV memory 怎样变。

真机阶段再测。预期模式是 prompt 越长 prefill 工作越多；KV 越大；decode attention 成本也会随历史长度变化，但具体幅度必须实测。

无 GPU 路径

L0 用时间轴图和 KV 预算公式完成。无需运行模型。

排错

  • 首 token 慢：先分解 model load、prompt tokenization、prefill，不直接怪 decode。
  • TG 随 context 增长下降：检查 KV attention/memory、KV dtype、backend。
  • 并发一开 OOM：重新预算每 slot KV 与 runtime buffer。

Retrieval Practice

  1. Prefill 与 decode 的依赖关系为什么不同？
  2. 为什么 decode 小 batch 更容易受 memory bandwidth 限制？
  3. KV cache 避免了什么重算，又增加了什么资源？
  4. 长 context 为什么既影响容量又可能影响 decode？
  5. batching 为什么可能提高总吞吐却拉高单请求延迟？
  6. 从 decoder-only 结构列出选 GPU 时至少五个相关维度。

Decision Rule

任何 LLM “速度”比较至少分 PP/TTFT 与 TG/ITL，并绑定 context、batch/concurrency、模型与 runtime。不能用单一 token/s 代表所有交互场景。
