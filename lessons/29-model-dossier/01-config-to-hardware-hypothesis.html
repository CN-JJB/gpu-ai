LLM 架构 6 — 不看跑分，先从 config.json 做一份 Model Dossier

1. 目标不是“算出显存精确值”

目标是先把已知结构整理出来：

模型是谁
→ attention 什么结构
→ KV 多大
→ FFN 多宽
→ 有没有 MoE
→ 权重规模
→ 哪些东西还必须实测

2. 为什么 8B/14B 远远不够？

总参数量不知道：

  • Hq / Hkv；
  • head_dim；
  • FFN expansion；
  • MoE top-k；
  • sliding/local attention；
  • RoPE/context scheme。

这些都会改变本地部署。

公式只能证明“肯定不够”的一部分情况，不能证明 runtime 一定能 fit。

9. 为什么不自动给 PP/TG？

因为 config 只能给 hypothesis：

large dense weights
→ TG bandwidth might matter

large prompt
→ PP matrix/kernel might matter

large Hkv/context
→ KV might matter

MoE
→ expert placement/routing might matter

真正的数字必须进 Experiment 40 实测。

学生闭环 — Model Architecture Dossier

硬件门槛：L0 主路径；真实模型/硬件只用于增强。

成本：0 元。

风险：safe。

能力目标

  • 把“模型/输入/质量/benchmark 身份”变成可审计对象。
  • 能指出公式或配置的适用边界，不把近似写成事实。
  • 为后续硬件选择提供可重复的 workload contract。

小实验 / 反馈

做 Experiment 52：dossier model；再做 Experiment 53：real model dossier。

Retrieval Practice

  1. 为什么 config.json 只能给 hardware hypothesis，不能直接给 benchmark 结论？
  2. 哪些字段影响权重容量，哪些影响 KV，哪些影响每 token active compute？
  3. 模型 repo 写 128K context，为什么还不能说明你的本地 runtime 能稳定跑 128K？
  4. 如果模型是 MoE，你的 dossier 里必须比 dense 多写哪几类字段？

完成证据

完成一个真实模型 Architecture Dossier：参数/层数/hidden/FFN/attention/KV/context/MoE/weight format，并把每个字段映射到容量、带宽、compute 或 runtime 风险。

如何选择 / 迁移

遇到新模型或新 backend 时，优先冻结 身份 + 输入 + protocol，再谈性能或质量；不可比的数据宁可 BLOCKED，也不要硬排排行榜。
