Overload / Admission Control — 一个都不拒绝，为什么反而可能更差？

Prerequisite Check

开始前，你应该能解释 SLO、queue、active capacity 和 stable throughput，并理解“到达速率”与“完成速率”不是一回事。

如果还不熟：把 offered load 想成不断进入系统的工作，把 service capacity 想成系统稳定完成工作的上限。若长期 offered load > capacity，等待工作会累积；这不是靠更长队列就能修好的。

真实问题

你的本地 LLM 平时很好用，但一到多人同时请求，TTFT 越来越长。你可以继续排队、立即拒绝、让客户端重试，或者限制单次工作量；每一种选择都会改变用户体验和系统稳定性。

真正的问题是：当负载接近或超过稳定容量时，怎样让一部分请求快速、明确地失败，而不是让所有请求一起陷入长尾；同时又不让 retry 把过载继续放大？Admission control 的目标不是追求“0 reject”，而是保护可预测的 SLO。

学生闭环 — Overload / Admission Control

硬件门槛：L0 模拟主路径；真实 server 增强 L1。

成本：0 元。

风险：默认 safe；涉及网络暴露时只在受控本地环境完成，先审计再开放。

能力目标

  • 从“单机 benchmark”升级到“用户看到的服务行为”。
  • 用 tail/SLO/capacity/fairness/exposure 约束系统，而不是只追总 tok/s。
  • 能通过 trace/metrics 解释一个服务为什么好用或不好用。

小实验 / 反馈

教材补全：过载时真正要保护的不是“HTTP 200 比例”

系统只有四种基本选择

1. queue
2. reject
3. shed/degrade work
4. add capacity

如果长期 offered load 大于 service capacity，前三种只是决定“怎么失败”；只有第四种或降低 workload 才能消除持续过载。

Worked Example：无界队列为什么会制造“假可用”

容量 1 req/s，持续到达 1.4 req/s。即使每个请求最终都返回 200，queue 仍会以约 0.4 req/s 的速度增长。

after 60 s:
≈ 24 requests accumulated

如果每个服务 1 s：
最尾部请求还要额外等几十秒

这类系统从 HTTP 成功率看“健康”，从用户 SLO 看已经失败。

Admission Policy 要写成可审计规则

accept if:
active_slots < limit
AND kv_headroom >= threshold
AND queue_depth < limit
AND estimated_work <= policy

else:
reject / retry-after / degrade

不要求你一定采用这些字段，但要求规则可解释、可复现。

Retry 的三个条件

  • 只对可能瞬时恢复的失败重试。
  • 必须有 backoff，通常还需要 jitter，避免大量客户端同步重试。
  • 必须有 retry budget；否则“可靠性机制”会变成负载放大器。

取消也要端到端验证

客户端断开以后，检查 scheduler 是否真的释放 slot、KV 和计算。否则你可能同时拥有：

client thinks request is gone
server still generating
GPU still busy

故障排查顺序

  1. 先看 offered load 是否已经超过稳定 capacity。
  2. 看 queue depth 与 queue wait 是否持续增长。
  3. 看 active slots / KV 是否饱和。
  4. 看 reject 后是否出现 retry amplification。
  5. 验证 cancel 是否真的释放资源。

Decision Rule

一个系统宁可明确地、快速地拒绝一部分工作，也不应让所有请求一起进入不可控的长尾。是否接受这种 tradeoff，由你的 SLO 决定。
