Overload / Admission Control — 一个都不拒绝，为什么反而可能更差？

1. 先看最基本不等式

incoming work
>
server can finish

如果持续这样，queue 一定增长。

你不能靠：

“先都收下来”

凭空创造 GPU 算力。

2. 无界队列的假象

表面：

HTTP 200
没有 reject

实际上：

TTFT
2s
4s
8s
...
没有立即失败，不等于服务健康。

3. Bounded Queue

比如：

1 active
+
最多 2 waiting

第四个再来：

REJECT

这牺牲了一部分请求成功率，但保护 queue 不无限增长。

4. Toy workload

10 requests
每 0.5 s 来一个

server:
1 request / second

短时间 offered load 约：

2 req/s

处理能力：

1 req/s

明显 overload。

5. 无界 queue

10 attempts
10 completed
0 rejected

mean wait = 2.25 s
p95 wait  = 4.5 s

看起来“全部成功”。

但交互式用户已经很难受。

6. Queue limit = 2，不重试

10 attempts
7 completed
3 rejected

p95 wait
=
2.0 s

它在做一个明确 tradeoff：

availability ↓
tail waiting ↓

7. 最危险的是立即重试

被 reject 就：

100 ms 后再试
100 ms 后再试
100 ms 后再试

结果：

10 original requests
→ 19 HTTP attempts

但还是：
7 completed
3 dropped
请求量扩大 1.9×，成功数完全没提高。

8. 这就是 retry amplification

overload
→ reject
→ immediate retry
→ more offered load
→ more reject
→ more retry

客户端本来想“更可靠”，结果自己给服务器补刀。

9. Backoff

改成：

0.5 s
1 s
2 s

这组 toy：

18 attempts
10 completed

最终都活下来了。

但是：

p95 wait = 5.5 s

所以：

eventual success
!= good UX

10. Timeout 也不是免费取消

用户浏览器超时：

client stopped waiting

不能自动推导：

GPU stopped generation

必须确认 cancellation 是否真的传到 scheduler/model。

11. Admission 不应该只看请求个数

这两个请求：

128 prompt + 32 output

和：

64k prompt + 4k output

资源成本完全不一样。

更好的 admission 可以考虑：

slots
KV headroom
prompt tokens
output budget
priority
SLO

12. 对本地 LLM 很现实

24 GiB 卡可能：

模型 weights fit

但：

4 个长 context
→ KV 快满了

第五个请求不是“多一个 HTTP 请求”那么简单。

13. 最终目标

保护 TTFT/ITL SLO
+
限制 backlog
+
有限重试
+
足够吞吐

而不是：

永不 reject
